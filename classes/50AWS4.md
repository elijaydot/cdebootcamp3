## Part 1: Warm-Up Quiz & Core Principle Review
*(Facilitated by Ayodeji Ajayi)*

The session opened with an interactive quiz reinforcing core cloud networking principles:

1. **Route Table Terminology:**
   * **Destination:** *Where* traffic is headed (e.g., `0.0.0.0/0` for the entire internet, or a specific CIDR range).
   * **Target:** The gateway, network interface, or connector used to get there (e.g., `local` for intra-VPC communication, or `igw-xxxx` for an Internet Gateway).
2. **What Makes a Subnet "Public"?**
   * Simply tagging or naming a subnet `public_subnet` does **not** make it public. A subnet becomes public **if and only if** its associated Route Table contains a route directing `0.0.0.0/0` to an active **Internet Gateway (IGW)**.
3. **The Universal Internet CIDR Block:**
   * `0.0.0.0/0` represents all possible IPv4 addresses across the global internet.
4. **Data Egress Hierarchy (Ascending Order of Cost):**
   * **Intra-AZ:** Free ($0.00/GB) within the exact same Availability Zone.
   * **Inter-AZ:** \~$0.01/GB across different AZs in the same Region.
   * **Inter-Region:** \~$0.02/GB across separate geographic regions (e.g., Frankfurt to Ireland).
   * **Internet Egress:** \~$0.09/GB routing data outside AWS to the public internet or external warehouses (the most expensive).

1. **Virtual Private Cloud (VPC):** An isolated, logically defined virtual data center provisioned inside a specific AWS Region.
2. **Subnets:** Slices of the parent VPC CIDR block bound to specific Availability Zones (AZs).
3. **Route Table (RT):** The virtual router containing rules (routes) that dictate where network packets leaving a subnet are directed.
4. **Internet Gateway (IGW):** The redundant, highly available VPC edge component enabling bi-directional communication between instances in your VPC and the public internet.

## Part 3: Subnet Sizing & The "AWS 5 Reserved IPs" Rule

### 1. The Class Demo Sizing Strategy
Instead of building a massive `/16` network ($65,536$ IPs) where tracking individual addresses is impossible, Mayowa deliberately chose a compact **`/27` CIDR block** for live tracking:

$$\text{Total IPs in } 10.0.0.0/27 = 2^{(32 - 27)} = 2^5 = 32 \text{ IPs} \quad (\text{Range: } 10.0.0.0 \text{ to } 10.0.0.31)$$

He then split this evenly into two subnets using `/28`:
* **Subnet A (Target: Public):** `10.0.0.0/28` $\rightarrow$ 16 IPs (`10.0.0.0` to `10.0.0.15`)
* **Subnet B (Target: Private):** `10.0.0.16/28` $\rightarrow$ 16 IPs (`10.0.0.16` to `10.0.0.31`)

### 2. The 5 Reserved AWS IPs (Crucial Interview Knowledge!)
When creating a subnet with 16 IPs, the AWS Console displays only **11 Available IPv4 Addresses**.

AWS permanently reserves **5 IP addresses** in every single subnet for internal routing and network management:
* **First IP (`.0`):** Network Address (identifies the subnet wire).
* **Second IP (`.1`):** VPC Router (the internal default gateway).
* **Third IP (`.2`):** AWS DNS Server (maps to `AmazonProvidedDNS`).
* **Fourth IP (`.3`):** Reserved by AWS for future internal expansion.
* **Last IP (`.15` in a `/28`, or `.255` in a `/24`):** Network Broadcast Address (AWS does not support broadcast, but reserves the address).

$$\text{Usable IPs} = 2^{(32 - \text{Prefix})} - 5$$

> **Official AWS Reference:** [AWS Subnet Sizing Documentation](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)  
> **Subnet Conversion Tool:** [IP Address Guide CIDR Utility](https://www.ipaddressguide.com/cidr)

## Part 4: Route Tables & The Target vs. Destination Paradigm

### 1. The Commute Analogy
To make route tables intuitive, Mayowa used an everyday travel analogy:
* **Destination:** The physical location you want to reach (e.g., Josephine's House or your company's office).
* **Target:** The vehicle or conduit used to travel there (e.g., your personal car, an Uber, or walking on your legs).
* **In AWS Terms:**
  * **Destination:** `0.0.0.0/0` (Anywhere on the public internet).
  * **Target:** `igw-0123456789abcdef0` (The Internet Gateway attached to the VPC).

### 2. Main Route Table vs. Custom Route Table
* **Main Route Table:** Automatically created alongside every new VPC. It defaults to routing all internal CIDR traffic to `local`.
  * *Best Practice:* Keep the Main Route Table private and dormant. Never route the Main Route Table directly to an Internet Gateway.
* **Custom Route Table:** Explicitly created and associated with specific subnets to control external routing boundaries.

## Part 5: The Public DNS Hostname Gotcha

When launching an EC2 instance into a newly created custom public subnet:
1. You may check **Auto-assign Public IP**, granting the virtual server an external public IP address (e.g., `13.60.30.105`).
2. However, the **Public IPv4 DNS** field in the AWS Console remains completely blank.
3. **The Root Cause:** AWS automatically enables DNS resolution, but leaves **DNS Hostnames disabled by default** on all custom VPCs.
4. **The Fix:**
   * Go to **VPC Console** $\rightarrow$ Select your custom VPC $\rightarrow$ **Actions** $\rightarrow$ **Edit VPC settings**.
   * Check **Enable DNS hostnames**.
   * Save changes.
   * Refreshing the EC2 dashboard will immediately reveal the fully qualified domain name:  
     `ec2-13-60-30-105.eu-north-1.compute.amazonaws.com`

## Part 6: Cloud FinOps — The Complete Data Transfer Cost Matrix

Mayowa closed the theoretical session by warning against unoptimized cloud architectures that incur massive network transfer fees:

```
+---------------------------------------------------------------------------------------+
| AWS Data Transfer Cost Matrix (Ingress vs. Egress)                                    |
+---------------------------------------------------------------------------------------+
| Communication Path                                  | Cost (USD / GB)                 |
+-----------------------------------------------------+---------------------------------+
| Data Ingress (Any external data coming INTO AWS)    | FREE ($0.00 / GB)               |
| Intra-AZ Transfer (Same Subnet / Same AZ)           | FREE ($0.00 / GB)               |
| Inter-AZ Transfer (Across AZs in the same Region)   | ~$0.01 per GB each way          |
| Inter-Region Transfer (e.g., Frankfurt to Ireland)  | ~$0.02 per GB                   |
| Internet Egress (Out of AWS to Snowflake/Internet)  | ~$0.09 per GB (FinOps Danger!)  |
+-----------------------------------------------------+---------------------------------+
```

### The $900 Data Pipeline Penalty Trap:
If an ETL tool (like Airflow or Airbyte) extracts **10 Terabytes ($10,000\text{ GB}$)** of database logs from an AWS VPC and sends them across the public internet to an external data warehouse:

$$10,000 \text{ GB} \times \$0.09/\text{GB} = \$900 \text{ in network egress fees alone!}$$

*Senior Engineering Solution:* Keep compute and storage inside the same AWS Region/AZ, or route traffic privately using **AWS PrivateLink** or **VPC Peering**.

> **Official AWS Reference:** [AWS EC2 On-Demand Pricing & Data Transfer](https://aws.amazon.com/ec2/pricing/on-demand/)

## Part 8: Complete Hands-On Lab & Demo Guide

This section contains the exact end-to-end technical steps to reproduce the live VPC demo conducted during the session.

### Demo Objective:
Build a custom VPC (`10.0.0.0/27`), carve out a public subnet (`10.0.0.0/28`), deploy and attach an Internet Gateway, configure a custom route table, toggle DNS hostnames, launch an EC2 instance, verify IP and DNS assignments, and execute a clean teardown.

---

### Step 1: Create the Custom Virtual Private Cloud (VPC)
1. Log in to the **AWS Management Console** and ensure you are in your assigned region (e.g., `eu-north-1` Stockholm).
2. Navigate to **VPC** $\rightarrow$ Click **Create VPC**.
3. Under **VPC settings**, choose **VPC only** *(avoid "VPC and more" so you can configure each architectural component manually)*.
4. **Name tag:** `Group_XX_cde_bytes_vpc` *(Replace `Group_XX` with your assigned team group identifier)*.
5. **IPv4 CIDR block:** Choose **IPv4 CIDR manual input**.
6. **IPv4 CIDR:** Enter `10.0.0.0/27`.
7. **Tenancy:** Leave as `Default`.
8. Click **Create VPC**.

---

### Step 2: Carve Out Subnet A (Public Subnet)
1. In the left navigation menu, click **Subnets** $\rightarrow$ Click **Create subnet**.
2. **VPC ID:** Select your newly created `Group_XX_cde_bytes_vpc`.
3. **Subnet name:** `Group_XX_subnet_a`.
4. **Availability Zone:** Select the first zone (e.g., `eu-north-1a`).
5. **IPv4 subnet CIDR block:** Enter `10.0.0.0/28`.
6. Click **Create subnet**.
7. *Verification:* Inspect the subnet list. Notice that under **Available IPv4 addresses**, AWS displays **11** (16 total minus the 5 reserved addresses).

---

### Step 3: Provision and Attach the Internet Gateway (IGW)
1. In the left navigation menu, click **Internet Gateways** $\rightarrow$ Click **Create internet gateway**.
2. **Name tag:** `Group_XX_cde_bytes_igw`.
3. Click **Create internet gateway**.
4. Notice the state is currently **Detached** (colored in amber/yellow).
5. Click **Actions** $\rightarrow$ Select **Attach to VPC**.
6. In the **Available VPCs** dropdown, select `Group_XX_cde_bytes_vpc`.
7. Click **Attach internet gateway**. State will turn green (**Attached**).

---

### Step 4: Create and Configure the Custom Route Table
1. In the left navigation menu, click **Route Tables** $\rightarrow$ Click **Create route table**.
2. **Name:** `Group_XX_cde_bytes_rt`.
3. **VPC:** Select `Group_XX_cde_bytes_vpc`.
4. Click **Create route table**.
5. With `Group_XX_cde_bytes_rt` selected, click the **Subnet associations** tab below $\rightarrow$ Click **Edit subnet associations**.
6. Check the box next to `Group_XX_subnet_a`.
7. Click **Save associations**.
8. Click the **Routes** tab $\rightarrow$ Click **Edit routes**.
9. Click **Add route**:
   * **Destination:** Enter `0.0.0.0/0`.
   * **Target:** Select **Internet Gateway** $\rightarrow$ Select `Group_XX_cde_bytes_igw`.
10. Click **Save changes**.
11. *Visual Verification:* Navigate back to **Your VPCs**, select `Group_XX_cde_bytes_vpc`, and inspect the **Resource map**. `Group_XX_subnet_a` should now display with a **Green public badge**, showing an active path through your route table out to the Internet Gateway.

---

### Step 5: Enable DNS Hostnames on the VPC
1. In **Your VPCs**, select `Group_XX_cde_bytes_vpc`.
2. Click **Actions** $\rightarrow$ Click **Edit VPC settings**.
3. Under **DNS settings**, verify that **Enable DNS resolution** is checked.
4. Check the box for **Enable DNS hostnames**.
5. Click **Save changes**.

---

### Step 6: Launch an EC2 Instance into the Custom Subnet
1. Navigate to the **EC2 Console** $\rightarrow$ Click **Launch instances**.
2. **Name:** `Group_XX_demo_server`.
3. **Application and OS Images:** Select **Amazon Linux** (or **Ubuntu**).
4. **Instance type:** Select `t3.micro` (or `t2.micro`).
5. **Key pair:** Proceed without a key pair or select an existing `.pem` key.
6. Under **Network settings**, click **Edit**:
   * **VPC:** Select `Group_XX_cde_bytes_vpc`.
   * **Subnet:** Select `Group_XX_subnet_a`.
   * **Auto-assign public IP:** Select **Enable**.
   * **Firewall (security groups):** Select **Create security group** or choose the default VPC security group.
7. Click **Launch instance**.

---

### Step 7: Verify Subnet IP Consumption and DNS Propagation
1. Go to **EC2** $\rightarrow$ **Instances** and select `Group_XX_demo_server`.
2. Observe the details panel:
   * **Private IPv4 address:** An IP from your subnet pool will be assigned (e.g., `10.0.0.12`).
   * **Public IPv4 address:** Assigned an external address (e.g., `13.60.30.105`).
   * **Public IPv4 DNS:** A fully resolved domain string is visible (e.g., `ec2-13-60-30-105.eu-north-1.compute.amazonaws.com`).
3. Return to **VPC** $\rightarrow$ **Subnets** $\rightarrow$ Select `Group_XX_subnet_a`.
4. Notice that **Available IPv4 addresses** has dropped from **11 to 10**, proving the EC2 instance claimed a private IP.

---

### Step 8: Complete Teardown & Resource Hygiene
To avoid unwanted account charges or hitting regional quotas (max 5 VPCs per region), clean up resources in this exact reverse sequence:
1. **Terminate the EC2 Instance:**
   * Go to **EC2** $\rightarrow$ **Instances** $\rightarrow$ Select `Group_XX_demo_server`.
   * Click **Instance state** $\rightarrow$ **Terminate instance**. Wait until it transitions to `Terminated`.
2. **Detach and Delete the Internet Gateway:**
   * Go to **VPC** $\rightarrow$ **Internet Gateways** $\rightarrow$ Select `Group_XX_cde_bytes_igw`.
   * Click **Actions** $\rightarrow$ **Detach from VPC** $\rightarrow$ Confirm Detach.
   * Click **Actions** $\rightarrow$ **Delete internet gateway** $\rightarrow$ Type `delete`.
3. **Delete the Custom Route Table:**
   * Go to **Route Tables** $\rightarrow$ Select `Group_XX_cde_bytes_rt`.
   * Click **Actions** $\rightarrow$ **Delete route table** $\rightarrow$ Confirm.
4. **Delete the Subnet:**
   * Go to **Subnets** $\rightarrow$ Select `Group_XX_subnet_a`.
   * Click **Actions** $\rightarrow$ **Delete subnet** $\rightarrow$ Confirm.
5. **Delete the VPC:**
   * Go to **Your VPCs** $\rightarrow$ Select `Group_XX_cde_bytes_vpc`.
   * Click **Actions** $\rightarrow$ **Delete VPC** $\rightarrow$ Type `delete` to confirm.

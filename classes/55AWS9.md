## Part 2: OLTP vs. OLAP & Columnar Block Storage

```
               [ Row-Oriented Storage (PostgreSQL / OLTP) ]
  Block 1 (8 KB):  [ ID: 1 | Name: Firex  | Age: 11 | Country: Nigeria ]
  Block 2 (8 KB):  [ ID: 2 | Name: Lekan  | Age: 10 | Country: Germany ]
  
  Query: SELECT AVG(age) FROM students;
  Result: Engine must read BOTH Block 1 and Block 2 into memory, wasting I/O on Name & Country!

-------------------------------------------------------------------------------------------

               [ Columnar Storage (Amazon Redshift / OLAP) ]
  Block A (1 MB):  [ Name: Firex, Lekan, Dennis, Mayowa, Zainab, Habib ... ]
  Block B (1 MB):  [ Age:  11,    10,    28,     32,     24,     29    ... ]
  Block C (1 MB):  [ Country: NG, DE,    US,     DE,     NG,     UK    ... ]
  
  Query: SELECT AVG(age) FROM students;
  Result: Engine reads ONLY Block B! Skips Blocks A and C completely (90%+ Disk I/O reduction).

```

### 1. Why Transactional Databases Fail at Analytics

* **OLTP Systems (PostgreSQL, MySQL):** Optimized for rapid, single-row `INSERT`, `UPDATE`, and `DELETE` operations. Data is stored in **row-oriented 8 KB blocks**. Scanning millions of rows to aggregate a single column forces the engine to load unnecessary columns from disk, saturating disk I/O and CPU.

* **OLAP Systems (Amazon Redshift):** Built for complex analytical aggregations, multi-table joins, and window functions across petabytes of historical data. Originally derived from a heavily re-engineered PostgreSQL fork, Redshift stores data in **column-oriented 1 MB blocks** and distributes processing across multiple servers.

### 2. The Columnar Storage Advantage

* Because values of the same data type are stored contiguously in 1 MB blocks, Redshift achieves **massive compression ratios** (often $3\times$ to $4\times$ smaller than raw row storage).

* When executing analytical queries, Redshift performs **Column Pruning**—reading strictly the column blocks referenced in your `SELECT` and `WHERE` clauses.

## 🕸️ Part 3: Distributed Systems & Redshift MPP Architecture

Mayowa demystified the word **Cluster**: *whenever you hear "cluster" in data engineering (Redshift, Apache Spark, Kafka, Kubernetes, Trino), it follows a **Master–Slave (Coordinator–Worker)** distributed architecture.*

```
                      [ BI Tools / dbt / Airflow / SQL Clients ]
                                          │
                                          ▼ (JDBC / ODBC Connection)
                 +─────────────────────────────────────────────────+
                 │                 LEADER NODE                     │
                 │  - SQL Parser & Query Optimizer                 │
                 │  - Execution Plan Generator                     │
                 │  - Result Aggregator (No User Data Stored!)     │
                 +────────────────────────┬────────────────────────+
                                          │ (High-Speed Internal Interconnect)
                    +─────────────────────┴─────────────────────+
                    ▼                                           ▼
     +─────────────────────────────+             +─────────────────────────────+
     │       COMPUTE NODE 1        │             │       COMPUTE NODE 2        │
     │  +───────────+ +───────────+│             │  +───────────+ +───────────+│
     │  │  Slice 1  │ │  Slice 2  ││             │  │  Slice 3  │ │  Slice 4  ││
     │  │ (CPU/RAM/ │ │ (CPU/RAM/ ││             │  │ (CPU/RAM/ │ │ (CPU/RAM/ ││
     │  │   Disk)   │ │   Disk)   ││             │  │   Disk)   │ │   Disk)   ││
     │  +───────────+ +───────────+│             │  +───────────+ +───────────+│
     +─────────────────────────────+             +─────────────────────────────+

```

### 1. The Leader Node (The Coordinator)

* The single point of contact for all external client connections (DBeaver, Airflow, dbt).

* **Does NOT store user table data.**

* Receives SQL queries, parses syntax, generates optimized execution plans, distributes compiled C++ code segments to Compute Nodes, and aggregates final results back to the client.

* **High Availability:** Replicated behind the scenes by AWS; if a Leader Node fails, AWS automatically fails over to a mirror node without user intervention.

### 2. Compute Nodes & Slices (The Workers)

* Compute Nodes are dedicated EC2 instances running behind the scenes that **store all table data** and execute heavy parallel computations.

* **Slices:** Each Compute Node is virtually partitioned into **Slices** based on its vCPU count. Each slice receives a dedicated allocation of CPU, memory, and disk space.

* **Massively Parallel Processing (MPP):** When a query runs, all slices across all Compute Nodes process their assigned data partitions simultaneously.

* **Heartbeats:** Compute Nodes continuously send heartbeat signals to the Leader Node. If a node stops responding, the Leader removes it and provisions a healthy replacement.

## Part 4: The Redshift Query Execution Lifecycle

When you submit a query (`SELECT customer_id, SUM(amount) FROM orders GROUP BY 1;`), it traverses four distinct stages inside the cluster:

```
[ SQL Query ] ──► 1. Parser ──► 2. Query Optimizer ──► 3. Execution Engine ──► 4. Compute Slices
                   (Checks       (Rewrites query,      (Builds physical       (Scans local disk
                    syntax)       pushes predicates)     step segments)         in parallel)

```

1. **The Parser:** Validates SQL syntax and translates plain-English SQL text into an internal logical tree representation.

2. **The Query Optimizer:** Evaluates table statistics, sort keys, and distribution styles to rewrite the query into the most efficient execution path (applying **Predicate Pushdown** and **Column Pruning**).

   * *FinOps Warning:* Poorly written queries force the Leader Node's Optimizer to burn extra CPU cycles attempting to rewrite complex subqueries.

3. **The Execution Engine:** Translates the optimized plan into sequential physical steps (segments and streams) and compiles them into machine code.

4. **Parallel Slice Execution:** Broadcasts the compiled code to every Compute Node slice. Slices read local disk blocks, filter rows, perform local aggregations, and return results to the Leader Node for final assembly.

> 🔗 **Official AWS Reference:** [Amazon Redshift Query Processing Lifecycle](https://docs.aws.amazon.com/prescriptive-guidance/latest/query-lifecycle-redshift/query-processing.html)

## Part 5: Table Performance Engineering — `SORTKEY` & `DISTSTYLE`

Mayowa recounted a pivotal career story: a production pipeline was taking **1 hour** to complete until a senior engineer joined the team, analyzed the physical layout of the Redshift tables, applied **Sort Keys** and **Distribution Styles**, and slashed runtime down to **20 minutes** without changing a single line of business logic.

### 1. Sort Keys (`SORTKEY`) — Skipping Disk Blocks via Zone Maps

* **How it works:** Defines the physical order in which rows are sorted on disk inside each 1 MB block.

* **Zone Maps:** For every 1 MB block, Redshift stores metadata tracking the **Minimum** and **Maximum** value of the Sort Key column.

* **Best Candidate Columns:** Timestamp columns (`created_at`, `updated_at`) used heavily in `WHERE` range filters and incremental loads.

```
UNSORTED TABLE (No Sort Key):
Block 1: [Min: 2025-01-01 | Max: 2025-12-31]  <-- Query: WHERE updated_at = '2025-03-09' (Must Scan!)
Block 2: [Min: 2025-02-15 | Max: 2025-11-20]  <-- Must Scan!
Block 3: [Min: 2025-03-01 | Max: 2025-08-10]  <-- Must Scan!

SORTED TABLE (SORTKEY(updated_at)):
Block 1: [Min: 2025-01-01 | Max: 2025-02-28]  <-- Skipped! (Out of range)
Block 2: [Min: 2025-03-01 | Max: 2025-03-31]  <-- SCANNED! (Target match found)
Block 3: [Min: 2025-04-01 | Max: 2025-12-31]  <-- Skipped! (Out of range)

```

### 2. Distribution Styles (`DISTSTYLE`) — Eliminating Network Shuffling

When joining two large tables (`customers` and `orders`), Redshift must match rows with identical join keys (`customer_id`). If matching rows sit on different Compute Node slices, Redshift must transfer rows across the internal network—an expensive operation called **Data Shuffling**.

```
                      [ DISTSTYLE EVEN (Round-Robin) ]
Slice 1: [ Customer: Temitope (ID: 1) ]      Slice 2: [ Order: Coca-Cola (Cust ID: 1) ]
Result: To join on ID=1, Slice 2 must SHUFFLE Coca-Cola across the network to Slice 1!

-------------------------------------------------------------------------------------------

                      [ DISTSTYLE KEY (DISTKEY(customer_id)) ]
Slice 1: [ Customer: Temitope (ID: 1) ]  +  [ Order: Coca-Cola (Cust ID: 1) ]
Slice 2: [ Customer: Habeeb (ID: 4)   ]  +  [ Order: Garlic (Cust ID: 4)    ]
Result: Co-located data! Joins happen locally on disk with ZERO network shuffling!

```

| Distribution Style | Placement Behavior | Ideal Use Case | 
| ----- | ----- | ----- | 
| **`KEY`** | Rows with identical values in the `DISTKEY` column are hashed to the exact same slice. | Large fact and dimension tables joined frequently on a shared key (e.g., `customer_id`). Eliminates shuffling! | 
| **`ALL`** | A complete copy of the entire table is duplicated onto the first slice of **every Compute Node**. | Small, slow-changing lookup/dimension tables (e.g., `countries`, `currencies`). Eliminates shuffling at the cost of extra disk storage. | 
| **`EVEN`** | Distributes rows evenly across all slices in a strict round-robin fashion. | Standalone staging tables that do not participate in joins, or tables without a clear join key. | 
| **`AUTO`** | Redshift automatically starts small tables as `ALL` and transitions them to `EVEN` or `KEY` as row counts grow. | Default recommendation when table growth patterns are unknown. | 

### Example Production DDL Syntax:

```
CREATE TABLE analytics.fact_orders (
    order_id BIGINT NOT NULL,
    customer_id INT NOT NULL,
    order_amount DECIMAL(10, 2),
    updated_at TIMESTAMP NOT NULL
)
DISTSTYLE KEY
DISTKEY (customer_id)
SORTKEY (updated_at);

```

## Part 6: Redshift Node Types — `RA3` vs. `R8g` (Graviton)

AWS deprecated legacy `DC2` nodes in favor of modern **Managed Storage** architectures that decouple compute from storage:

```
[ RA3 Node Architecture (Redshift Spectrum) ]
Leader Node ──► Launches External Spectrum Server Fleet ──► Scans S3 Data Lake
Cost: Cluster Hourly Rate + $5.00 per TB Scanned by Spectrum Fleet + S3 API Fees

[ R8g Node Architecture (AWS Graviton4 ARM) ]
Leader Node ──► Compute Nodes Query S3 Natively (Embedded Engine!)
Cost: Cluster Hourly Rate + S3 API Fees ONLY (Eliminates external Spectrum Fleet!)

```

1. **`RA3` Nodes (Redshift Analytics Gen 3):**

   * Separates compute from storage using high-speed SSD caches backed by Amazon S3.

   * Querying external S3 data lake tables via **Redshift Spectrum** requires spinning up an external fleet of Spectrum servers, incurring an additional **\$5.00 per Terabyte scanned** fee.

2. **`R8g` Nodes (AWS Graviton ARM Architecture):**

   * Powered by custom AWS Graviton processors delivering superior price-performance.

   * Features an **embedded native query engine** capable of scanning external S3 tables directly from the Compute Nodes—eliminating the external Spectrum server fleet and cutting S3 querying costs.

## Part 1: Warm-Up Quiz & Infrastructure Review
*(Facilitated by Abdulhakeem Salaudeen)*

The session opened with an interactive quiz testing core networking and EC2 compute retention from prior classes:

1. **Internet Gateway vs. NAT Gateway:**
   * **Internet Gateway (IGW):** Bi-directional doorway attached to the VPC boundary that translates private IP addresses to public IPs for public subnet instances.
   * **NAT Gateway:** Outbound-only device deployed **strictly inside a Public Subnet** that allows private subnet instances to initiate outbound connections (e.g., `pip install pandas`) while blocking any inbound access from the public internet.
2. **Diagnosing Hanging Connections:**
   * When client tools (e.g., dbt or Airbyte) hang indefinitely without an immediate error, it is a **Connection Timeout** caused by a security group or firewall dropping packets, not an authentication refusal.
3. **The Role of the Elastic Network Interface (ENI):**
   * An EC2 virtual machine does not own an IP address directly. The ENI is the virtual network card living inside the subnet that holds the private IP, associated security groups, and MAC address.
4. **EC2 Purchasing Strategy:**
   * **Spot Instances:** Best for flexible, non-critical, or fault-tolerant batch workloads that can handle 2-minute interruption warnings.
   * **Reserved Instances (RIs):** Best for 24/7 mission-critical production pipelines (like an Apache Airflow orchestrator scheduler) where downtime is unacceptable, offering up to 72% discounts over On-Demand rates.
5. **Auto Scaling Groups (ASG) Across Availability Zones:**
   * Deploying an ASG across multiple AZs (`eu-north-1a`, `eu-north-1b`, `eu-north-1c`) provides high availability. If an entire data center loses power, instances in the remaining zones automatically pick up the workload.

## Part 2: Amazon Simple Storage Service (S3) Deep-Dive

Amazon S3 is a globally accessible, horizontally scalable **object storage service**. It does not use a traditional hierarchical file system (like Linux ext4 or Windows NTFS); it stores objects in a flat namespace referenced by bucket names and keys.

```
+-------------------------------------------------------------------------+
| S3 Bucket: cdebytes-customers (Flat Namespace)                          |
|                                                                         |
|  Key (Virtual Folder Path)               Object (Payload & Metadata)    |
|  -------------------------------------   ----------------------------   |
|  raw/customers/2026-11-07/data.parquet   [ 10.4 MB Parquet Payload ]   |
|  raw/customers/2026-11-07/schema.json    [ 2.1 KB JSON Schema ]        |
|  images/profile_pics/avatar.png          [ 450 KB PNG Payload ]        |
+-------------------------------------------------------------------------+
```

### 1. Fundamental Terminology:
* **Objects:** Files and their associated metadata. S3 accepts any format: `.parquet`, `.csv`, `.json`, `.avro`, images, and raw binary streams.
* **Buckets:** The root containers holding objects. Bucket names must be **globally unique across all AWS accounts worldwide**.
* **Keys:** The full path string identifying an object (e.g., `customers/year=2026/month=11/data.parquet`). S3 creates the visual illusion of folders using forward slashes (`/`).
* **Storage Limit:** Individual objects can range from $0$ bytes up to **$5$ Terabytes**. A single bucket can hold unlimited total data.

### 2. S3 as the Modern Data Lake:
In enterprise architecture, S3 acts as the foundational raw storage sink (Data Lake) because:
* It decouples storage from compute (you pay for stored gigabytes separately from the engines querying them).
* It provides $99.999999999\%$ ($11$ 9s) of data durability by automatically replicating objects across a minimum of three distinct physical Availability Zones.

## Part 3: S3 Storage Classes & FinOps Tiering

AWS offers multiple storage classes tailored to object access frequency. Misunderstanding these tiers is one of the fastest ways to overspend on cloud storage.

```
       Access Frequency / Cost per GB
       ▲
  High │  [ S3 Standard ]         - Fast access, high storage cost ($0.023/GB)
       │  [ S3 Intelligent-Tiering ] - Auto-moves data based on access patterns
       │  [ S3 Standard-IA ]      - Lower storage cost, retrieval fees apply
       │  [ S3 Glacier Flexible ] - Archival, 1 min to 12 hours retrieval
   Low │  [ S3 Glacier Deep Archive ] - Lowest cost ($0.00099/GB), up to 12h retrieval
       └─────────────────────────────────────────────────────────────►
          Retrieval Latency (Milliseconds to Hours)
```

| Storage Class | Designed For | Retrieval Latency | Storage Cost (approx./GB/mo) | Retrieval Fee? |
| :--- | :--- | :--- | :--- | :--- |
| **S3 Standard** | Frequently accessed active data | Milliseconds | \~$0.023 | None |
| **S3 Intelligent-Tiering** | Unpredictable or shifting access patterns | Milliseconds | \~$0.023 (auto-drops) + monitoring fee | None |
| **S3 Standard-IA (Infrequent Access)** | Data accessed once or twice a month | Milliseconds | \~$0.0125 | Yes (per GB retrieved) |
| **S3 Glacier Instant Retrieval** | Archive data accessed once a quarter | Milliseconds | \~$0.004 | Yes |
| **S3 Glacier Flexible Retrieval** | Backup data accessed 1–2 times a year | 1 minute to 12 hours | \~$0.0036 | Yes |
| **S3 Glacier Deep Archive** | Long-term compliance retention (7–10 years) | **Up to 12 Hours** | **\~$0.00099** (cheapest) | Yes (highest per GB) |

### The "Deep Archive" Trade-Off:
* If compliance mandates retaining raw transactional logs for 7 years, **Glacier Deep Archive** is unbeatable (\~\$1 per terabyte/month).
* *The Catch:* If an emergency audit demands files immediately, Deep Archive **cannot return data on the spot**. You must initiate a restore request and wait up to $12$ hours for the payload to be staged back into S3 Standard.

## Part 4: Lifecycle Rules & The "Small File" Cost Trap

### 1. Automated Lifecycle Management
Instead of writing custom cron scripts to delete or move old files, S3 **Lifecycle Rules** automate data tiering:
* **Transition Actions:** Automatically demote objects (e.g., move from `S3 Standard` to `S3 Standard-IA` after 30 days, then to `Glacier Deep Archive` after 90 days).
* **Expiration Actions:** Permanently delete objects after a retention deadline (e.g., purge staging temporary files after 7 days).

### 2. The Small File Transition Trap (Crucial FinOps Concept!)
Mayowa highlighted a costly pitfall for data engineers writing thousands of micro-files:
* AWS assesses an administrative **Transition Request Fee** (per 1,000 requests) every time an object is moved to an archival class.
* If a pipeline writes millions of tiny **2 KB files** and transitions them to Glacier:
  * The transition request fees will cost significantly more than the storage savings gained!
* **The Rule of Thumb:** Consolidate data into compact, columnar files (**128 MB to 512 MB Parquet files**) before applying lifecycle transitions.

> 🔗 **Official AWS Reference:** [Amazon S3 Pricing & Lifecycle Request Costs](https://aws.amazon.com/s3/pricing/)

## Part 5: Bucket Versioning & Delete Markers

Human error and automated pipeline overwrites are inevitable. **S3 Bucket Versioning** provides complete protection against data loss.

```
Scenario A: Versioning Disabled
[ File: customer.csv ] ---> Click "Delete" ---> Result: PERMANENTLY LOST (No Recovery)

Scenario B: Versioning Enabled
[ File: customer.csv (Version ID: 1111) ] ---> Click "Delete"
                                                     |
                                                     v
[ Top of Stack: DELETE MARKER (Version ID: 2222) ] <--- Masks underlying object!
[ Hidden Stack: customer.csv  (Version ID: 1111) ] <--- Data is safe and intact!
                                                     |
                                (Delete the Delete Marker)
                                                     v
[ File: customer.csv (Version ID: 1111) ] <--- Object Instantly Restored!
```

### How Versioning Works:
1. **Disabled by Default:** On a new bucket, deleting a file completely purges the object payload from disk.
2. **Enabled Mode:**
   * Every upload of a file with an identical key assigns a new unique **Version ID** rather than overwriting the prior version.
   * Issuing a standard `Delete` operation **does not delete the object**. S3 inserts a zero-byte **Delete Marker** at the top of the version stack.
   * Normal API calls (like `s3:GetObject`) receive a `404 Not Found` response because the Delete Marker is current.
3. **Restoring the File:** By toggling **Show versions**, selecting the **Delete Marker**, and permanently deleting *only the marker*, the original file version resurfaces at the top of the stack and is restored instantly.

## Part 6: The Modern Decoupled Data Platform Architecture

Mayowa walked through the standard architectural pattern used at top-tier companies to protect operational databases and data warehouses from being brought down by analytics and machine learning:

```
[ Transactional Sources ]
(PostgreSQL / MySQL / ERP)
           |
           | Ingestion Pipeline (Airbyte / Flink / Python)
           v
+-----------------------------------------------------------------------------------+
| Raw Data Lake: Amazon S3 (Bucket: cdebytes-customer-data-lake)                   |
| - Format: Apache Parquet (Partitioned by date/region)                             |
| - Secured by IAM Policies & Encrypted at rest                                     |
+-----------------------------------------+-----------------------------------------+
                                          |
                      +-------------------+-------------------+
                      |                                       |
                      v                                       v
+-----------------------------------------+   +-------------------------------------+
| AWS Glue Data Catalog                   |   | ETL / ELT Transformation Pipeline   |
| (Database: all_customers, Table: orders)|   | (dbt / Apache Spark / Airflow)      |
+---------------------+-------------------+   +------------------+------------------+
                      |                                          |
                      v                                          v
+-----------------------------------------+   +-------------------------------------+
| Query Engine: Amazon Athena (Serverless)|   | Cloud Data Warehouse                |
| - Standard ANSI SQL over S3 Files       |   | (Amazon Redshift / Snowflake)       |
+---------------------+-------------------+   +------------------+------------------+
                      |                                          |
                      v                                          v
        [ Data Science & ML Teams ]                 [ BI Reporting & Executive Dashboards ]
        (Jupyter, SageMaker, Ad-Hoc Analytics)      (Tableau, PowerBI, Metric Layers)
```

### Why Decouple the Warehouse from the Data Lake?
1. **The Warehouse CPU Crisis:**
   * Data warehouses (like Amazon Redshift or Snowflake) rely on dedicated compute clusters running continuously.
   * If Data Scientists, Machine Learning engineers, ad-hoc analysts, and scheduled BI dashboards all hammer the warehouse concurrently, **CPU utilization spikes to 100%**.
   * Dashboards freeze, executive reporting delays occur, and data warehouse scaling costs balloon.
2. **The Serverless Offload Solution:**
   * Write raw and cleaned data into **Amazon S3** in open formats (Apache Parquet).
   * Catalog the schema using the **AWS Glue Data Catalog**.
   * Direct Data Science and exploration workloads to **Amazon Athena**.
   * Athena runs queries using a serverless execution fleet, scanning S3 directly with zero impact on the Redshift cluster's CPUs.

## Part 7: AWS Glue Data Catalog & Amazon Athena

### 1. What is the AWS Glue Data Catalog?
* It is a centralized, Apache Hive-compatible **metadata repository**.
* It **does not store actual data rows**. It stores schema definitions, column data types (`STRING`, `BIGINT`, `DOUBLE`), file formats (`PARQUET`), and the underlying S3 URI location (`s3://cdebytes-customer-data-lake/customers/`).
* Think of the Glue Catalog as a table of contents, while S3 is the actual book.

### 2. What is Amazon Athena?
* An interactive, serverless **query engine** based on open-source Presto/Trino.
* Requires **zero server management** or compute cluster provisioning.
* Translates standard ANSI SQL queries into distributed scan operations across S3 files using the schema mapped by the Glue Data Catalog.

### 3. Athena FinOps Sizing ($5 / Terabyte Scanned):
* **Pricing Model:** Athena charges **$5.00 per Terabyte of data scanned** by your SQL queries.
* **The Parquet Advantage:**
  * If a query runs against a 10 GB uncompressed CSV file to calculate a single column average, Athena must scan all 10 GB (costing $0.05).
  * If that data is converted to **compressed Apache Parquet**, the file size shrinks to \~1.5 GB, and because Parquet is **columnar**, Athena scans *only* the specific column requested (e.g., 80 MB).
  * The query cost drops by over **99%**, executing significantly faster.

## Part 8: Cloud FinOps — S3 VPC Gateway Endpoints vs. Internet Egress

Mayowa revealed an architectural detail that costs companies thousands in unnecessary network fees:

```
UNOPTIMIZED (Default Path):
[ EC2 Private Subnet ] ---> [ NAT Gateway ] ---> [ IGW ] ---> [ Public Internet ] ---> [ Amazon S3 ]
Cost: $0.045/hour (NAT) + $0.045/GB (NAT data) + $0.09/GB (Internet egress) = ~$0.135 / GB!

OPTIMIZED (VPC Gateway Endpoint):
[ EC2 Private Subnet ] =================== [ S3 VPC Gateway Endpoint ] ===================> [ Amazon S3 ]
Cost: 100% FREE ($0.00 / GB) - Traffic never leaves the private AWS backbone!
```

* **The Problem:** Amazon S3 is a public cloud service. It does not live natively inside your private VPC subnets. By default, traffic from an EC2 instance to S3 routes through an Internet Gateway or NAT Gateway, incurring **$0.09/GB egress and $0.045/GB NAT processing fees**.
* **The Solution:** Provision an **S3 VPC Gateway Endpoint**. It updates your subnet route tables with a direct private route to S3 across the internal AWS network bus.
* **The Cost:** **100% Free.** Zero hourly fee, zero per-gigabyte data transfer fee.

> 🔗 **Official AWS Reference:** [AWS Gateway Endpoints for Amazon S3](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-s3.html)

### Demo 1: S3 Bucket Versioning & Delete Marker Recovery

#### Objective
Create a version-enabled S3 bucket, upload a test file, demonstrate that deleting the file without versioning permanently destroys it, enable versioning, simulate an accidental deletion, inspect the hidden **Delete Marker**, and restore the original file.

```
+-------------------------------------------------------------------------+
| Demo 1 Flow: The Recovery of an "Accidentally Deleted" S3 Object        |
+-------------------------------------------------------------------------+
| 1. Upload File (cde_logo.png)                                           |
| 2. Issue Standard Delete -> File disappears from active UI view         |
| 3. Toggle [Show versions] -> Delete Marker revealed at top of stack     |
| 4. Delete the Delete Marker -> Original file resurfaces intact!         |
+-------------------------------------------------------------------------+
```

#### Step-by-Step Instructions

##### Step 1: Create a Bucket Without Versioning
1. Open the **Amazon S3 Console** $\rightarrow$ Click **Create bucket**.
2. **Bucket name:** `cdebytes-versioning-lab-xxxx` *(must be globally unique; use your initials/date)*.
3. **Region:** `eu-central-1` (Frankfurt) or `eu-north-1` (Stockholm).
4. Under **Bucket Versioning**, select **Disable**.
5. Click **Create bucket**.

##### Step 2: Test Permanent Deletion (The Dangerous Default)
1. Click into your new bucket. Click **Upload** $\rightarrow$ **Add files**.
2. Select any image or text file from your computer (e.g., `test_document.txt`). Click **Upload**.
3. Select `test_document.txt` from the bucket list $\rightarrow$ Click **Delete**.
4. Type `permanently delete` into the confirmation box $\rightarrow$ Click **Delete objects**.
5. *Result:* The file is completely purged from AWS. It cannot be recovered.

##### Step 3: Enable Bucket Versioning
1. Inside the bucket, navigate to the **Properties** tab.
2. Under **Bucket Versioning**, click **Edit**.
3. Select **Enable** $\rightarrow$ Click **Save changes**.

##### Step 4: Upload and Trigger Accidental Deletion
1. Return to the **Objects** tab.
2. Upload `test_document.txt` again.
3. Select `test_document.txt` $\rightarrow$ Click **Delete**.
4. Notice the confirmation box prompt changes: it now asks you to type `delete` (instead of `permanently delete`).
5. Type `delete` $\rightarrow$ Click **Delete objects**.
6. *Observation:* In the default Objects view, the bucket appears empty!

##### Step 5: Reveal and Delete the Delete Marker
1. At the top right of the object table, slide the **Show versions** toggle to the **ON** position.
2. Two rows appear for `test_document.txt`:
   * **Row 1 (Top):** Type is **Delete marker** (Size: 0 B, Version ID: `3kL...`).
   * **Row 2 (Bottom):** Original file payload (Size: e.g., 2.4 KB, Version ID: `9vB...`).
3. Check the box next to the **Delete marker** row only.
4. Click **Delete** $\rightarrow$ Type `permanently delete` $\rightarrow$ Confirm.
5. Turn the **Show versions** toggle back to **OFF**.
6. **Result:** `test_document.txt` is restored to the active bucket directory.

##### Step 4: Author the Ingestion & Cataloging Script
Create a new file named `ingest_and_catalog.py` and add the following code:

```python
import pandas as pd
import boto3
import awswrangler as wr

# 1. Define Dummy Transactional Data
data = {
    "customer_id": [101, 102, 103, 104, 105],
    "first_name": ["Mayowa", "Judith", "Osas", "Temitope", "Dennis"],
    "country": ["Germany", "Nigeria", "Nigeria", "United Kingdom", "United States"],
    "signup_date": ["2026-01-15", "2026-03-22", "2026-05-10", "2026-08-01", "2026-11-07"],
    "total_spend": [1250.50, 430.00, 2890.75, 150.20, 3100.00]
}

df = pd.DataFrame(data)
df["signup_date"] = pd.to_datetime(df["signup_date"])

# 2. Configuration Parameters
BUCKET_NAME = "cdebytes-analytics-datalake-xxxx"  # Replace with your actual S3 bucket name
GLUE_DATABASE = "all_customers"
GLUE_TABLE = "customers"
S3_PATH = f"s3://{BUCKET_NAME}/raw/customers/"

# 3. Create AWS Session
# Note: In production on EC2, omit keys and let the IAM Instance Profile authenticate!
session = boto3.Session(
    region_name="eu-central-1"
)

print("Starting ingestion: Converting DataFrame to Parquet & Writing to S3...")

# 4. Write Parquet to S3 AND Register in Glue Catalog Simultaneously
response = wr.s3.to_parquet(
    df=df,
    path=S3_PATH,
    dataset=True,
    database=GLUE_DATABASE,
    table=GLUE_TABLE,
    mode="overwrite",
    boto3_session=session
)

print("Success! Data written and cataloged.")
print(f"S3 Files Created: {response['paths']}")
```

##### Step 5: Execute the Ingestion Script
Run the script from your terminal:
```bash
python ingest_and_catalog.py
```

   * Click **Save**.
3. **Run ANSI SQL Queries:**

   * The `customers` table appears in the table list.

## 2. Real-World Git Architecture: Staging, Main & Production Safety

### 2.1 The Kitchen Recipe Analogy
In a high-end restaurant, chefs do not invent dishes randomly during service; they strictly follow standardized recipes. In software and data engineering:
- **`main` / `master` Branch:** The single source of truth powering live client websites, ETL pipelines, and production analytics databases.
- **`staging` / `develop` Branch:** An integration layer where features are assembled, tested, and validated prior to scheduled production deployments.
- **Feature Branches (`feat/...`, `test_env`, etc.):** Isolated scratchpads where engineers build isolated updates without disrupting coworkers.

```text
[ Remote Repository (GitHub / GitLab) ]
  ├── main (PROTECTED - Powers Production / Live Site)
  │     ▲
  │     │ Scheduled Release / Admin Gatekeeper
  ├── staging (PROTECTED - Integration / Testing)
        ▲
        │ Pull Request (Requires 2 Approvals + Automated Checks)
  ┌─────┴────────────────────────────────┐
  │ Feature Branch: feat/customer_table  │
  └──────────────────────────────────────┘
        ▲
        │ git push origin feat/customer_table
[ Local Machine / VS Code ]
  └── Local Workspace -> Staging Area (`git add`) -> Local Repo (`git commit`)
```

### 2.2 Why Direct Pushes Cause Outages
Direct pushes bypass code reviews and CI checks, frequently resulting in catastrophic production failures—such as broken schemas, data wipeouts, or 404 errors. Gatekept workflows ensure that every change is reviewed, tested, and vetted before reaching deployment branches.

## 3. The Essential Git Workflow: The Core 6 Commands

Ahmed emphasized that junior engineers need mastery over six foundational commands before attempting advanced maneuvers like rebasing or cherry-picking:

```text
1. git clone <url>          ──▶  Download repository to local machine (run once)
2. cd <repo_folder>         ──▶  Navigate inside the Git environment
3. git pull origin <base>   ──▶  Sync local base branch with remote changes
4. git checkout -b <branch> ──▶  Create and switch to a dedicated feature branch
5. git add <file>           ──▶  Stage tracked modifications
6. git commit -m "message"  ──▶  Commit snapshot locally
7. git push origin <branch> ──▶  Push branch to remote and generate PR URL
```

### 3.1 Step-by-Step Command Breakdown

| Step | Command | Purpose & Practical Warning |
| :--- | :--- | :--- |
| **0. Clone** | `git clone https://github.com/...` | Clones remote repository locally. *Crucial:* You must `cd` into the cloned folder before running any Git commands, otherwise Git returns `fatal: not a git repository`. |
| **1. Sync Base** | `git pull origin main` | Refreshes the local base branch with all remote updates before branching off. |
| **2. Branch Off** | `git checkout -b <branch_name>`<br>*(or `git switch -c <name>`)* | Creates an isolated branch mirroring the latest synced state. |
| **3. Stage** | `git add <filename>` | Moves modified files into the staging area. *Avoid blind `git add .` unless intentionally staging everything.* |
| **4. Check State**| `git status` | Verifies untracked vs. staged files. Red indicates unstaged; green indicates staged. |
| **5. Commit** | `git commit -m "Descriptive summary"` | Records changes to the local repository history. |
| **6. Push** | `git push --set-upstream origin <branch>` | Pushes branch to GitHub and establishes remote tracking. |

## 4. Avoiding Merge Conflicts & "Commits Behind" Desynchronization

### 4.1 The Divergence Problem
A common pitfall occurs when an engineer creates a local branch without pulling the latest remote changes first, or when teammates merge their PRs while the engineer is still working:
```
Remote main:    ---●---●---● (Teammates Dennis & Charles merged their PRs)
                    \
Local feature:       ●---● (Created from an outdated commit — 2 commits behind!)
```

When creating a PR, GitHub will flag:  
`"This branch is 1 commit ahead and 2 commits behind main."`

### 4.2 Standard Recovery Procedure
To resolve desynchronization cleanly before opening or merging a PR:
1. Commit all ongoing work on the local feature branch.
2. Switch back to the local base branch: `git checkout main` (or `staging`).
3. Pull all upstream changes: `git pull origin main`.
4. Switch back to your feature branch: `git checkout <feature-branch>`.
5. Merge the updated base into your feature branch: `git merge main`.
6. Resolve any conflicting lines locally, commit the resolution, and push the clean state: `git push origin <feature-branch>`.

## 5. Protected Pull Requests (PRs) & Enterprise Code Review

### 5.1 Branch Protection Rules
In production repositories, branches like `staging` and `main` enforce strict protection settings:
- **Direct Pushes Blocked:** Developers cannot run `git push origin main`.
- **Mandatory Reviewers:** Requires approval from at least 1–2 designated team members.
- **Status Checks:** Automated CI tests (e.g., SQL linter, formatting checks) must pass before the "Merge" button unlocks.

### 5.2 Anatomy of a Professional Pull Request
Opening a PR with empty descriptions or vague summaries (e.g., *"testing"*) is strictly bad practice. High-standard teams enforce PR templates containing:
- **Summary of Changes:** Clear explanation of what was built or refactored.
- **Related Issue Link:** Explicitly tying the PR to a ticket (e.g., `Closes #13`).
- **Testing & Verification:** Evidence/logs proving the code was validated locally.
- **Draft PR State:** Flagging unfinished PRs as **Draft** prevents reviewers from merging incomplete code prematurely.

## 6. GitHub Issues & Agile Ticket Management

### 6.1 Standardizing Requirements (Jira vs. GitHub Issues)
Modern engineering teams use issue trackers to log requirements, bugs, and data requests rather than relying on informal chat messages.

```text
[ Request / Bug Identified ]
         │
         ▼
[ Structured Issue Created via Template ]
  ├── Description & Business Justification
  ├── Schema / SQL / Data Requirements
  ├── Reproduction Steps & Error Screenshots
  └── Definition of Done (Acceptance Criteria)
         │
         ▼
[ Sprint Triage / Standup Meeting ]
  ├── Assignee Assigned (e.g., Data Engineer)
  └── Labels Attached (bug, enhancement, sql-task)
         │
         ▼
[ Feature Branch Created -> PR Opened -> Closes #Issue upon Merge ]
```

### 6.2 Internal vs. External Cross-Department Requests
- **Internal Data Team Requests:** Can be assigned immediately to a specific data engineer by the team lead.
- **External Department Requests (Marketing, Sales, Product):** Submitted without an assignee, then triaged during sprint planning/daily standups based on engineer bandwidth and domain expertise.

### 6.3 Automated Issue Lifecycle
By referencing the issue identifier within the Pull Request description (e.g., `Closes #13` or `Fixes #24`), GitHub automatically closes the corresponding issue once the PR is approved and merged into the base branch.

## 7. Common Student Errors & Practical Troubleshooting

| Observed Issue | Root Cause | Fix / Resolution |
| :--- | :--- | :--- |
| `fatal: not a git repository` | Command executed in the parent directory outside the cloned repo. | `cd` into the downloaded project directory containing the `.git` folder. |
| `fatal: No configured push destination` | Running plain `git push` on a new local branch without setting upstream. | Run `git push --set-upstream origin <branch_name>`. |
| `fatal: Authentication failed (403/Password)` | GitHub deprecated raw password authentication for HTTPS operations. | Configure SSH keys (`ssh-keygen`) or generate a GitHub Personal Access Token (PAT). |
| `Merging is blocked` | Target branch is protected and missing required approvals/CI checks. | Request peer reviews from assigned colleagues and ensure all automated status checks pass. |

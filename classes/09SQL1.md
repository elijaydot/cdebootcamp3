## 2. Data Classification Spectrum

| Data Category | Core Characteristics | Concrete Examples | Storage / Query Paradigm |
| :--- | :--- | :--- | :--- |
| **Structured Data** | Rigid schema, fixed data types, strictly organized into tabular rows and columns. | RDBMS (PostgreSQL, SQL Server), CSV files, Parquet tables. | Relational Databases, SQL (`SELECT`, `JOIN`). |
| **Semi-Structured Data** | Contains internal tags, markers, or hierarchical key-value pairs without a rigid tabular schema. | JSON documents, XML, HTML files. | Document stores (MongoDB), NoSQL, JSON column parsers. |
| **Unstructured Data** | Lacks predefined conceptual model or structural schema; native binary format. | Audio files, raw text documents, images, video feeds. | Object Storage (AWS S3, Azure Blob, Google Cloud Storage). |

## 3. Storage System Hierarchy: File Storage to Data Lakes

1. **File Storage / Flat Files:** Local operating system directories holding standalone documents (`.csv`, `.xlsx`). Good for ad-hoc sharing; unusable for multi-user concurrency or referential integrity.
2. **Relational Database (RDBMS / OLTP):** Stores structured rows and columns, strictly enforces data types and constraints, handles millions of rows, and supports concurrent ACID transactions.
3. **Data Warehouse (DWH / OLAP):** "A database on steroids"—acts as a consolidated central repository aggregating historical data across multiple operational systems and flat files, optimized for high-performance aggregate analytics.
4. **Data Lake:** Massive central storage layer capable of dumping unlimited structured, semi-structured, and unstructured data at scale (e.g., Amazon S3 buckets, Azure Data Lake Storage).

## 5. Case Study Architecture: Parch & Posey Schema

The class utilized the simulated **Parch & Posey** paper sales business across 4 US regions with 50 sales representatives.

```
 [ Region ] (1) 
     │
     └──< (N) [ Sales Reps ] (1)
                  │
                  └──< (N) [ Accounts ] (1) ───< (N) [ Web Events ]
                               │
                               └──< (N) [ Orders ]
```

* **`region`**: Primary key (`id`) and region name (`name`).
* **`sales_reps`**: Primary key (`id`), `name`, and foreign key (`region_id` → `region.id`).
* **`accounts`**: Primary key (`id`), `name`, `website`, `lat`, `long`, `primary_poc`, and foreign key (`sales_rep_id` → `sales_reps.id`).
* **`orders`**: Primary key (`id`), foreign key (`account_id` → `accounts.id`), quantities (`standard_qty`, `gloss_qty`, `poster_qty`), and financial decimals (`total_amt_usd`, etc.).
* **`web_events`**: Primary key (`id`), foreign key (`account_id` → `accounts.id`), `occurred_at`, and `channel` (direct, Facebook, organic, etc.).

### Referential Constraints and Table Creation Sequence

A table containing a foreign key cannot be created before the parent table containing the referenced primary key exists. Dimension or lookup tables must therefore be created before fact or transaction tables.

```text
[ region ]  (Primary key table; create first)
    └── [ sales_reps ]  (references region_id; create second)
          └── [ accounts ]  (references sales_rep_id; create third)
                ├── [ orders ]      (references account_id)
                └── [ web_events ]  (references account_id)
```

The required creation order is `region` → `sales_reps` → `accounts` → `orders` and `web_events`.

### Why Normalize?

Storing `region_name` as text in every order or sales representative row consumes extra storage and creates update anomalies. Moving the region into its own table and referencing it with an integer `region_id` saves space, reduces repetition, and enforces consistency.

## 6. SQL Server Environment Setup and Schema Grouping

### Local Connection and Cross-Platform Options
* **Connection String:** In SSMS, use `.` (period) or `localhost` with **Windows Authentication** (or `system_name\SQLEXPRESS`). Ensure "Trust Server Certificate" is checked if prompted.
* **Mac/Linux Options:** While SSMS is native to Windows, Mac/Linux users can run SQL Server in Docker containers or connect using **DBeaver** or **Azure Data Studio**.

### Schema Management: Logical Grouping and Security

Schemas act as logical containers inside a database. They can partition tables by department, domain, or permission tier:
```sql
-- Create a custom schema
CREATE SCHEMA demo;
GO

-- Create a table inside the schema
CREATE TABLE demo.region (
    id INT NOT NULL,
    name VARCHAR(50) NOT NULL,
    CONSTRAINT pk_demo_region PRIMARY KEY (id)
);
```
This simplifies granular Role-Based Access Control (RBAC): a user can receive access to `demo.*` without gaining access to `dbo.*` tables.

## 7. DDL: Defining and Modifying Database Structures

Data Definition Language operates on database objects, metadata, and table structures rather than individual row contents. Its commands include `CREATE`, `ALTER`, `DROP`, and `TRUNCATE`.

### Creating Tables with Constraints
```sql
CREATE TABLE dbo.orders (
    id INT NOT NULL,
    account_id INT NOT NULL,
    occurred_at DATETIME NOT NULL,
    standard_qty INT NOT NULL,
    gloss_qty INT NOT NULL,
    poster_qty INT NOT NULL,
    total INT NOT NULL,
    standard_amt_usd DECIMAL(18, 2) NOT NULL,
    gloss_amt_usd DECIMAL(18, 2) NOT NULL,
    poster_amt_usd DECIMAL(18, 2) NOT NULL,
    total_amt_usd DECIMAL(18, 2) NOT NULL,
    CONSTRAINT pk_orders PRIMARY KEY (id),
    CONSTRAINT fk_orders_accounts FOREIGN KEY (account_id) REFERENCES dbo.accounts(id)
);
```

### Adding a Column

```sql
ALTER TABLE dbo.accounts
ADD customer_type VARCHAR(50) NULL;
```

### Modifying a Column's Type or Capacity

The class demonstrated expanding the column from its original 50-character capacity. Depending on the required business limit, it can be changed to 100 or 200 characters:

```sql
ALTER TABLE dbo.accounts
ALTER COLUMN customer_type VARCHAR(100) NULL;

ALTER TABLE dbo.accounts
ALTER COLUMN customer_type VARCHAR(200) NULL;
```

### Renaming a Column

Unlike PostgreSQL, which uses `ALTER TABLE ... RENAME COLUMN ...`, SQL Server uses the built-in `sp_rename` system stored procedure:

```sql
EXEC sp_rename 'dbo.accounts.customer_type', 'account_type', 'COLUMN';
```

### Dropping Columns and Objects

```sql
ALTER TABLE dbo.accounts
DROP COLUMN account_type;

DROP TABLE IF EXISTS dbo.demo_region;
```

## 8. DML: Working with Table Data

Data Manipulation Language changes the rows stored inside tables. Its principal commands are `INSERT`, `UPDATE`, `DELETE`, and `MERGE`.

### Inserting Data

The session inserted a standalone Tesla account as a practical example:

```sql
INSERT INTO dbo.accounts (id, name, website, lat, long, primary_poc, sales_rep_id)
VALUES (
    5001, 
    'Tesla Motors', 
    'www.tesla.com', 
    37.7749, 
    -122.4194, 
    'Elon Musk', 
    321500
);
```

Two additional records illustrated the difference between temporary test data and data intended to become permanent:

```sql
INSERT INTO dbo.accounts (id, name, website, lat, long, primary_poc, sales_rep_id)
VALUES (9999, 'Temporary Test Co', 'www.testco.com', 40.7128, -74.0060, 'Jane Doe', 321500);

INSERT INTO dbo.accounts (id, name, website, lat, long, primary_poc, sales_rep_id)
VALUES (9999, 'Permanent Client Co', 'www.permanent.com', 40.7128, -74.0060, 'Jane Doe', 321500);
```

These statements reuse ID `9999` because they belong to separate transaction demonstrations, not one continuous insert sequence.

### Updating Records with Targeted Filtering

Always qualify an `UPDATE` with a targeted `WHERE` clause. Without one, SQL Server applies the change to every row in the table. The class used two variations for account ID `1001`:

```sql
UPDATE dbo.accounts
SET website = 'www.walmartstores.com',
    primary_poc = 'Jane Doe'
WHERE id = 1001;

UPDATE dbo.accounts
SET website = 'www.walmartcareers.com',
    primary_poc = 'Sarah Jenkins'
WHERE id = 1001;
```

> **Safety rule:** Before running an `UPDATE` or `DELETE`, first use the same `WHERE` clause in a `SELECT` statement to confirm the exact rows being targeted.

## 9. Transaction Safety: `BEGIN TRANSACTION`, `COMMIT`, and `ROLLBACK`

Transactions support ACID guarantees by treating a batch of queries as an indivisible unit of work. Changes should be enclosed in explicit transaction blocks when testing inserts, updates, or deletes, especially in production-like environments. A correct result can be made permanent with `COMMIT`; a mistake or test can be undone with `ROLLBACK`.

```
       +------------------------------------+
       |         BEGIN TRANSACTION          |
       +------------------------------------+
                         │
                         ▼
       +------------------------------------+
       |  Execute DML (INSERT/UPDATE/DELETE)|
       +------------------------------------+
                         │
         ┌───────────────┴───────────────┐
         ▼                               ▼
 [ Satisfied / Correct ]     [ Error / Testing State ]
         │                               │
         ▼                               ▼
+-----------------+             +------------------+
|     COMMIT      |             |     ROLLBACK     |
| (Saved to Disk) |             | (Changes Undone) |
+-----------------+             +------------------+
```

### Safe Insert Testing with `ROLLBACK`

```sql
BEGIN TRANSACTION;

INSERT INTO dbo.accounts (id, name, website, lat, long, primary_poc, sales_rep_id)
VALUES (9999, 'Temporary Test Co', 'www.testco.com', 40.7128, -74.0060, 'Jane Doe', 321500);

-- Verify the row while the transaction is still active
SELECT * FROM dbo.accounts WHERE id = 9999;

-- Restore the table to its previous state
ROLLBACK TRANSACTION;
```

### Making an Insert Permanent with `COMMIT`

```sql
BEGIN TRANSACTION;

INSERT INTO dbo.accounts (id, name, website, lat, long, primary_poc, sales_rep_id)
VALUES (9999, 'Permanent Client Co', 'www.permanent.com', 40.7128, -74.0060, 'Jane Doe', 321500);

COMMIT TRANSACTION;
```

### Testing a Delete Safely

```sql
BEGIN TRANSACTION;

DELETE FROM dbo.accounts WHERE name = 'Tesla Motors';

-- Verify whether the state matches expectations
SELECT * FROM dbo.accounts WHERE name = 'Tesla Motors';

-- Undo the test with zero permanent data loss
ROLLBACK TRANSACTION;
```

## 10. Referential Integrity and Foreign Key Deletion Barriers

SQL Server protects relationships between parent and child tables. A parent row cannot be deleted while child rows still reference its primary key.

```text
[ accounts ] (Parent row: Apple, id = 1002)
     ▲
     │  Foreign key barrier: the referenced parent cannot be deleted
     │
[ orders ]   (Child rows: 10+ orders placed by Apple)
```

### Why Deleting Apple Fails but Deleting Tesla Can Succeed

* **Apple:** If account ID `1002` has existing rows in `dbo.orders` or `dbo.web_events`, `DELETE FROM dbo.accounts WHERE id = 1002;` raises a foreign key constraint violation. The equivalent name-based attempt, `DELETE FROM dbo.accounts WHERE name = 'Apple';`, fails for the same reason.
* **Tesla:** A newly inserted account with no referencing child rows can be deleted without violating a relationship.

### Manual Child-First Deletion

One resolution is to remove all referencing child rows before deleting the parent:

```sql
BEGIN TRANSACTION;

DELETE FROM dbo.web_events WHERE account_id = 1002;
DELETE FROM dbo.orders WHERE account_id = 1002;
DELETE FROM dbo.accounts WHERE id = 1002;

COMMIT TRANSACTION;
```

### Cascading Deletes and Updates

The alternative is to define cascading behavior on the foreign key. This automates parent-child cleanup, so it should be researched and selected deliberately:

```sql
ALTER TABLE dbo.orders
ADD CONSTRAINT FK_Orders_Accounts
FOREIGN KEY (account_id) REFERENCES dbo.accounts(id)
ON DELETE CASCADE
ON UPDATE CASCADE;
```

## 11. Critical Distinctions: `DELETE` vs. `TRUNCATE`

| Operational Dimension | `DELETE` Statement | `TRUNCATE` Statement |
| :--- | :--- | :--- |
| **Command Classification** | DML (Data Manipulation Language) | DDL (Data Definition Language) |
| **Row Filtering** | Supports `WHERE` clause to delete specific rows. | No `WHERE` clause; clears entire table at once. |
| **Logging and Execution** | Scans rows and logs each deletion individually, making it slower on large datasets. | Deallocates data pages with minimal transaction logging, making it near-instantaneous regardless of table volume. |
| **Identity Counter** | Retains existing auto-increment identity seed. | Resets table identity counter back to seed value. |
| **Foreign Key Constraints** | Can delete rows if no active foreign key references exist. | Is blocked if the table is referenced by any foreign key constraint, even if the referencing table is empty. |

## 12. Student Q&A and Troubleshooting
### Is `GO` required after every SQL Server query?

No. `GO` is a client batch separator recognized by SSMS and related tools; it is not standard SQL. Statements terminated with semicolons can execute sequentially, while `GO` explicitly separates execution batches.

### Can PostgreSQL be used instead of Microsoft SQL Server?

Yes. Core ANSI SQL statements such as `SELECT`, `INSERT`, `UPDATE`, and standard DDL are very similar across engines. Differences appear in procedural dialects such as T-SQL versus PL/pgSQL and in administrative syntax such as SQL Server's `sp_rename` versus PostgreSQL's `ALTER TABLE ... RENAME`.

### What does `DECIMAL(18, 2)` mean?

It defines a precision of 18 total digits and a scale of 2 digits after the decimal point. This is suitable for financial values because it avoids floating-point rounding errors in currency calculations.

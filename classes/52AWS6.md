## Part 1: Quick-Fire Architectural Recap (Packet Journey to an EC2 Instance)

Mayowa opened with an end-to-end recap tracing the exact path an inbound packet takes from an external client on the public internet down to an application running on a Linux virtual machine:

```
[ External User / Web Client ]
              |
              v
    [ Internet Gateway (IGW) ]  <--- Translates Public IP -> Subnet Private IP
              |
              v
    [ Network ACL (NACL) ]      <--- Subnet-Level Firewall (Stateless, Rule Numbers)
              |
              v
[ Elastic Network Interface (ENI) ]
              |
              v
    [ Security Group (SG) ]     <--- Instance/ENI Firewall (Stateful, Port 8080 Check)
              |
              v
     [ Linux OS Kernel ]        <--- Kernel identifies socket listening on Port 8080
              |
              v
 [ Apache Airflow Webserver ]   <--- Serves UI to Client Browser
```

1. **Internet Gateway (IGW):** First point of contact at the VPC boundary; routes traffic and handles 1:1 NAT translation from the public IPv4 address to the instance's private IPv4 address.
2. **Network Access Control List (NACL):** Evaluates inbound traffic at the **subnet level**. By default, AWS allows all inbound/outbound traffic (`Rule 100: ALLOW`).
3. **Elastic Network Interface (ENI):** The virtual network card bound to the EC2 instance inside the subnet.
4. **Security Group (SG):** Evaluated at the **ENI boundary**. If port `8080` (or `22` for SSH) is not explicitly permitted in the inbound rules, the packet is silently dropped.
5. **Linux Kernel & Application Port:** Traffic enters the operating system; the kernel checks local listening daemons (e.g., MySQL on `3306`, Airflow on `8080`) and forwards the payload to the application container.

## Part 2: IAM Roles vs. Instance Profiles (The Presidential Office Analogy)

### 1. The Real-World Election Analogy
To make IAM Roles intuitive, Mayowa used a political election analogy:
* **The Role / The Office:** The *Office of the President*. The office exists independently of whoever occupies it.
* **The Policy / Privileges:** The official powers, rights, and perks legally attached to that office (free travel, official residence, executive veto power).
* **The Principal / Candidate:** Mayowa or any citizen running for election.
* **Assuming the Role:** When Mayowa wins the election, he steps into the office and **assumes the role**. He inherits all privileges attached to that office. Once his term ends, he vacates the office, leaving the privileges behind.

```
+-------------------------------------------------------------------------+
| IAM Policy (The Privileges): AmazonS3FullAccess                          |
+-------------------------------------------------------------------------+
                                   |
                                   v (Attached to)
+-------------------------------------------------------------------------+
| IAM Role (The Office): Temitope_Role_Demo                               |
| Trust Relationship: ec2.amazonaws.com                                   |
+-------------------------------------------------------------------------+
                                   |
                                   v (Assumed by)
+-------------------------------------------------------------------------+
| EC2 Instance Profile: Embedded Identity attached to EC2 Hardware       |
| -> AWS Security Token Service (STS) rotates temporary keys invisibly    |
+-------------------------------------------------------------------------+
```

### 2. Why Long-Lived Static Keys are Banned in Production
In legacy or beginner environments, engineers generate an IAM User, create static credentials (`AKIA...` and Secret Key), and store them in `.env` files, Docker Compose YAMLs, or hardcoded Python scripts.
* **The Threat:** If a developer laptop is lost, a GitHub repository is accidentally made public, or an instance is compromised, attackers harvest the keys and rack up hundreds of thousands of dollars in crypto-mining charges.
* **The Production Solution (IAM Roles & Instance Profiles):**
  * You create an **IAM Role** with a **Trust Relationship** allowing `ec2.amazonaws.com` to assume it.
  * You attach an **IAM Policy** granting specific permissions (e.g., `s3:PutObject`, `s3:GetObject`).
  * You attach this role to your running EC2 instance as an **Instance Profile**.
  * **How AWS Handles Authentication:** The **AWS Security Token Service (STS)** automatically generates temporary, short-lived API credentials, injects them directly into the instance metadata service (`http://169.254.169.254/latest/meta-data/`), and rotates them automatically without human intervention.

## Part 3: EC2 Purchasing Models & The FinOps Playbook

Mayowa broke down the three primary purchase options on AWS, emphasizing that senior engineers win promotions and stakeholder trust by cutting infrastructure waste:

```
+-----------------------------------------------------------------------------------------+
| AWS EC2 Purchasing Models Comparison                                                    |
+---------------------+-------------------+-----------------------+-----------------------+
| Feature / Metric    | On-Demand         | Reserved Instances    | Spot Instances        |
+---------------------+-------------------+-----------------------+-----------------------+
| Commitment Length   | None (Pay-as-you-go)| 1 Year or 3 Years   | None (Surplus pool)   |
| Discount Level      | 0% (Baseline Max) | Up to 72% Discount    | Up to 90% Discount    |
| Interruption Risk   | Zero (Guaranteed) | Zero (Guaranteed)     | High (2-minute warning)|
| Payment Options     | Hourly / By Second| All / Partial / No Upfront | Billed by Second |
| Ideal Workload Type | Spiky, dev/test,  | Steady-state core DBs,| Stateless apps, batch |
|                     | short-lived jobs  | 24/7 production hosts | pipelines, K8s workers|
+---------------------+-------------------+-----------------------+-----------------------+
```

### 1. On-Demand Instances
* The most flexible, convenient, and **most expensive** purchase model.
* No long-term commitment; launch and terminate at will, billed down to the second.
* *Best for:* Unpredictable workloads, early development, proof-of-concept testing.

### 2. Reserved Instances (RIs) & Savings Plans
* Contractual commitment for **1 year or 3 years** in exchange for massive hourly discounts.
* **Payment Tiers:**
  * *All Upfront:* Greatest discount.
  * *Partial Upfront:* Balanced cash flow.
  * *No Upfront:* Monthly payment with a smaller discount.
* *Best for:* Core production relational databases (PostgreSQL/RDS), persistent message brokers (Kafka), and 24/7 master servers.

### 3. Spot Instances (The Cloud Secret Weapon)
* AWS constructs massive hyperscale data centers sized to handle global peak traffic spikes (e.g., Black Friday). During normal periods, massive pools of server racks sit idle.
* AWS sells this spare compute capacity at steep discounts (often **70% to 90% off On-Demand rates**).
* **The Trade-off (Preemption):** If an On-Demand customer requests that capacity, AWS reclaims the instance.
* **The 2-Minute Termination Notice:** AWS sends an automated interruption signal via CloudWatch / Instance Metadata exactly **2 minutes** before terminating or stopping the Spot instance.
* *FinOps Reality Check:* Mayowa shared a real-world enterprise achievement where optimizing compute using Spot architecture cut an organization's monthly infrastructure bill from **\$160,000 down to \$26,000**.

## Part 4: Auto Scaling Groups (ASG) & Self-Healing Compute

```
                 [ Auto Scaling Group (ASG) ]
                 - Desired Capacity: 2
                 - Min: 1 | Max: 4
                 - Launch Template: c5a.xlarge (Spot)
                               |
            +------------------+------------------+
            |                                     |
            v                                     v
  [ Spot Instance 1 ]                   [ Spot Instance 2 ]
  Status: HEALTHY                       Status: TERMINATED (Preempted!)
            |                                     |
            |                                     v
            |                         [ ASG Health Check Triggers ]
            |                                     |
            |                                     v
            |                         [ ASG Automatically Launches ]
            |                         [ Replacement Spot Instance  ]
            |                                     |
            v                                     v
  [ Spot Instance 1 ]                   [ Spot Instance 3 (NEW) ]
```

### 1. How an Auto Scaling Group Works
An Auto Scaling Group (ASG) is a logical collection of EC2 instances managed by an automated rule engine:
* **Desired Capacity:** The target number of running instances your workload requires (e.g., `Desired = 2`).
* **Minimum / Maximum Capacity:** Safety boundaries preventing scaling down to zero or scaling up beyond budget limits.
* **Scaling Policies:** Dynamic metrics (e.g., *“If average CPU utilization exceeds 80% for 5 minutes, add 2 instances”*).

### 2. Auto Scaling as a Spot Interruption Defense
* When running Spot instances, individual servers *will* be terminated periodically.
* An ASG acts as an automated janitor: the moment a Spot instance receives a termination notice or drops off health checks, the ASG immediately queries available AZs and launches a replacement instance to restore the Desired Capacity.
* **Launch Templates & Instance Diversification:** To prevent outages when a specific instance pool runs out of spare capacity, production ASGs configure **multiple instance families** (e.g., allow `c5a.xlarge`, `c5.xlarge`, `m5.xlarge`, or `m5a.xlarge`). If one family is depleted, the ASG launches another.

## Part 5: Private Subnet Egress via NAT Gateway

In enterprise security architectures, databases and backend data pipelines (like Airflow workers) are placed inside **Private Subnets** with zero direct inbound routes from the internet. However, these systems frequently need outbound connectivity to run `pip install pandas`, download software security updates, or push data to external APIs.

```
[ Private Subnet: 10.0.0.16/28 ]             [ Public Subnet: 10.0.0.0/28 ]
+------------------------------+             +-------------------------------+
| EC2 Backend / Airflow Worker |             | NAT Gateway (Elastic IP Bound)|
| (No Public IP Address)       |             |                               |
+--------------+---------------+             +---------------+---------------+
               | (Outbound Only)                             |
               v                                             v
  [ Private Route Table ]                       [ Public Route Table ]
  Destination: 0.0.0.0/0                        Destination: 0.0.0.0/0
  Target: nat-0123456789abcdef0                 Target: igw-0123456789abcdef0
               |                                             |
               +---------------------------------------------> [ Internet Gateway (IGW) ]
                                                                     |
                                                                     v
                                                          🌐 The Public Internet
```

### 1. NAT Gateway Architecture Rules
* **Placement:** A NAT Gateway **must always be deployed inside a Public Subnet**.
* **Elastic IP Requirement:** A NAT Gateway must be allocated a static **Elastic IPv4 Address** upon creation.
* **Routing Table Logic:**
  * The **Public Subnet Route Table** routes `0.0.0.0/0` to the **Internet Gateway (IGW)**.
  * The **Private Subnet Route Table** routes `0.0.0.0/0` to the **NAT Gateway (`nat-xxxx`)**.
* **Stateful Outbound Translation:** The NAT Gateway receives outbound requests from private instances, substitutes its own Elastic IP, routes the packet to the Internet Gateway, and seamlessly passes the returned response back to the private instance. 
* **Inbound Lockdown:** No outside client on the internet can initiate a connection into a private instance through a NAT Gateway.

### 2. FinOps Warning: NAT Gateway Costs
A NAT Gateway is not free:
* Billed at an **hourly availability charge** (approx. \$0.045/hour $\approx$ \$32.40/month per gateway).
* Billed at a **data processing charge** (approx. \$0.045 per Gigabyte transferred).
* *Architectural Best Practice:* For dev/test environments, terminate NAT Gateways when not in use. For high-volume data pipelines, keep transfers internal or route traffic via free S3/DynamoDB **VPC Gateway Endpoints**.

>  **Official AWS Reference:** [AWS VPC NAT Gateway User Guide](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html)

## Part 6: Production Blueprint — Airflow Distributed on Kubernetes with Spot Instances

Mayowa shared a live production architecture running at Core Data Engineers, demonstrating how modern engineering teams combine all these primitives:

```
+-----------------------------------------------------------------------------------------+
| AWS Region: eu-central-1 (Frankfurt)                                                    |
|                                                                                         |
|  +-----------------------------------------------------------------------------------+  |
|  | Kubernetes Cluster (EKS / Managed Node Group)                                     |  |
|  | Managed by Auto Scaling Group (Desired Capacity = 3, Spot Instances: c5a.xlarge)  |  |
|  |                                                                                   |  |
|  |  [ Worker Node 1 (AZ 1a) ]   [ Worker Node 2 (AZ 1b) ]   [ Worker Node 3 (AZ 1c) ]|  |
|  |  +-----------------------+   +-----------------------+   +-----------------------+  |  |
|  |  | Pod: Airflow Webserver|   | Pod: Airflow Scheduler|   | Pod: Airflow Celery   |  |  |
|  |  | Pod: Airbyte Sync App |   | Pod: Postgres Metadata|   |      Worker Task      |  |  |
|  |  +-----------------------+   +-----------------------+   +-----------------------+  |  |
|  +-----------------------------------------------------------------------------------+  |
+-----------------------------------------------------------------------------------------+
```

### 1. The Single-Node Trap vs. Distributed Kubernetes
* **The Single-Node Bottleneck:** Running Airflow, Postgres metadata, and Airbyte on a single EC2 instance inside Docker Compose creates a single point of failure (no high availability, no resource isolation, noisy neighbor memory starvation).
* **The Kubernetes Multi-AZ Pattern:** 
  * Three EC2 instances of type `c5a.xlarge` are deployed across separate Availability Zones (`eu-central-1a`, `eu-central-1b`, `eu-central-1c`).
  * All three instances run as **Spot Instances** inside an Auto Scaling Group (`Desired = 3`).
  * Airflow components are containerized into **Kubernetes Pods** and distributed across nodes.
  * If AWS reclaims Node 2, Kubernetes automatically reschedules the interrupted pods onto Node 1 and Node 3 within seconds, while the ASG provisions a replacement spot server in the background.

### 2. Live Pricing Comparison (c5a.xlarge in Frankfurt)
Mayowa demonstrated live pricing comparisons via Vantage / AWS Console:
* **On-Demand:** **\$0.154 / hour**
* **1-Year Reserved:** **\$0.097 / hour**
* **3-Year Reserved:** **\$0.067 / hour**
* **Spot Price:** **\$0.071 / hour** (*Over 54% immediate savings with zero commitment!*)

### Demo 1: Passwordless S3 Data Ingestion via EC2 IAM Instance Profiles

#### Objective
Deploy an Apache Airflow DAG onto an EC2 server with **zero hardcoded credentials**. Observe the pipeline fail with `NoCredentialsError`, attach an empty IAM Role to witness `AccessDenied`, grant `AmazonS3FullAccess`, and verify automated data ingestion directly into an S3 bucket.

```
+------------------------------------------------------------------------------------+
| Live Demo Test Matrix: The 3 Stages of Pipeline Authentication                     |
+-------------------+------------------------------+---------------------------------+
| Test Phase        | Attached IAM Configuration   | Pipeline Execution Result       |
+-------------------+------------------------------+---------------------------------+
| Stage 1: Baseline | No IAM Role attached         | ❌ FAILED: Unable to locate     |
|                   |                              |    credentials                  |
| Stage 2: Identity | IAM Role with 0 permissions  | ❌ FAILED: Access Denied        |
| Stage 3: Success  | IAM Role + S3 FullAccess     | ✅ SUCCESS: Data written to S3  |
+-------------------+------------------------------+---------------------------------+
```

#### Step-by-Step Instructions

##### Step 1: Create the Target S3 Data Lake Bucket
1. Open the **Amazon S3 Console** $\rightarrow$ Click **Create bucket**.
2. **Bucket name:** `cdebytes-customer-data-lake-xxxx` *(must be globally unique)*.
3. **Region:** Select your active region (e.g., `eu-north-1` Stockholm or `eu-central-1` Frankfurt).
4. Leave all other default settings (Block all public access enabled).
5. Click **Create bucket**.

##### Step 2: Create the IAM Role for EC2
1. Open the **IAM Console** $\rightarrow$ Click **Roles** $\rightarrow$ Click **Create role**.
2. Under **Trusted entity type**, select **AWS service**.
3. Under **Use case**, select **EC2** *(allows EC2 instances to call AWS services on your behalf)*.
4. Click **Next**.
5. **Add permissions:** Do **not** select any policy! Leave permissions completely blank to test identity recognition first.
6. Click **Next**.
7. **Role name:** `Temitope_Role_Demo`.
8. Review the Trust Policy JSON:
   ```json
   {
       "Version": "2012-10-17",
       "Statement": [
           {
               "Effect": "Allow",
               "Principal": {
                   "Service": "ec2.amazonaws.com"
               },
               "Action": "sts:AssumeRole"
           }
       ]
   }
   ```
9. Click **Create role**.

##### Step 3: Run Baseline Test (No IAM Role Attached)
1. SSH into your running EC2 instance where Airflow is running:
   ```bash
   ssh -i ~/Downloads/cde_demo_keypair.pem ubuntu@<EC2-PUBLIC-IP>
   ```
2. Navigate to your Airflow directory and inspect the Python DAG code:
   ```bash
   cd ~/airflow/dags
   cat customer_s3_dag.py
   ```
   *Notice: The script uses `boto3.client('s3')` with NO access keys or secret keys.*
3. Open the **Airflow Web UI** in your browser (`http://<EC2-PUBLIC-IP>:8080`).
4. Trigger `customer_s3_dag`.
5. Click the failed task $\rightarrow$ Open **Logs**.
6. **Observed Error (Stage 1):**
   ```text
   botocore.exceptions.NoCredentialsError: Unable to locate credentials
   ```

##### Step 4: Attach the Blank IAM Role (Instance Profile)
1. In the **EC2 Console**, navigate to **Instances** $\rightarrow$ Select your Airflow EC2 instance.
2. Click **Actions** $\rightarrow$ **Security** $\rightarrow$ **Modify IAM role**.
3. In the dropdown, select `Temitope_Role_Demo`.
4. Click **Update IAM role**.
5. Return to the Airflow Web UI $\rightarrow$ Re-trigger `customer_s3_dag`.
6. Open task **Logs**.
7. **Observed Error (Stage 2):**
   ```text
   botocore.exceptions.ClientError: An error occurred (AccessDenied) when calling the PutObject operation: Access Denied
   ```
   *Diagnosis: The server successfully detected credentials via STS, but the role has no permissions to write to S3!*

##### Step 5: Attach S3 Permissions & Achieve Green Pipeline Health
1. Open the **IAM Console** $\rightarrow$ Click **Roles** $\rightarrow$ Select `Temitope_Role_Demo`.
2. Under the **Permissions** tab, click **Add permissions** $\rightarrow$ **Attach policies**.
3. Search for and check `AmazonS3FullAccess` *(in production, scope this to a custom policy allowing only `s3:PutObject` on your specific bucket)*.
4. Click **Add permissions**.
5. Return to the Airflow Web UI $\rightarrow$ Clear/Re-trigger `customer_s3_dag`.
6. **Result:** The DAG run turns bright green (**Success**)!
7. Open the **Amazon S3 Console** $\rightarrow$ Navigate into `cdebytes-customer-data-lake-xxxx`.
8. Verify that three new customer data objects appear in the bucket.

### Demo 2: Outbound Internet Access for Private Subnets via AWS NAT Gateway

#### Objective
Configure outbound internet connectivity for an isolated private subnet using a NAT Gateway deployed in a public subnet, update route tables, and verify that private workloads can perform software downloads (`pip install pandas`) while remaining completely unreachable from inbound public traffic.

```
[ Private Route Table ] -> 0.0.0.0/0 -> [ NAT Gateway in Public Subnet ] -> [ IGW ] -> 🌐 Internet
```

#### Step-by-Step Instructions

##### Step 1: Verify Subnet Separation in VPC
1. Open the **VPC Console** $\rightarrow$ Click **Subnets**.
2. Ensure you have two distinct subnets inside your custom VPC:
   * `Public_Subnet` (e.g., `10.0.0.0/28` in `eu-north-1a`).
   * `Private_Subnet` (e.g., `10.0.0.16/28` in `eu-north-1b`).

##### Step 2: Allocate an Elastic IP & Deploy the NAT Gateway
1. In the left VPC menu, click **NAT Gateways** $\rightarrow$ Click **Create NAT gateway**.
2. **Name:** `cde_demo_nat_gateway`.
3. **Subnet:** Select `Public_Subnet` *(CRITICAL: A NAT Gateway must ALWAYS sit in a public subnet with direct internet access)*.
4. **Connectivity type:** Select **Public**.
5. **Elastic IP allocation ID:** Click **Allocate Elastic IP** to automatically generate and bind a dedicated static public IPv4 address.
6. Click **Create NAT gateway**.
7. *Wait 2 to 3 minutes until the NAT Gateway status changes from `Pending` to `Available`.*

##### Step 3: Configure the Private Subnet Route Table
1. In the left VPC menu, click **Route Tables** $\rightarrow$ Click **Create route table**.
2. **Name:** `Private_Subnet_Route_Table`.
3. **VPC:** Select your custom VPC.
4. Click **Create route table**.
5. Select `Private_Subnet_Route_Table` $\rightarrow$ Click the **Subnet associations** tab $\rightarrow$ Click **Edit subnet associations**.
6. Check `Private_Subnet` and click **Save associations**.
7. Click the **Routes** tab $\rightarrow$ Click **Edit routes**.
8. Click **Add route**:
   * **Destination:** Enter `0.0.0.0/0` *(all outbound internet traffic)*.
   * **Target:** Select **NAT Gateway** $\rightarrow$ Select `cde_demo_nat_gateway`.
9. Click **Save changes**.

##### Step 4: Verify Architecture in the VPC Resource Map
1. In the left VPC menu, click **Your VPCs** $\rightarrow$ Select your custom VPC.
2. Scroll down to inspect the **Resource map**:
   * `Public_Subnet` connects to `Public_Route_Table` $\rightarrow$ routes out to the **Internet Gateway (IGW)** (Green Badge).
   * `Private_Subnet` connects to `Private_Subnet_Route_Table` $\rightarrow$ routes out to the **NAT Gateway** $\rightarrow$ routes through the Public Subnet to the **IGW** (Blue Badge).
3. The private subnet is now fully capable of initiating outbound API requests and package downloads while maintaining complete perimeter isolation against unsolicited inbound internet attacks.

## 2. AWS Global Topology: Regions, Availability Zones & Compliance

Understanding where infrastructure physically resides is critical for low-latency networking and legal data governance.

```
                     GEOGRAPHIC WORLD / CONTINENT
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       ▼                                                       ▼
[ Region: eu-central-1 ]                               [ Region: af-south-1 ]
   Frankfurt, Germany                                     Cape Town, South Africa
       │                                                       │
 ┌─────┴────────────────────────┐                        ┌─────┴────────────────────────┐
 │ Isolated Data Centers (AZs)  │                        │ Isolated Data Centers (AZs)  │
 │ • eu-central-1a              │                        │ • af-south-1a                │
 │ • eu-central-1b              │                        │ • af-south-1b                │
 │ • eu-central-1c              │                        │ • af-south-1c                │
 └──────────────────────────────┘                        └──────────────────────────────┘
```

### Key Architectural Definitions:
* **Region:** A distinct physical geographic location/city worldwide containing clusters of data centers (e.g., `eu-central-1` in Frankfurt, `us-east-1` in North Virginia, `af-south-1` in Cape Town).
  * *African Coverage Note:* As of 2026, AWS maintains one primary cloud region on the African continent: **Cape Town, South Africa (`af-south-1`)**, launched in 2020 with 3 Availability Zones.
* **Availability Zone (AZ):** One or more discrete data centers with redundant power, networking, and connectivity within an AWS Region. They are separated by meaningful physical distance (miles apart) to isolate fault domains, yet connected via ultra-low-latency private fiber.
* **High Availability (HA):** Deploying infrastructure across multiple AZs (e.g., primary database in `eu-central-1a` and synchronous replica in `eu-central-1b`). If zone A catches fire, traffic fails over seamlessly to zone B.

### Data Residency & Compliance (GDPR vs. Latency)
When student **Blessed Ebosele** asked what governs regional selection, Mayowa highlighted two non-negotiable considerations:
1. **Legal Data Sovereignty / Privacy Regulations (GDPR):** If your users reside in Germany or the EU, storing customer records on US-based servers (`us-east-1`)—even if compute is significantly cheaper—violates international privacy regulations and invites catastrophic legal fines.
2. **Network Latency:** Data travels through fiber at physical speeds. Serving UK or European users from a data center in South Africa introduces round-trip packet latency, degrading application performance.

## 3. The Bedrock Service: Identity & Access Management (IAM)

Mayowa stressed that **IAM is the very first service every engineer must master**:

$$
\text{IAM Knowledge} = \text{The Difference Between a Professional Engineer and a "Mechanic"}
$$

```
                                  AWS ACCOUNT
                                       │
                      ┌────────────────┴────────────────┐
                      ▼                                 ▼
           ROOT USER ACCOUNT                   IAM USERS / IDENTITIES
       (Superadmin / Billing Email)         (Engineers, Pipelines, Bots)
              │                                         │
     ❌ NEVER USE FOR DAILY WORK!              ✅ Scoped Least-Privilege Access
     Lock with MFA and vault it!               Governed by attached JSON policies
```

### The Authentication vs. Authorization Boundary
* **Authentication (AuthN) — "Who are you?":** Proving identity. Handled via console passwords + MFA (for humans) or Access Key IDs + Secret Access Keys (for programmatic scripts and Airflow/Airbyte tasks).
* **Authorization (AuthZ) — "What are you allowed to do?":** Determining permissions. Governed entirely by IAM Policies. Being authenticated does not mean you can query S3 or launch an EC2 server; you must be explicitly authorized.

### Access Vectors: Console vs. Programmatic Keys
1. **AWS Management Console (GUI):** Web interface accessed by human engineers using an IAM username, account ID, and password + MFA.
2. **Programmatic Access (CLI / SDK / API):** Non-human processes (Python scripts, Airflow DAGs, Terraform) cannot log in via web browsers. They require:
   * **AWS Access Key ID:** Analogous to a username.
   * **AWS Secret Access Key:** Analogous to a secure, long-lived password.

## 4. Deciphering the Amazon Resource Name (ARN)

Every unique resource provisioned in AWS—from an IAM user to an S3 object or Redshift cluster—is assigned a globally unique identifier known as an **ARN**.

```
arn:partition:service:region:account-id:resource-id
arn:partition:service:region:account-id:resourcetype/resource-id
arn:partition:service:region:account-id:resourcetype:resource-id
```

### Breakdown of ARN Components:

```
  arn:aws:iam::340752000000:user/zainab
   ▲   ▲   ▲  ▲      ▲      ▲     ▲
   │   │   │  │      │      │     └─ Resource ID: "zainab"
   │   │   │  │      │      └─────── Resource Type: "user/"
   │   │   │  │      └────────────── Account ID: 12-digit AWS account number
   │   │   │  └───────────────────── Region: Blank! (IAM is a global service)
   │   │   └──────────────────────── Service Namespace: "iam"
   │   └──────────────────────────── Partition: Standard public cloud ("aws")
   └──────────────────────────────── Scheme: Constant prefix ("arn")
```

### Why Regional Fields Vary:
* **Global Services (IAM, CloudFront, Route53):** Have an empty region segment (e.g., `arn:aws:iam::123456789012:user/developer`).
* **Regional Services (S3, EC2, RDS):** Explicitly require the region code:
  * S3 Bucket: `arn:aws:s3:::my-production-data-lake`
  * EC2 Instance: `arn:aws:ec2:eu-central-1:123456789012:instance/i-0abcd1234efgh5678`

## 5. Enterprise Policy Engineering: Anatomy of an IAM Policy

IAM Policies are declarative JSON documents defining access boundaries.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3DataLakeReadWriteWithIPRestriction",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::cde-analytics-lakehouse",
        "arn:aws:s3:::cde-analytics-lakehouse/*"
      ],
      "Condition": {
        "IpAddress": {
          "aws:SourceIp": "197.210.0.0/16"
        }
      }
    }
  ]
}
```

### Dissecting the Policy Elements:

| Key | Description | Technical Requirement |
| :--- | :--- | :--- |
| **`Version`** | The language syntax release date. | **Must always be `"2012-10-17"`**. (Do not use current calendar dates; `"2008-10-17"` is legacy and lacks condition features). |
| **`Statement`** | Array of individual permission rules. | A single policy can chain multiple permission statements together. |
| **`Sid`** | Statement ID. | Optional human-readable description for auditing and log inspection. |
| **`Effect`** | The outcome of evaluation. | Explicit **`"Allow"`** or **`"Deny"`**. (Default in AWS is implicit deny; an explicit deny overrides any allow). |
| **`Action`** | Specific API operations permitted. | Formatted as `service:operation` (e.g., `"s3:GetObject"`, `"rds:CreateDBInstance"`). |
| **`Resource`** | The targeted entity ARN. | Targets exact ARNs. Wildcards (`*`) grant broad access and must be avoided in production. |
| **`Condition`** | Contextual constraints. | Restricts access based on client IP, MFA status, secure SSL/TLS protocols, or dates. |

## 6. The Production Scenario: Segregating Sensitive PII in Data Lakes

Mayowa walked through a real-world enterprise challenge to explain why AWS-managed policies fail in corporate environments:

```
                  RAW S3 INGESTION LAKEHOUSE
┌─────────────────────────────────────────────────────────────┐
│ Bucket: s3://cde-company-data-lake                          │
│                                                             │
│ 📁 /pii-customer-records/        📁 /public-aggregated-sales/│
│    (Names, BVN, Credit Cards)       (Daily revenue, Counts) │
└──────────────┬──────────────────────────────┬───────────────┘
               │                              │
               ▼                              ▼
    [ Debt Collection Team ]         [ BI Analytics Team ]
    Requires PII access to recover   Must NEVER see customer PII;
    defaulted loans                  only aggregated trends permitted
```

### The Breakdown:
* **The AWS-Managed Policy Trap:** Attaching `AmazonS3FullAccess` or `AmazonS3ReadOnlyAccess` grants access to the **entire bucket**, instantly exposing confidential PII to analysts and violating banking privacy laws.
* **The Customer-Managed Policy Fix:** Engineers author custom JSON policies restricting the BI Analytics group strictly to `arn:aws:s3:::cde-company-data-lake/public-aggregated-sales/*`, while explicitly denying or omitting the `/pii-customer-records/*` path prefix.

## 🏗️ 7. The Three Non-Negotiables: The Core Cloud Trio

Mayowa concluded by defining the three essential pillars of modern cloud architecture:

```
┌────────────────────────────────────────────────────────────────────────┐
│                  THE CLOUD TRIO FOR DATA ENGINEERS                     │
├────────────────────────────────────────────────────────────────────────┤
│ 1. IAM (Security & Permissions):                                       │
│    Authentication, roles, authorization, least-privilege boundary.     │
│                                                                        │
│ 2. VPC (Networking & Isolation):                                       │
│    IP CIDR blocks, public/private subnets, firewalls, and routing.     │
│                                                                        │
│ 3. EC2 (Compute & Servers):                                            │
│    Virtual machines, CPU/RAM sizing, EBS persistent block storage.     │
└────────────────────────────────────────────────────────────────────────┘
```

Every advanced platform—whether **Snowflake running on AWS**, an **Airflow cluster on Kubernetes (EKS)**, a **Databricks lakehouse**, or a **Redshift warehouse**—is built directly on top of these three services. Mastering them provides complete architectural independence.

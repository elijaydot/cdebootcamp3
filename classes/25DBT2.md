# dbt Core, dbt Cloud, and Databricks: Connectivity, Debugging, and Compilation

**Consolidated technical masterclass from the September 21, 2026 live labs (84-minute hands-on lab and 59-minute troubleshooting clinic)**

**Lead facilitator:** Victor Okon  
**Core topics:** dbt project architecture, dbt Core versus dbt Cloud, `uv` dependency management, Databricks Unity Catalog and SQL Warehouse provisioning, PAT and service-principal authentication, cross-platform environment variables, `dbt debug`, `dbt compile`, target artifacts, static lineage documentation, and live cohort troubleshooting.

---

## 1. Session Overview

These sessions moved the cohort from a configured but inactive dbt project to a working connection with a Databricks SQL Warehouse. They also introduced dbt Cloud as a managed alternative to local dbt Core development.

The central lesson was that a dbt project cannot execute until its profile can authenticate with an active compute engine. Once `dbt debug` passes, dbt can compile Jinja and SQL, resolve model dependencies, and execute transformations in the warehouse. Most setup failures occur at the boundary between the active shell, environment variables, authentication credentials, the warehouse HTTP path, and the dbt project directory.

The facilitator summarized the local connection challenge as follows:

> "A dbt project is inert until your profile validates against an active compute engine. The moment `dbt debug` passes green, your local SQL code transforms into compiled warehouse executions. The challenge is never the SQL; it is mastering the bridge between environment variables, authentication tokens, and warehouse HTTP paths across different operating systems." [cite: 13]

The follow-up clinic placed that workflow in a wider engineering context:

> "dbt Core is free, customizable, and gives you total control over Git workflows, local virtual environments, and CI/CD runners. dbt Cloud eliminates much of the local environment setup by providing a managed IDE, scheduler, and credentials interface, at the trade-off of per-seat licensing costs. A senior analytics engineer should be fluent in both." [cite: 15]

## 2. dbt Core and dbt Cloud

Both products support analytics engineering, but they place responsibility in different locations.

| Attribute | dbt Core (local CLI) | dbt Cloud (managed SaaS) |
| :--- | :--- | :--- |
| **Cost** | Free and open source | Free single-seat tier; paid per-seat enterprise tiers |
| **Execution environment** | Local CLI, Docker, Airflow, Prefect, or GitHub Actions | Managed cloud compute and browser-based IDE |
| **Configuration** | `profiles.yml` and operating-system environment variables | Web forms, dropdowns, OAuth, development credentials, and managed secrets |
| **Documentation and lineage** | Generated locally, including `dbt docs generate --static` | Hosted documentation and an integrated graphical DAG |
| **Developer onboarding** | Requires Python, Git, a package manager such as `uv`, and local credentials | Browser-based onboarding with less local setup |
| **Control** | Full control over environments, dependencies, Git, and CI/CD | Platform-managed IDE, scheduling, credentials, and orchestration |
| **Primary trade-off** | Greater flexibility with greater setup responsibility | Easier onboarding with platform cost and less local control |

### 2.1 The dbt Core route

The local workflow uses Astral `uv` to create an isolated environment and synchronize dependencies declared in `pyproject.toml` and locked in `uv.lock`.

```bash
uv sync
uv run dbt debug
uv run dbt compile
```

Running `uv sync` enables another engineer who clones the repository to install the same versions of `dbt-databricks` and its dependencies without polluting the global Python environment. Local dbt can then be integrated with Git workflows and external orchestrators such as Airflow, Prefect, or GitHub Actions.

### 2.2 The dbt Cloud route

dbt Cloud provides a browser IDE, hosted scheduling, managed connection settings, and hosted lineage. It avoids local shell and path problems, including Windows errors such as `uv trampoline failed to canonicalize script path`, while still connecting to the same Databricks SQL Warehouse.

## 3. dbt Project Architecture

The reference repository separates the Git root and Python environment from the active dbt project:

```text
cdc_modelling/ (Git root)
|-- .venv/                     # uv-managed virtual environment
|-- pyproject.toml             # Project and package dependencies
|-- uv.lock                    # Reproducible dependency lock file
`-- cdc_marketing/             # Active dbt project directory
    |-- dbt_project.yml        # dbt project configuration
    |-- profiles.yml           # Connection profiles and targets
    |-- .env                   # Local environment-variable scratchpad
    |-- analyses/              # Ad hoc, non-materialized SQL and archives
    |-- macros/                # Reusable Jinja functions and overrides
    |-- models/                # SQL transformation layers
    |   |-- staging/           # One-to-one raw cleanup: Bronze to Silver
    |   |-- intermediate/      # Business joins and cross-domain entities
    |   `-- marts/             # Facts and dimensions: Gold layer
    |-- seeds/                 # Small version-controlled CSV lookups
    |-- snapshots/             # Slowly Changing Dimension history
    |-- tests/                 # Data-quality assertions
    |   |-- generic/           # Reusable tests configured in YAML
    |   `-- singular/          # Custom SQL assertions
    `-- target/                # Generated SQL, metadata, and documentation
```

### 3.1 Responsibilities of the main folders

- **`analyses/`:** Contains SQL that dbt compiles but does not materialize as a table or view. Removing the `.sql` extension from a retired model can turn it into a searchable Git archive that does not run in daily builds.
- **`macros/`:** Holds reusable Jinja logic, such as currency conversion mappings and schema overrides. Macros keep repeated transformations DRY.
- **`models/`:** Contains the transformation graph, commonly organized into staging, intermediate, and marts layers.
- **`seeds/`:** Holds small, non-sensitive, static CSV lookup data such as region codes or discount tiers. Seeds are not appropriate for credentials, dynamic datasets, or high-volume data.
- **`snapshots/`:** Tracks record changes over time for Slowly Changing Dimension Type 2 use cases. dbt adds fields such as `dbt_valid_from` and `dbt_valid_to`.
- **`tests/`:** Contains or configures data assertions. Generic tests include `unique`, `not_null`, `accepted_values`, and `relationships`. A singular test is custom SQL, and it fails whenever its query returns one or more rows.
- **`target/`:** Stores generated artifacts and should be inspected after compilation or documentation generation.

Models and tests should use dependency-aware references instead of hard-coded physical paths:

```sql
select * from {{ ref('model_name') }}
```

```sql
select * from {{ source('source_name', 'table_name') }}
```

These functions allow dbt to construct the dependency graph, determine build order, and generate lineage.

## 4. Databricks Foundation

dbt requires a Databricks catalog, schema, SQL Warehouse, hostname, HTTP path, and authentication credential.

### 4.1 Unity Catalog topology

```text
+--------------------------------------------------------+
|             DATABRICKS UNITY CATALOG                   |
|                                                        |
|  CATALOG: bronze_production                            |
|  `-- SCHEMA: cdc_staging                               |
|      `-- TABLES: Managed Delta Lake tables             |
+--------------------------------------------------------+
```

### 4.2 Create the catalog and schema

Run the following statements in the Databricks SQL Editor. Terminate each statement with a semicolon or execute the statements individually.

```sql
-- Create the root catalog.
CREATE CATALOG IF NOT EXISTS bronze_production;

-- Create the working schema inside the catalog.
CREATE SCHEMA IF NOT EXISTS bronze_production.cdc_staging;
```

### 4.3 Collect the connection values

| Value | Example | Where to find it |
| :--- | :--- | :--- |
| **Catalog** | `bronze_production` | Unity Catalog or the SQL Editor |
| **Schema** | `cdc_staging` | Unity Catalog or the SQL Editor |
| **Server hostname** | `dbc-xxxxxxxx-xxxx.cloud.databricks.com` | **SQL Warehouses > warehouse name > Connection Details** |
| **HTTP path** | `/sql/1.0/warehouses/xxxxxxxxxxxxxxxx` | **SQL Warehouses > warehouse name > Connection Details** |
| **Personal Access Token** | `dapi_xxxxxxxxxxxxxxxxxxxxxxxxxxxx` | **User Profile/Settings > Developer > Access Tokens > Generate New Token** |

When creating the PAT used in the lab, select the **All APIs** access scope. A token with insufficient scope can authenticate partially but fail when dbt submits SQL operations.

## 5. Authentication and Secret Governance

Development and production automation should not depend on the same identity model.

```text
+------------------------------------------------------------------------+
|                  SECURITY AND CREDENTIAL ARCHITECTURE                   |
+------------------------------------------------------------------------+
| LOCAL DEVELOPMENT: HUMAN DEVELOPER                                     |
| - Authentication: Personal Access Token (PAT)                          |
| - Typical lifetime: Temporary, for example 30 to 730 days              |
| - Lab scope: All APIs                                                   |
| - Storage: Active shell environment variable                           |
|            DATABRICKS_PAT_TOKEN                                        |
+------------------------------------------------------------------------+
| PRODUCTION AND CI/CD: AUTOMATED IDENTITY                               |
| - Authentication: Service principal, a non-human machine identity      |
| - Protocol: Managed OAuth machine-to-machine                           |
| - Credentials: Client ID and client secret                             |
| - Storage: Azure Key Vault, AWS Secrets Manager, or GitHub Secrets     |
| - Benefit: Automation is independent of an employee's account          |
+------------------------------------------------------------------------+
```

Never hard-code a PAT, password, or client secret in `profiles.yml`, `dbt_project.yml`, source code, or Git. An exposed token can compromise the connected lakehouse. Use environment-variable placeholders locally and a managed secret store in automation.

The Databricks server hostname is non-sensitive metadata and may be written directly in `profiles.yml`. Tokens and other secrets must remain external.

## 6. Configure dbt Core

### 6.1 Proven Windows PowerShell workflow

The following is the complete command sequence that worked in Windows PowerShell for this project. Begin in the `CDE3BootCamp` workspace root.

#### Install the Databricks adapter and project dependencies

```powershell
Set-Location .\cdc_modeling\

uv add dbt-databricks
```

If the adapter installation encounters a cache or TLS-related problem, clean the `uv` cache and retry with native TLS:

```powershell
uv cache clean
uv add dbt-databricks --native-tls
```

Then synchronize the environment and add Elementary's Databricks integration:

```powershell
uv sync
uv add 'elementary-data[databricks]~=0.22.0'
```

#### Initialize the dbt project

```powershell
uv run dbt init cdc_marketing --skip-profile-setup
Set-Location .\cdc_marketing\
```

> **Path correction:** Use `Set-Location .\cdc_marketing\` or `cd .\cdc_marketing\`. The command `cd \.cdc_marketing\` points to a different folder named `.cdc_marketing` at the drive root and is not the project path created by `dbt init`.

#### Set the Databricks environment variables

Replace the two placeholders with the HTTP path and PAT copied from Databricks.

```powershell
$env:DEV_SCHEMA="cdc_staging"
$env:DEV_CATALOG="bronze_production"
$env:DEV_HTTP_PATH="paste your HTTP path"
$env:DATABRICKS_PAT_TOKEN="paste your PAT token"
```

These variables apply to the current PowerShell session. Run the remaining commands in the same terminal. Do not commit or publicly display the PAT.

#### Confirm that dbt is installed

```powershell
uv pip list | findstr dbt
```

This filters the installed package list to show dbt packages and their versions. Confirm that `dbt-core` and `dbt-databricks` appear.

#### Debug, compile, document, and run the first model

Run the commands in this order:

```powershell
uv run dbt debug
uv run dbt compile
uv run dbt docs generate --static
uv run dbt run --select my_first_dbt_model
```

`dbt debug` must pass before compilation and execution. The final command selects only `my_first_dbt_model` and materializes it according to its configured materialization.

#### Verify the table in Databricks

After the model run succeeds, open Databricks and navigate to:

```text
Catalog > bronze_production > cdc_staging > my_first_dbt_model
```

The built relation should appear inside the `cdc_staging` schema. Depending on the model configuration, Databricks may identify it as a table or view.

#### Open the static documentation and lineage graph

1. In the dbt project's `target/` folder, locate `static_index.html`.
2. Open it in a browser. On Windows, **Open with Live Server** in VS Code is the recommended method.
3. In the documentation site, select the floating **View Lineage Graph** button.
4. Inspect the upstream and downstream relationships among the project's models, sources, tests, and tables.

### 6.2 `profiles.yml`

Keep `profiles.yml` inside `cdc_marketing/`, beside `dbt_project.yml`, for the workflow used in this lab.

```yaml
cdc_marketing:
  target: "{{ env_var('DBT_TARGET', 'dev') }}"

  meta:
    base: &base
      type: databricks
      threads: 8

  outputs:
    dev: &dev_service_account
      <<: *base
      host: dbc-0196bfaf-1e17.cloud.databricks.com
      token: "{{ env_var('DATABRICKS_PAT_TOKEN') }}"
      catalog: "{{ env_var('DEV_CATALOG') }}"
      schema: "{{ env_var('DEV_SCHEMA') }}"
      http_path: "{{ env_var('DEV_HTTP_PATH') }}"
```

The profile uses YAML anchors to share adapter settings and Jinja `env_var` calls to read values from the process environment. `DBT_TARGET` defaults to `dev`; the other values must be available before dbt parses the profile.

If a required variable is unavailable in the shell that launches dbt, parsing stops with an error such as:

```text
Env var required but not provided: 'DATABRICKS_PAT_TOKEN'
```

PowerShell uses `$env:` assignments rather than the Bash `export` command.

```powershell
$env:DEV_SCHEMA="cdc_staging"
$env:DEV_CATALOG="bronze_production"
$env:DEV_HTTP_PATH="/sql/1.0/warehouses/your-warehouse-id"

```

### 6.5 Windows: Git Bash

Git Bash uses Bash syntax even though it is running on Windows.

```bash
export DEV_SCHEMA="cdc_staging"
export DEV_CATALOG="bronze_production"
export DEV_HTTP_PATH="/sql/1.0/warehouses/your-warehouse-id"
export DATABRICKS_PAT_TOKEN="dapi_your_token_value_here"

echo "$DEV_SCHEMA"
echo "$DEV_CATALOG"
```

If quoting causes a shell-specific path problem, the lab also used unquoted assignments such as `export DEV_SCHEMA=cdc_staging`. Do not include spaces around `=`.

### 6.6 Windows: WSL/Ubuntu

WSL is a Linux environment and therefore also uses Bash `export` syntax:

```bash
export DEV_SCHEMA="cdc_staging"
export DEV_CATALOG="bronze_production"
export DEV_HTTP_PATH="/sql/1.0/warehouses/your-warehouse-id"
export DATABRICKS_PAT_TOKEN="dapi_your_token_value_here"
```

Environment variables normally exist only in the terminal process where they were set. Opening a new PowerShell, Command Prompt, Git Bash, WSL, or VS Code terminal does not guarantee that values from another terminal will be inherited. Set and verify them in the same active terminal that will run dbt. Avoid printing the PAT during routine verification.

## 8. Configure dbt Cloud for Databricks

dbt Cloud moves the connection configuration from the local shell into its web interface.

```text
+------------------------------------------------------------------------+
|                    dbt CLOUD TO DATABRICKS                             |
+------------------------------------------------------------------------+
| 1. Connection name       Databricks                                    |
| 2. Server hostname       dbc-xxxxxxxx-xxxx.cloud.databricks.com        |
| 3. HTTP path             /sql/1.0/warehouses/xxxxxxxxxxxxxxxx          |
| 4. Personal Access Token dapi_xxxxxxxxxxxxxxxxxxxxxxxxxxxx             |
| 5. Target catalog        bronze_production                             |
| 6. Target schema         cdc_staging or a personal development schema |
| 7. Threads               8                                             |
+------------------------------------------------------------------------+
```

### Browser setup workflow

1. Open the dbt Cloud account setup page.
2. Create a project named `cdc_marketing` and choose **Databricks** as the adapter.
3. In **Connection Details**, enter the Databricks SQL Warehouse server hostname and HTTP path.
4. Set the target catalog to `bronze_production` and choose the working schema, such as `cdc_staging` or a personal development schema.
5. In **Development Credentials**, enter the developer's PAT and configure `8` threads.
6. Select **Test Connection**.
7. After the connection test turns green, save the credentials and begin compiling models in the browser IDE.

This route is useful when local Python, `uv`, shell syntax, or PATH configuration blocks progress. It does not remove the need for correct Databricks permissions, warehouse details, or responsible secret handling.

## 9. Compile Models and Inspect Artifacts

After `dbt debug` succeeds, compile the project:

```bash
uv run dbt compile
```

Compilation performs the following work:

1. Reads model SQL, YAML configuration, and Jinja.
2. Evaluates macros and resolves `ref()` and `source()` relationships.
3. Builds the project dependency graph and validates compilation against the adapter's SQL dialect.
4. Writes generated SQL and metadata to `target/`.

Important generated artifacts include:

| Artifact | Purpose |
| :--- | :--- |
| `target/compiled/` | Compiled SQL after Jinja and dbt functions are resolved |
| `target/manifest.json` | Graph of models, seeds, tests, sources, macros, and dependencies |
| `target/run_results.json` | Results and timing metadata from executed dbt commands |
| `target/catalog.json` | Warehouse relation and column metadata generated for docs |
| `target/index.html` | Standard documentation application shell |
| `target/static_index.html` | Portable static documentation generated with `--static` |

Compilation does not materialize models. The next execution step is `dbt run`, which creates or updates configured tables and views:

```bash
uv run dbt run
```

## 10. Generate and View Documentation

### 10.1 Standard documentation

```bash
uv run dbt docs generate
```

Standard generation produces separate assets such as `manifest.json`, `catalog.json`, and `index.html`. Opening `index.html` directly can fail because browser CORS rules prevent the page from loading the adjacent JSON files. The normal solution is a local web server:

```bash
uv run dbt docs serve
```

### 10.2 Portable static documentation

```bash
uv run dbt docs generate --static
```

The `--static` option bundles the project graph, model and column descriptions, definitions, and lineage data into one portable file:

```text
target/static_index.html
```

The file can be shared or hosted in cloud storage without keeping `dbt docs serve` running.

### 10.3 Viewing the generated site

- **macOS:** In VS Code, right-click `target/static_index.html` and choose **Open in Default Browser**.
- **Linux:** Use **Open in Default Browser**, a browser-opening extension, or serve the file locally.
- **Windows:** The class recommendation was the VS Code **Live Server** extension; right-click the file and select **Open with Live Server**.

The generated documentation provides an interactive DAG that shows dependencies established by `ref()` and `source()`.

## 11. Troubleshooting Matrix

| Error or symptom | Likely cause | Resolution |
| :--- | :--- | :--- |
| `dbt_project.yml not found` | The terminal is at the Git root rather than inside `cdc_marketing` | Change into the directory that contains `dbt_project.yml` before running dbt |
| No profile found | `profiles.yml` is missing, duplicated, malformed, or not in the location expected by this lab | Place the valid file beside `dbt_project.yml` in `cdc_marketing/` and remove conflicting duplicates |
| `Env var required but not provided: 'DATABRICKS_PAT_TOKEN'` | The variable was never set, the wrong shell syntax was used, or it was set in a different terminal | Use `$env:NAME="value"` in PowerShell or `export NAME="value"` in Bash/zsh/Git Bash/WSL, then run dbt in that same shell |
| Token scope connectivity failure | The PAT lacks the required API scope | Regenerate the PAT with **All APIs**, update the active shell or dbt Cloud credential, and retest |
| `Failed to create catalog` or SQL syntax error | Multiple SQL statements were submitted without delimiters | Add semicolons or execute the statements individually in Databricks SQL Editor |
| Authentication or connection failure | PAT is invalid/expired, hostname or HTTP path is wrong, warehouse is unavailable, or permissions are missing | Re-copy values from **SQL Warehouses > Connection Details**, confirm the warehouse is active, and validate access |
| Malformed Jinja/profile parsing error | Incorrect braces, quotes, indentation, or `env_var` expressions in `profiles.yml` | Compare the profile with the valid YAML example and correct the malformed expression |
| `uv trampoline failed to canonicalize script path` on Windows | Windows path resolution, execution permission, installation, or PATH problem | Verify the `uv` installation and PATH; retry from Git Bash or WSL/Ubuntu if necessary |
| Static docs appear blank or standard docs cannot load JSON | The standard docs page was opened directly and browser CORS blocked assets | Use `uv run dbt docs serve`, generate with `--static`, or open the static file through Live Server |

### 11.1 Recommended diagnosis order

1. Confirm the current directory contains `dbt_project.yml`.
2. Confirm `profiles.yml` is present and valid for this project.
3. Verify non-secret environment variables in the active terminal.
4. Confirm the PAT is current and has the required scope without printing it.
5. Re-copy the hostname and HTTP path from the selected SQL Warehouse.
6. Confirm the SQL Warehouse is running and the identity can use the catalog and schema.
7. Run `uv sync`, then retry `uv run dbt debug`.
8. Compile only after all debug checks pass.

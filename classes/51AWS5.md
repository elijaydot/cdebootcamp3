## Part 1: Opening Quiz Review & Key Reminders
*(Facilitated by Ayodeji Ajayi)*

The session opened with an interactive quiz reinforcing VPC networking concepts from Wednesday’s class:

1. **Route Table Terminology:**
   * **Destination:** *Where* network packets are headed (e.g., `0.0.0.0/0` for the entire internet, or a specific CIDR range).
   * **Target:** The gateway, network interface, or vehicle used to get there (e.g., `local` for intra-VPC, or `igw-xxxx` for an Internet Gateway).
2. **What Makes a Subnet "Public"?**
   * Simply naming a subnet `public_subnet` does **not** make it public. A subnet becomes public **if and only if** it is explicitly associated with a Route Table that routes `0.0.0.0/0` to an active **Internet Gateway (IGW)**.
3. **The Universal Internet CIDR Block:**
   * `0.0.0.0/0` represents every possible IPv4 address across the global internet.
4. **Data Egress Hierarchy (Ascending Order of Cost):**
   * **Intra-AZ Transfer:** Free ($0.00/GB) within the same Availability Zone.
   * **Inter-AZ Transfer:** ~$0.01/GB across different AZs in the same Region.
   * **Inter-Region Transfer:** ~$0.02/GB across different AWS Regions.
   * **Internet Egress:** ~$0.09/GB moving data out of AWS to the public internet (the most expensive).

```
|  | (Shared Tenancy - Default)    |             | (Shared Tenancy - Default)    |        |
|  +-------------------------------+             +-------------------------------+        |
+-----------------------------------------------------------------------------------------+
```

### 1. From Physical Racks to Cloud Instances
* An EC2 instance is not an abstract cloud concept; it is an isolated, virtualized slice of physical hardware housed in massive server rooms across AWS Availability Zones.
* **The Hypervisor:** Software/hardware layer (such as the **AWS Nitro System**) running on physical host servers that abstracts hardware, handles virtualization, and provisions isolated Virtual Machines (EC2 instances).

### 2. Hardware Tenancy Models
When creating a VPC or EC2 instance, you choose a tenancy model:
* **Default (Shared Tenancy):**
  * Multiple AWS customers share the physical CPU, memory, and motherboard of the same host machine.
  * Completely isolated via software and hypervisor memory sandboxing.
  * Most cost-effective; standard for 99% of cloud workloads.
* **Dedicated Instances:**
  * Runs on hardware dedicated exclusively to a single AWS account.
  * Other instances in your account can share the hardware, but no outside customer can.
  * Incurs an additional hourly charge.
* **Dedicated Hosts:**
  * You rent the **entire physical bare-metal server**.
  * Grants visibility into physical core counts, sockets, and host hardware IDs.
  * Required for strict regulatory compliance, proprietary server licensing (e.g., bring-your-own-license for Microsoft/Oracle), or specific security audits.
  * Extremely expensive.

## Part 3: EC2 Instance Types & Workload Matrix

An instance type string defines both the **family** and the **size**:

$$\Large \underbrace{\text{c7g}}_\text{Family} \, . \, \underbrace{\text{2xlarge}}_\text{Size}$$

* **Prefix (`c7g`):** Indicates the generation and purpose (`c` = compute optimized, `7` = 7th generation, `g` = Graviton / ARM architecture).
* **Suffix (`2xlarge`):** Dictates the hardware allocations: number of vCPUs, gigabytes of RAM, network bandwidth, and EBS throughput.

```
       [ General Purpose (t3, m5) ]
              /              \
             /                \
[ Compute Optimized (c5, c6g) ]  [ Memory Optimized (r5, r6g) ]
             \                /
              \              /
        [ Storage Optimized (i3, d2) ]
```

### 1. Instance Categories for Data Engineers
1. **General Purpose (`t3`, `t4g`, `m5`, `m6i`):**
   * Balanced CPU-to-memory ratio.
   * Ideal for web servers, container control planes, lightweight dev environments, and staging pipelines.
   * `t` series instances support **burstable performance** using CPU credits.
2. **Compute Optimized (`c5`, `c6g`, `c7g`):**
   * High vCPU-to-memory ratio.
   * Selected when query execution, mathematical transformation, or batch compute pushes CPU usage near 100% while memory usage remains modest.
   * Preferred for batch processing, video encoding, and dedicated machine learning inference nodes.
3. **Memory Optimized (`r5`, `r6g`, `x2gd`):**
   * Massive memory footprint relative to vCPUs.
   * Essential for in-memory processing engines such as **Apache Spark**, **Presto/Trino**, large-scale **Pandas/Polars** data transformations, and high-throughput caching (Redis, Memcached).
4. **Storage Optimized (`i3`, `i4i`, `d2`):**
   * Designed for workloads demanding sequential read/write operations and high direct-attached disk I/O (I/O Operations Per Second - IOPS).
   * Ideal for distributed data warehouses, massive NoSQL data stores (Cassandra, ScyllaDB), and Elasticsearch/OpenSearch clusters.

> 🔗 **Official AWS Reference:** [EC2 Instance Type Specifications](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-instance-type-specifications.html)

## Part 4: Storage Architecture — EBS vs. Instance Store

```
   [ EC2 Instance Compute Engine ]
          |               \
          | (Network Bus)  \ (Direct Bus)
          v                 v
+--------------------+   +-----------------------+
| Amazon EBS Volume  |   | Instance Store Volume |
| (Network Block)    |   | (Ephemeral / Attached)|
| - Survives Reboots |   | - Blazing Fast IOPS   |
| - Survives Stops   |   | - LOST ON STOP/KILL!  |
| - Snapshots to S3  |   |                       |
+--------------------+   +-----------------------+
```

### 1. Amazon EBS (Elastic Block Store)
* **Architecture:** Network-attached virtual disk drive. It behaves like an external SSD/HDD connected to the virtual machine across a high-speed dedicated network link.
* **Durability:** Data **persists independently** of the instance life cycle. If you stop, terminate, or replace the EC2 instance, the EBS volume remains intact (unless the `DeleteOnTermination` flag is set to true).
* **Snapshots:** Point-in-time incremental snapshots can be saved directly to Amazon S3.

### 2. Instance Store (Ephemeral Storage)
* **Architecture:** Physical, high-speed NVMe or SSD drives physically attached to the server host chassis housing your virtual instance.
* **Performance:** Incredible IOPS with ultra-low latency; eliminates network packet hops.
* **The Fatal Trap (Ephemeral):** **Data is volatile.** If you **Stop** or **Terminate** the instance, every byte written to an Instance Store volume is permanently wiped. It only survives basic operating system reboots.
* **Use Case:** Scratch disks, temporary Spark shuffle data, temporary buffers, and stateless caching tiers.

> **Official AWS Reference:** [Amazon EBS Pricing & Volume Types](https://aws.amazon.com/ebs/pricing/)

## Part 5: Networking Deep Dive — The Invisible ENI & Elastic IPs

### 1. Elastic Network Interface (ENI)
* An EC2 instance **does not own an IP address directly**.
* An **ENI** is a virtual network interface card (vNIC) created inside your subnet. It captures:
  * A primary private IPv4 address.
  * One or more secondary private IPv4 addresses.
  * An optional public IPv4 address or Elastic IP.
  * Associated Security Groups.
  * A hardware MAC address.
* When you launch an EC2 instance, AWS automatically attaches an ENI (e.g., `eth0`) to it. You can detach ENIs and attach them to different instances to seamlessly redirect network traffic.

### 2. The Public IP Gotcha & The Need for Elastic IPs (EIP)
* **Dynamic Public IPv4:** By default, when an instance in a public subnet has *Auto-assign Public IP* enabled, AWS assigns an IP address from its dynamic pool.
* **The Problem:** If you **Stop** the instance (to save money or reboot), that public IP is released back into the global AWS pool. When you **Start** the instance again, **it receives a completely new public IP address**. Any external tool, firewall whitelist, or DNS record pointing to the old IP breaks immediately!
* **The Solution (Elastic IP):** An **Elastic IP (EIP)** is a static, reserved, public IPv4 address that belongs to your AWS account. It stays permanently bound to your ENI until you explicitly release it, surviving all instance Stop/Start cycles.
* **FinOps Warning:** AWS charges for public IPv4 addresses per hour whether they are attached to active instances or sitting idle. Always release unused Elastic IPs.

## Part 6: Network Defense-in-Depth — Security Groups vs. NACLs

Understanding the two distinct layers of AWS cloud firewalls is essential for system defense:

```
[ Outside World / Internet (0.0.0.0/0) ]
                   |
                   v
   +-------------------------------+
   | Network ACL (NACL)            | <--- Subnet Level | Stateless
   | (Rule 100: Allow / Deny)      |      Inspects inbound AND outbound explicitly
   +-------------------------------+
                   |
                   v
   +-------------------------------+
   | Security Group (SG)           | <--- Instance / ENI Level | Stateful
   | (Allow Rules Only)            |      Return traffic is automatically permitted
   +-------------------------------+
                   |
                   v
       [ EC2 Linux Operating System ]
                   |
                   v
     [ Application / Port, e.g., 8080 ]
```

| Feature | Security Group (SG) | Network Access Control List (NACL) |
| :--- | :--- | :--- |
| **Operating Layer** | Instance / ENI Level | Subnet Level |
| **Rule Capabilities** | **ALLOW rules only** (Everything else is implicitly denied) | **ALLOW and DENY rules** |
| **State Nature** | **Stateful:** If traffic is allowed in, return traffic is automatically allowed out regardless of outbound rules. | **Stateless:** Outbound return traffic must be explicitly permitted in the outbound table. |
| **Rule Evaluation** | All rules are evaluated simultaneously before granting access. | Rules are processed strictly in **numerical order** (lowest number first, e.g., Rule 100 beats Rule 200). |
| **Default Configuration** | New custom SGs deny all inbound traffic and allow all outbound traffic. | Default VPC NACLs allow all inbound and outbound traffic (`*`). |

## Part 7: Packet Tracing with VPC Reachability Analyzer

* When data engineers see connection timeouts (`Connection timed out: connect`), they often scramble blindly between application code, database credentials, and VPC routes.
* **VPC Reachability Analyzer:** A declarative configuration analysis tool that tests network reachability between source and destination endpoints in a VPC without sending real data packets.
* It traces the hop-by-hop path:  
  $$\text{Internet Gateway (IGW)} \longrightarrow \text{NACL Evaluation} \longrightarrow \text{Route Table Path} \longrightarrow \text{Security Group} \longrightarrow \text{ENI} \longrightarrow \text{EC2}$$
* If traffic is blocked, it pinpoints the exact misconfigured rule, identifying whether an issue stems from a closed Security Group port or a blocking NACL deny rule.

### Demo 2: The SSH Connection Freeze, Key Permissions & Whitelisting

#### Objective
Experience why connections hang when Security Groups are closed, learn to fix private key permission vulnerabilities (`UNPROTECTED PRIVATE KEY FILE`), and gain shell access to the instance.

#### Step-by-Step Instructions

1. **Attempting Connection Without Security Group Inbound Rules:**
   * Copy the public IPv4 address (e.g., `13.60.30.105`) or public DNS hostname from the EC2 instance dashboard.
   * Open your terminal and attempt to SSH into the box:
     ```bash
     ssh -i ~/Downloads/cde_demo_keypair.pem ubuntu@13.60.30.105
     ```
   * **Observation:** The terminal hangs indefinitely with no response.
   * **Root Cause:** The default Security Group blocks all inbound traffic. Packets are dropped silently at the ENI boundary without returning a reject response. Terminate the hang using `Ctrl + C`.

2. **Whitelisting SSH Traffic in the Security Group:**
   * Open **EC2** $\rightarrow$ **Security Groups**. Select the instance's Security Group.
   * Click **Inbound rules** $\rightarrow$ **Edit inbound rules**.
   * Click **Add rule**:
     * **Type:** `SSH`
     * **Port Range:** `22`
     * **Source:** Select **My IP** (auto-detects your public IP, e.g., `102.89.x.x/32`) or select `Anywhere-IPv4` (`0.0.0.0/0`) for class testing.
   * Click **Save rules**.

3. **Resolving SSH Key Permission Rejection:**
   * Re-run the SSH command:
     ```bash
     ssh -i ~/Downloads/cde_demo_keypair.pem ubuntu@13.60.30.105
     ```
   * **The Error:**
     ```text
     @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
     @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
     @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
     Permissions 0644 for '~/Downloads/cde_demo_keypair.pem' are too open.
     It is required that your private key files are NOT accessible by others.
     This private key will be ignored.
     Load key "...": Bad permissions
     ubuntu@13.60.30.105: Permission denied (publickey).
     ```
   * **The Fix:** Strip all group and world permissions, making the key file readable only by your local user account:
     ```bash
     chmod 400 ~/Downloads/cde_demo_keypair.pem
     ```
   * Verify the file permissions:
     ```bash
     ls -la ~/Downloads/cde_demo_keypair.pem
     # Output must show: -r-------- (read-only by owner)
     ```

4. **Successful Shell Authentication:**
   * Re-execute the SSH command:
     ```bash
     ssh -i ~/Downloads/cde_demo_keypair.pem ubuntu@13.60.30.105
     ```
   * Type `yes` when prompted to accept the host authenticity fingerprint.
   * You are now securely logged into the remote cloud server:
     ```text
     Welcome to Ubuntu 24.04 LTS (GNU/Linux 6.8.0-1017-aws x86_64)
     ubuntu@ip-10-0-0-12:~$
     ```

### Demo 4: The Dynamic Public IP Trap vs. Elastic IP Allocation

#### Objective
Prove that restarting standard EC2 instances changes their public IP address and breaks external endpoints, then resolve the issue using an Elastic IP.

#### Step-by-Step Instructions

1. **Record the Current Public IP:**
   * Identify your active instance's public IPv4 address (e.g., `13.60.30.105`).
2. **Execute an Instance Stop:**
   * In the EC2 Console, select the instance $\rightarrow$ **Instance state** $\rightarrow$ **Stop instance**.
   * Confirm the stop action. Wait until the instance transitions to `Stopped`.
   * **Observation:** The **Public IPv4 address** field goes completely blank! The IP has been returned to the global AWS pool.
3. **Restart the Instance:**
   * Select the instance $\rightarrow$ **Instance state** $\rightarrow$ **Start instance**.
   * Wait until the instance state transitions back to `Running`.
   * **Observation:** Inspect the Public IPv4 address. It is now completely different (e.g., `16.171.24.151`). Any user or script relying on `13.60.30.105:8080` can no longer reach the server.
4. **Allocate and Associate an Elastic IP (The Permanent Fix):**
   * On the left menu under **Network & Security**, click **Elastic IPs**.
   * Click **Allocate Elastic IP address**.
   * Keep default settings (Amazon's pool of IPv4 addresses) and click **Allocate**.
   * Select the newly allocated Elastic IP $\rightarrow$ click **Actions** $\rightarrow$ **Associate Elastic IP address**.
   * **Resource type:** `Instance`.
   * **Instance:** Select your running instance (`Group_XX_demo_instance`).
   * **Private IP address:** Select the internal IP (`10.0.0.12`).
   * Click **Associate**.
5. **Verify Elasticity:**
   * Notice your instance now displays the Elastic IP as its public address.
   * Stop and restart the instance again.
   * **Result:** The public IP address remains fixed. External data pipelines, web clients, and firewall rules continue operating seamlessly.

### Demo 5: Subnet-Level Lockdown Using Network ACLs (NACLs)

#### Objective
Implement defense-in-depth by deploying a subnet-level stateless firewall and demonstrating how a NACL overrides Security Group rules.

#### Step-by-Step Instructions

1. **Inspect the Default NACL:**
   * Navigate to **VPC Console** $\rightarrow$ **Security** $\rightarrow$ **Network ACLs**.
   * Locate the default NACL associated with your VPC.
   * Inspect the Inbound Rules:
     * Rule `100` | Traffic: `All traffic` | Protocol: `All` | Range: `All` | Source: `0.0.0.0/0` | **ALLOW**.
     * Rule `*` | Traffic: `All traffic` | **DENY** (catch-all default).

2. **Create a Restrictive Custom NACL:**
   * Click **Create network ACL**.
   * **Name:** `Group_XX_block_all_nacl`.
   * **VPC:** Select `Group_XX_cde_bytes_vpc`.
   * Click **Create network ACL**.
   * *Notice:* A brand new custom NACL denies all traffic (`Rule *: DENY`) by default.

3. **Associate the Restrictive NACL with the Subnet:**
   * Select `Group_XX_block_all_nacl`.
   * Select the **Subnet associations** tab $\rightarrow$ **Edit subnet associations**.
   * Select `subnet_a` (where the instance is running).
   * Click **Save changes**.

4. **Test the Impact:**
   * Even though the Security Group permits inbound traffic on Port `8080` and Port `22`, attempt to refresh the Airflow UI or SSH into the server.
   * **Observation:** All connections fail immediately.
   * **Key Takeaway:** **NACLs govern the subnet boundary.** If a packet is denied at the NACL layer, it is discarded before it ever reaches the Security Group or the instance's ENI card.

5. **Revert to the Default NACL:**
   * Return to **Subnet associations** on the default VPC NACL.
   * Re-associate `subnet_a` with the default NACL to restore normal connectivity.

### Demo 6: Diagnosing Packet Drops with VPC Reachability Analyzer

#### Objective
Use declarative AWS networking diagnostics to trace traffic paths and automatically pinpoint misconfigured security policies.

#### Step-by-Step Instructions

1. **Simulate a Silent Failure:**
   * Navigate to **EC2** $\rightarrow$ **Security Groups**.
   * Edit the instance's inbound rules: delete the rule allowing traffic on Port `8080`.
   * Confirm the Airflow browser UI is hanging and unreachable.

2. **Create a Reachability Path:**
   * Open the **VPC Console**. Scroll down the left sidebar to **Network Analysis** $\rightarrow$ **Reachability Analyzer**.
   * Click **Create and analyze path**.
   * **Name:** `airflow-web-path-analysis`.
   * **Source type:** Select **Internet Gateways**.
   * **Source:** Select `Group_XX_cde_bytes_igw`.
   * **Destination type:** Select **Instances**.
   * **Destination:** Select your running EC2 instance.
   * **Protocol:** Select `TCP`.
   * **Destination port:** Enter `8080`.
   * Click **Create and analyze path**.

3. **Evaluate the Diagnostic Results:**
   * Wait 10 to 30 seconds for the analyzer execution state to change from `Pending` to `Completed`.
   * **Status:** Displays a clear red indicator: **`Not reachable`**.
   * Scroll down to **Explanations**:
     * The diagnostic report traces the packet path:
       * `Source: Internet Gateway` $\rightarrow$ **Passed** ✅
       * `Route Table Evaluation` $\rightarrow$ **Passed** ✅
       * `Network ACL (NACL)` $\rightarrow$ **Passed** ✅
       * `Security Group Rule Evaluation` $\rightarrow$ **FAILED** ❌
     * Exact Error Message:  
       *`No security group rule allows traffic from the source to the network interface eni-xxxxxxxx on port 8080.`*
   * **Conclusion:** The Reachability Analyzer eliminates guesswork by identifying the exact firewall layer blocking your data pipeline.

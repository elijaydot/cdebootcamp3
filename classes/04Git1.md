## Key topics covered

- What Git is and why use it
  - Git = distributed version control tool for tracking versions of files and enabling collaboration.
  - GitHub (and alternatives GitLab, Bitbucket) = remote hosting services for Git repositories.
  - Main benefits: versioning (snapshots), collaboration (concurrent work without blocking), ability to revert/fix mistakes, and audit/logging of changes.

- The four Git areas (core conceptual model)
  - Working directory (working tree): where files are edited on your machine.
  - Staging area (index): where changes are added (git add) before committing.
  - Local repository (.git): committed snapshots stored locally (git commit).
  - Remote repository (origin on GitHub/etc.): shared remote where pushes/pulls happen.
  - Ahmed repeatedly emphasized: every file/change exists in exactly one of these four places at any time.

- Basic Git workflow and important commands demonstrated
  - Setup, initialize: git init (creates .git directory)
  - Status and viewing: git status (check where you are), git log (view commit history), git log --oneline / git log --graph (brief and graphical views)
  - Staging: git add <file> or git add . (stage multiple/untracked files)
  - Commit: git commit -m "message"
  - Branching & switching: git checkout -b <branch-name> (create+switch) and git checkout <branch-name> (switch), git branch (list)
  - Fetch/pull/push:
    - git clone (first-time copy from remote to local)
    - git fetch vs git pull discussed (fetch gets updates from remote; pull typically fetch+merge; practical differences noted)
    - git push (send local commits/branches to remote); Ahmed demonstrated specifying upstream on first push
  - Undoing & history:
    - Mentioned git revert and other rollback methods (ability to fix mistakes via history)
  - Other useful commands mentioned: git remote, git diff (implied), git rm (to remove staged file)

- Branching and merging concepts
  - Branches are separate lines of work created from the main branch (main/master). Ahmed showed creating branches for feature work and switching between them.
  - Typical collaborative workflow: create branch from main → work on branch locally → push branch to remote → open pull request / merge on remote → update local main by pulling/merging.
  - Merge conflicts: cause, how they arise (concurrent edits to same area), and approach: stay calm, resolve by choosing appropriate changes, stage and commit resolution. Ahmed promised hands-on conflict resolution in the next practical session.
  - Naming note: master vs main (teams are moving from 'master' to 'main' as default naming).

- Fork vs Clone
  - Fork = copy of someone else's repository on your own remote account (GitHub) — useful when you want your own remote copy to modify before contributing back.
  - Clone = copy from a remote to your local machine.
  - Ahmed illustrated typical fork→clone→work→pull-request flow for contributing to third-party projects.

- Git hosting and team practices
  - Importance of pushing work regularly (so others can see progress); the use of draft PRs / branches to indicate in-progress work.
  - In production teams, direct pushes to main are usually restricted; merges to main are controlled (e.g., via pull requests, CI/CD, release branches).
  - Ahmed recommended using GitHub/GitLab/Bitbucket accounts and noted they’ll cover Git for Data Engineering and team workflows in the next class.

## Questions and answers (notable Q&A)

- Can Git work without GitHub?
  - Yes — Git works locally. GitHub/GitLab/Bitbucket are remote hosts for collaboration.
- Difference between git fetch and git pull?
  - git fetch downloads updates from remote (to local repository) without merging; git pull fetches and merges (convenience but can produce unexpected merges).
- Can a git add . stage multiple files?
  - Yes — git add . stages all changes (Ahmed cautioned on using it carelessly and explained selective adds are often better).
- Does Git track empty folders?
  - No — Git does not track empty directories; Git tracks files.
- Fork vs clone difference?
  - Fork duplicates a remote repo under your remote account (on GitHub) — clone pulls a remote repo to local machine.
- Merge conflict handling and how they occur:
  - Conflicts occur when changes to the same content overlap; resolve by inspecting conflicting blocks, choosing/combining changes, then add + commit resolution. Ahmed stressed staying calm and that conflicts are common.
- Who manages the main branch?
  - Depends on company policy. Proper teams restrict direct pushes to main; merges are controlled (reviewers/CI). Ahmed said next class will detail real-world protections/releases.

## Part 1: Warm-Up Quiz — Terraform Grammar & Resource Referencing Recap
*(Facilitated by Ayodeji Ajayi)*

The session opened with an interactive Slido quiz reinforcing Friday’s Terraform fundamentals:

1. **Arguments vs. Attributes:**
   * **Arguments:** Input parameters you supply inside a `.tf` resource block to define desired state (e.g., `bucket = "my-bucket"`).
   * **Attributes:** Output properties generated by AWS *after* the resource is created (e.g., `arn`, `id`, `endpoint`), which can be referenced dynamically by downstream resources.
2. **Resource Referencing vs. Data Blocks:**
   * **Resource Referencing (`aws_iam_access_key.user.secret`):** Used to pass attributes from a resource newly created within your current Terraform configuration.
   * **Data Sources (`data "aws_vpc" "existing"`):** Used to query and reference pre-existing infrastructure that was provisioned outside your current Terraform workspace.
3. **AWS Secrets Management Services:**
   * Distinguished between **AWS Systems Manager (SSM) Parameter Store** (`aws_ssm_parameter`) and **AWS Secrets Manager** for securely storing generated database credentials without hardcoding secrets in Git.

## Part 2: FinOps Governance — AWS Cost Allocation Tags

In production AWS accounts shared by dozens of engineers across multiple squads, viewing billing purely by AWS Service (e.g., *"EC2 cost \$400, RDS cost \$250"*) is useless for accountability—you cannot tell **which team or pipeline** burned the budget.

```
[ AWS Billing & Cost Explorer ]
         │
         ├── Default View (By Service):  EC2: $400 | RDS: $250 | DMS: $180  (Who spent it? Unknown!)
         │
         └── Tagged View (By Cost Allocation Tag):
               ├── Team = "Data Engineering" | Service = "Airflow"  ──► $120.50
               ├── Team = "Platform Squad"   | Service = "Atlantis" ──► $45.00
               └── Environment = "Staging"   | Owner = "Judith"     ──► $18.20
```

### How Enterprise Tagging Works in Terraform:
1. **Standardized Tagging Schema:** Every Terraform resource block must include a `tags` map defining organizational ownership:
   ```hcl
   tags = {
     Team        = "Data Engineering"
     Environment = "Production"
     Service     = "Airflow"
   }
   ```
2. **Activating Cost Allocation Tags in AWS:**
   * Simply adding tags in Terraform does not immediately make them filterable in billing reports.
   * Administrators must navigate to **AWS Billing and Cost Management** $\rightarrow$ **Cost Allocation Tags** and click **Activate** on user-defined tag keys (`Team`, `Environment`, `Service`).
3. **Cost Explorer Auditing:** Once active, leads can filter **AWS Cost Explorer** by `Dimension: Tag` to pinpoint exact daily/monthly spending per squad and application—with **zero extra AWS charges** for using tags.

## Part 3: Remote State Management (`S3 Backend`) & State Locking

Storing `terraform.tfstate` ("The Brain") on a single engineer's laptop works for solo learning, but causes immediate disaster in team environments:
* If your laptop crashes, the state file is lost.
* If two engineers run `terraform apply` at the exact same second against the same state file, **concurrent writes corrupt `terraform.tfstate`**.

```
[ Engineer A: terraform apply ] ──(Acquires Lock)──► [ Remote S3 Backend Bucket ]
                                                     ├── File: production/production.tfstate
[ Engineer B: terraform apply ] ──❌ BLOCKED! ──────► └── Lock: production.tfstate.tflock
                                                         ("State locked by Engineer A!")
```

### 1. The Remote S3 Backend Pattern:
* **Bootstrap Step:** You must manually create one dedicated, version-enabled S3 bucket first (the "chicken-and-egg" prerequisite, since Terraform needs the bucket to exist before storing its own state inside it).
* **Backend Configuration Block (`backend.tf`):** Instructs Terraform Core to read and write state directly to S3 rather than local disk.

### 2. Native S3 State Locking (`use_lockfile = true`):
* Historically, AWS required pairing an S3 bucket with an **Amazon DynamoDB** table to handle state locking.
* Modern Terraform (`v1.10+` / AWS Provider `v6+`) supports **native S3 lock files** via the `use_lockfile = true` argument inside the `s3` backend block.
* When Engineer A runs `terraform apply`, Terraform writes a temporary `.tflock` file in S3. If Engineer B attempts an `apply` simultaneously, Terraform blocks Engineer B until Engineer A's operation completes and releases the lock.

> 🔗 **Official Terraform Docs:** [Terraform S3 Backend & State Locking](https://developer.hashicorp.com/terraform/language/backend/s3)

## Part 4: Enterprise Repository Architecture & Multi-Provider Secrets

Rather than dumping 1,000 lines of HCL into a single `main.tf` file, production repositories separate environments into directories and split infrastructure by **workload/service** so deprecating a tool is as clean as deleting or commenting out one file:

```
production-terraform-repo/
├── production/
│   ├── backend.tf          # S3 remote state & AWS/Random provider declarations
│   ├── datalake.tf         # S3 buckets for raw/silver/gold data lake layers
│   └── airbyte.tf          # Dedicated RDS Postgres DB + Random Password + SSM Parameter
└── staging/
    ├── backend.tf
    ├── datalake.tf
    └── airbyte.tf
```

### Multi-Provider Secret Chaining (Zero Hardcoded Passwords!):
To provision an **Amazon RDS PostgreSQL** database without hardcoding a password in Git:
1. **`random_password` (from `hashicorp/random` provider):** Generates a cryptographically strong 24-character password in memory during execution.
2. **`aws_ssm_parameter` (from `hashicorp/aws` provider):** Automatically saves that generated password securely into **AWS Systems Manager Parameter Store** under a structured path (e.g., `/production/data-engineering/airbyte/rds-password`) so engineers can retrieve it safely from the AWS Console when needed.
3. **`aws_db_instance` (from `hashicorp/aws` provider):** References `random_password.airbyte_db_password.result` directly as its master password.
4. **Automatic Dependency Graph:** Because `aws_ssm_parameter` and `aws_db_instance` reference `random_password`, Terraform Core automatically knows it **must** generate the password first before creating the parameter or database—no manual `depends_on` meta-arguments required!

## Part 5: Essential Terraform Code Quality & Teardown Commands

Before pushing `.tf` code to GitHub, engineers run two built-in CLI hygiene commands (also enforced automatically in CI/CD pipelines):

1. **`terraform fmt` (Format):**
   * Automatically rewrites `.tf` files to canonical HashiCorp style, fixing messy indentation, spacing, and aligning `=` signs cleanly.
2. **`terraform validate` (Syntax & Logic Check):**
   * Validates HCL syntax, checks for unclosed curly braces `{}`, and verifies that all resource types and argument names actually exist in the provider schema—all locally without touching AWS APIs.
3. **Surgical Deletion vs. `terraform destroy`:**
   * **Avoid `terraform destroy` in shared production workspaces!** Running `terraform destroy` wipes out *every single resource* tracked in that state file, including infrastructure owned by other team members.
   * **Safe Production Deletion:** Comment out (`# ... #`) or delete *only* the specific resource block you wish to decommission in its `.tf` file, then run `terraform plan` and `terraform apply` to destroy strictly that resource.

## Part 6: Enterprise GitOps Workflow with Atlantis

Mayowa demonstrated how real-world data platform teams enforce peer review, visibility, and auditability using **GitHub** and **Atlantis** (an open-source Terraform pull request automation server running on Kubernetes/EC2):

```
[ Engineer Laptop ]
   │  1. git checkout -b feat/add-bucket
   │  2. Write HCL in datalake.tf & git push
   ▼
[ GitHub Pull Request (Main Branch Protected) ]
   │  3. Webhook triggers Atlantis Server automatically
   ▼
[ Atlantis Automation Server ]
   │  4. Clones repo, runs `terraform init` & `terraform plan`
   │  5. Locks remote state & posts plan diff directly into PR comments!
   ▼
[ Senior Lead / Peer Reviewer ]
   │  6. Inspects `terraform plan` output inside GitHub PR
   │  7. Clicks "Approve" on the Pull Request
   ▼
[ Engineer Comments: `atlantis apply` on PR ]
   │  8. Atlantis verifies PR approval, executes `terraform apply`,
   │     provisions live AWS resources, releases lock & merges PR to `main`!
```

### Why Enterprise Teams Use Atlantis:
* **No Local `apply` Privileges:** Human engineers have `ReadOnlyAccess` in the AWS Console and cannot run `terraform apply` locally.
* **Mandatory Peer Review:** Atlantis blocks `atlantis apply` until at least one authorized reviewer officially approves the Pull Request on GitHub.
* **Built-In Audit Trail & Concurrency Locking:** Every infrastructure change is permanently logged in GitHub PR history alongside who wrote it, who reviewed it, the exact `terraform plan` output, and who triggered `atlantis apply`.

> 🔗 **Official Atlantis Docs:** [RunAtlantis.io — Terraform Pull Request Automation](https://www.runatlantis.io/docs/)

### Demo 1: Configuring Remote S3 State Backend & FinOps Cost Tags

#### Objective:
Create a versioned S3 bucket to host remote Terraform state, structure a production directory layout (`backend.tf` and `datalake.tf`), enable native S3 state locking (`use_lockfile = true`), and deploy a FinOps-tagged S3 bucket.

#### Step-by-Step Instructions:

##### Step 1: Manually Bootstrap the Remote State S3 Bucket
1. Log in to the **AWS Management Console** $\rightarrow$ Navigate to **Amazon S3** $\rightarrow$ Click **Create bucket**.
2. **Bucket name:** `cde-data-engineering-statefile-2026` *(must be globally unique)*.
3. **AWS Region:** `eu-north-1` (Stockholm) *(or your designated region)*.
4. **Bucket Versioning:** Select **Enable** *(critical so you can recover previous `terraform.tfstate` versions if state ever gets corrupted)*.
5. Leave **Block all public access** enabled $\rightarrow$ Click **Create bucket**.

##### Step 2: Initialize the Production Project Directory
Open your terminal and create a clean workspace:
```bash
mkdir production-setup
cd production-setup
mkdir production staging
code .
```

##### Step 3: Configure Providers & S3 Remote Backend (`production/backend.tf`)
Inside `production/`, create a file named `backend.tf` and add:
```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }

  backend "s3" {
    bucket       = "cde-data-engineering-statefile-2026"
    key          = "production/production.tfstate"
    region       = "eu-north-1"
    use_lockfile = true
  }
}

provider "aws" {
  region = "eu-north-1"
}
```

##### Step 4: Initialize the Remote Backend
In your terminal, navigate into the `production/` folder and run `terraform init`:
```bash
cd production
terraform init
```
* **Expected Output:**
  `Initializing the backend... Successfully configured the backend "s3"! Terraform will automatically use this backend unless the backend configuration changes.`

##### Step 5: Define a Tagged Data Lake Bucket (`production/datalake.tf`)
Create `production/datalake.tf` and define an S3 bucket with full FinOps Cost Allocation Tags:
```hcl
resource "aws_s3_bucket" "ingestion" {
  bucket = "cde-test-bucket-tagged-2026"

  tags = {
    Team        = "Data Engineering"
    Environment = "Production"
    Service     = "Airflow"
  }
}
```

##### Step 6: Plan, Apply, and Verify Remote State in S3
```bash
terraform plan
terraform apply
```
* Type `yes` when prompted.
* **Verification:**
  1. Check your local `production/` folder in VS Code: **no `terraform.tfstate` file exists locally!**
  2. Open the **AWS S3 Console** $\rightarrow$ Open `cde-data-engineering-statefile-2026` $\rightarrow$ Click into the `production/` folder $\rightarrow$ `production.tfstate` is safely stored in the cloud!

### Demo 2: Multi-Provider Secret Generation & Provisioning RDS PostgreSQL (`airbyte.tf`)

#### Objective:
Dynamically generate a 24-character database password using the `random` provider, store it securely in **AWS Systems Manager (SSM) Parameter Store**, and launch an **Amazon RDS PostgreSQL 18** database referencing that password—without hardcoding a single secret.

#### Step-by-Step Instructions:

##### Step 1: Create `production/airbyte.tf`
Inside `production/`, create `airbyte.tf` and add the three linked resource blocks:
```hcl
# 1. Generate a secure 24-character random password
resource "random_password" "airbyte_db_password" {
  length           = 24
  special          = false
  override_special = "!%@"
}

# 2. Store the generated password in AWS SSM Parameter Store
# Note: Hierarchical parameter names MUST start with a forward slash "/"
resource "aws_ssm_parameter" "airbyte_rds_password" {
  name  = "/production/data-engineering/airbyte/rds-password"
  type  = "SecureString"
  value = random_password.airbyte_db_password.result

  tags = {
    Team        = "Data Engineering"
    Environment = "Production"
    Service     = "Airbyte"
  }
}

# 3. Provision the RDS PostgreSQL Database Instance
resource "aws_db_instance" "airbyte_db" {
  identifier           = "cde-new-db"
  allocated_storage    = 20
  db_name              = "airbyte"
  engine               = "postgres"
  engine_version       = "18"
  instance_class       = "db.t3.micro"
  username             = "airbyte"
  password             = random_password.airbyte_db_password.result
  skip_final_snapshot  = true

  tags = {
    Team        = "Data Engineering"
    Environment = "Production"
    Service     = "Airbyte"
  }
}
```

##### Step 2: Format, Validate, and Apply
Run Terraform's code quality gates before provisioning:
```bash
terraform fmt        # Auto-formats HCL indentation and alignment
terraform validate   # Verifies syntax and resource attribute validity
terraform plan       # Previews all 3 resources to be added
terraform apply      # Provisions password, SSM parameter, and RDS instance
```
* Type `yes` and wait ~4–5 minutes for RDS provisioning to complete.

##### Step 3: Retrieve the Generated Password from AWS SSM Console
1. Open the **AWS Management Console** $\rightarrow$ Search for **Systems Manager** $\rightarrow$ In the left menu under **Application Management**, click **Parameter Store**.
2. Click on `/production/data-engineering/airbyte/rds-password`.
3. Under **Value**, click **Show** to reveal the exact 24-character password generated by Terraform.
4. Open the **Amazon RDS Console** $\rightarrow$ **Databases** $\rightarrow$ Confirm `cde-new-db` is `Available` with all tags attached.

## Part 9: Infrastructure Teardown & Clean-Up Checklist

To avoid ongoing RDS and storage charges, follow the **surgical teardown** procedure demonstrated in class:

1. **Comment Out Resources in `.tf` Files (Do NOT run `terraform destroy`):**
   * Open `production/airbyte.tf` and `production/datalake.tf` in VS Code.
   * Select all resource blocks (`random_password`, `aws_ssm_parameter`, `aws_db_instance`, `aws_s3_bucket`) and comment them out using `Ctrl + /` (or `Cmd + /` on Mac).
   * *Keep `backend.tf` untouched so Terraform still knows how to connect to your remote S3 state file!*
2. **Apply the Surgical Removal:**
   ```bash
   terraform plan    # Verify: Plan: 0 to add, 0 to change, 4 to destroy
   terraform apply   # Type 'yes' to cleanly delete the RDS DB, SSM param, and test bucket
   ```
3. **Manually Clean Up the Bootstrap State Bucket (Optional):**
   * Once all Terraform-managed resources are destroyed, open the **AWS S3 Console**, empty `cde-data-engineering-statefile-2026` (including all object versions), and delete the bucket.

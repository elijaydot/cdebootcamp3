## 1. Quick Recap: Relational Normalization & The Parch & Posey Schema
The dataset models a commercial paper supply enterprise with 5 interconnected tables:
1. **`web_events`**: Tracks user traffic (`id`, `account_id`, `occurred_at`, `channel` [direct, Facebook, organic, AdWords, banner, Twitter]).
2. **`accounts`**: Stores client organizations (`id`, `name`, `website`, `lat`, `long`, `primary_poc`, `sales_rep_id`).
3. **`sales_reps`**: Maps representatives (`id`, `name`, `region_id`).
4. **`region`**: Stores territories (`id`, `name` [Northeast, Midwest, Southeast, West]).
5. **`orders`**: Transactional facts (`id`, `account_id`, `occurred_at`, quantities [`standard_qty`, `gloss_qty`, `poster_qty`, `total`], amounts [`standard_amt_usd`, `gloss_amt_usd`, `poster_amt_usd`, `total_amt_usd`]).

> **Why Normalize?** Storing text strings like `'Walmart'` repeatedly across 50,000 order rows consumes massive storage (each character takes bytes). Storing an integer foreign key `account_id = 1001` (4 bytes) and looking up `'Walmart'` once in the `accounts` table dramatically reduces disk footprint and eliminates data anomalies.

## 2. Core DQL Syntax: The `SELECT` Statement & Projections
The `SELECT` statement retrieves rows and columns from database tables:
```sql
-- Projecting all columns (Full table scan)
SELECT * FROM dbo.web_events;

-- Projecting specific columns (Reduces I/O bandwidth)
SELECT occurred_at, account_id, channel 
FROM dbo.web_events;
```
* **Schema Resolution:** Omitting the schema defaults to `dbo` (e.g., `FROM orders` evaluates to `FROM dbo.orders`). Explicit schema qualification (`dbo.orders`) is best practice in enterprise environments.

## 3. The Filtering Engine: `WHERE` Clause & Comparison Operators

The `WHERE` clause filters rows **before** any grouping or aggregation takes place.

### A. Equality & Range Operators
```sql
-- Filtering text / categorical data
SELECT name, website, primary_poc 
FROM dbo.accounts 
WHERE name = 'Apple';

-- Numeric comparison: Orders with total amount >= $1,000
SELECT * 
FROM dbo.orders 
WHERE total_amt_usd >= 1000;

-- Inequality / Negation
SELECT * FROM dbo.orders WHERE total_amt_usd <> 0; -- or !=
```

### B. Logical Operators (`AND`, `OR`, `NOT`) & Parenthesis Safety
When combining multiple conditions, operator precedence requires careful grouping with parentheses:
```sql
-- Retrieve web events from 2016 coming strictly from organic or AdWords channels
SELECT occurred_at, account_id, channel 
FROM dbo.web_events
WHERE (occurred_at >= '2016-01-01' AND occurred_at < '2017-01-01')
  AND channel IN ('organic', 'adwords');
```
* **Best Practice:** Always wrap compound logical expressions in parentheses `(...)` so the query parser evaluates sub-clauses in the intended order rather than misinterpreting `AND`/`OR` precedence.

### C. Continuous Range Filtering: `BETWEEN` vs. Comparison Operators
* **`BETWEEN low AND high` is strictly inclusive** of both boundaries (`>= low AND <= high`).
```sql
-- These two queries are mathematically equivalent:
SELECT * FROM dbo.orders WHERE total BETWEEN 500 AND 600;
SELECT * FROM dbo.orders WHERE total >= 500 AND total <= 600;

-- For strict boundary exclusion (501 to 599):
SELECT * FROM dbo.orders WHERE total > 500 AND total < 600;
-- or:
SELECT * FROM dbo.orders WHERE total BETWEEN 501 AND 599;
```

### D. Set Membership: `IN` vs. `NOT IN`
```sql
-- Filtering for multiple accounts
SELECT name, primary_poc, sales_rep_id 
FROM dbo.accounts 
WHERE name IN ('Walmart', 'Target', 'Nordstrom');

-- Negating the set (excluding accounts)
SELECT name, primary_poc, sales_rep_id 
FROM dbo.accounts 
WHERE name NOT IN ('Walmart', 'Target', 'Nordstrom');
```

## 4. Pattern Matching & Wildcards (`LIKE` / `NOT LIKE`)

Wildcards enable string search across text columns:
* `%` matches **zero, one, or multiple characters**.
* `_` matches **exactly one character**.

| Pattern Syntax | Meaning | Example Match | Example SQL Snippet |
| :--- | :--- | :--- | :--- |
| `'C%'` | Starts with 'C' | *Citigroup, Cisco* | `WHERE name LIKE 'C%'` |
| `'%s'` | Ends with 's' | *Apple Inc., Starbucks* | `WHERE name LIKE '%s'` |
| `'%one%'` | Contains 'one' anywhere | *Honeywell, Stone Inc.* | `WHERE name LIKE '%one%'` |
| `'NOT LIKE %one%'` | Does NOT contain 'one' | *Walmart, Target* | `WHERE name NOT LIKE '%one%'` |

## 5. Critical Distinction: `NULL` vs. `0` / Empty Strings
* **`NULL`** represents unknown, unrecorded, or missing data. It has no value.
* **`0`** is an explicit numeric scalar quantity (e.g., $0 paid).
* **Evaluation Rule:** You **cannot** use `= NULL` or `<> NULL` because `NULL` cannot be equal to anything (even another `NULL`). You **must use `IS NULL` or `IS NOT NULL`**.
```sql
-- Correct way to find missing poster quantities
SELECT * FROM dbo.orders WHERE poster_qty IS NULL;

-- Querying explicit zero-dollar orders
SELECT * FROM dbo.orders WHERE poster_amt_usd = 0;
```

## 6. Sorting & Limiting Result Sets (`ORDER BY`, `TOP`, `LIMIT`)

### Multi-Column Sorting Hierarchy
When multiple columns are specified in `ORDER BY`, the database sorts by the first column, then breaks ties by sorting subsequent columns:
```sql
-- Sort orders by account_id ascending, then by total spend descending
SELECT id, account_id, total_amt_usd 
FROM dbo.orders 
ORDER BY account_id ASC, total_amt_usd DESC;
```

### Top-N Analysis & Dialect Variations
```sql
-- Microsoft SQL Server (T-SQL)
SELECT TOP 10 account_id, total_amt_usd 
FROM dbo.orders 
ORDER BY total_amt_usd DESC;

-- PostgreSQL / MySQL Equivalent
SELECT account_id, total_amt_usd 
FROM dbo.orders 
ORDER BY total_amt_usd DESC 
LIMIT 10;
```

## 7. Date Engineering & Time Series Extraction

| Function | Dialect / Engine | Description | Example Output (`2016-03-15 14:30:00`) |
| :--- | :--- | :--- | :--- |
| `YEAR(date)` | T-SQL / Standard | Extracts numeric calendar year | `2016` |
| `MONTH(date)` | T-SQL / Standard | Extracts numeric calendar month (1-12) | `3` |
| `DAY(date)` | T-SQL / Standard | Extracts day of month (1-31) | `15` |
| `DATEPART(part, date)` | T-SQL | Extracts integer date component | `DATEPART(month, occurred_at) -> 3` |
| `DATE_TRUNC('month', date)` | PostgreSQL / T-SQL modern | Truncates timestamp down to start of period | `2016-03-01 00:00:00` |

### Analytical Nuance: `DATEPART` vs. `DATE_TRUNC`
* **`DATEPART(month, occurred_at)` / `MONTH()`:** Returns pure month numbers (`1` to `12`). If you group sales by `MONTH()`, it will lump **January 2014, January 2015, and January 2016 together into a single "Month 1" bucket** (useful for seasonal analysis, misleading for chronological trends).
* **`DATE_TRUNC('month', occurred_at)`:** Truncates to `2014-01-01`, `2015-01-01`, and `2016-01-01` separately, preserving true continuous monthly time series.

## 8. The Engine Under the Hood: Logical Query Execution Order

Why did `WHERE order_year = 2016` throw an error when using an alias, but `ORDER BY order_year DESC` worked perfectly?

```
Written Order (Syntax)             Execution Order (Database Engine)
-----------------------            ---------------------------------
1. SELECT                          1. FROM & JOINs (Identify data source)
2. FROM                            2. WHERE (Row-level filtering)
3. WHERE                           3. GROUP BY (Aggregate into partitions)
4. GROUP BY                        4. HAVING (Filter aggregated partitions)
5. HAVING                          5. SELECT & Aliasing (Calculate expressions)
6. ORDER BY                        6. ORDER BY (Sort final projection)
7. TOP / LIMIT                     7. TOP / LIMIT (Truncate output)
```

* **The Alias Trap:** The `WHERE` clause executes at **Step 2**, long before `SELECT` creates the alias at **Step 5**. Thus, `WHERE` does not know the alias exists.
* **Why `ORDER BY` Works:** `ORDER BY` executes at **Step 6**, after `SELECT` has assigned aliases, allowing alias referencing.

## 9. The Core Architectural Battle: `WHERE` vs. `HAVING`

```
┌────────────────────────────────────────────────────────┐
│                      RAW TABLE                         │
└────────────────────────────────────────────────────────┘
                           │
                           ▼
              [ 1. WHERE Clause Filters ]  <-- Filters individual rows FIRST
                           │
                           ▼
              [ 2. GROUP BY Partitions ]   <-- Groups remaining rows
                           │
                           ▼
              [ 3. Aggregations (SUM) ]    <-- Computes scalar aggregates
                           │
                           ▼
              [ 4. HAVING Clause Filters]  <-- Filters aggregated group partitions
```

| Dimension | `WHERE` Clause | `HAVING` Clause |
| :--- | :--- | :--- |
| **Execution Point** | **Before** `GROUP BY` and aggregations. | **After** `GROUP BY` and aggregations. |
| **Level of Granularity** | **Row-level filtering.** | **Partition / Aggregate-level filtering.** |
| **Aggregate Functions** | **Cannot** contain aggregate functions (`WHERE SUM(total) > 100` $
ightarrow$ **ERROR**). | **Can** contain aggregate functions (`HAVING SUM(total) > 100`). |
| **Query Performance** | **High Performance:** Prunes unneeded rows early, reducing data sent to memory/CPU. | **Higher Overhead:** Aggregates all data first before discarding groups. |

### Performance Comparison:
```sql
-- OPTION A: High Performance (Pre-filtering with WHERE)
-- Filters rows to 2016 first, then computes SUM on that subset
SELECT YEAR(occurred_at) AS order_year, SUM(total_amt_usd) AS total_revenue
FROM dbo.orders
WHERE occurred_at >= '2016-01-01' AND occurred_at < '2017-01-01'
GROUP BY YEAR(occurred_at);

-- OPTION B: Suboptimal (Post-filtering with HAVING)
-- Computes SUM across the entire history of the company (2013-2020), then discards non-2016 years
SELECT YEAR(occurred_at) AS order_year, SUM(total_amt_usd) AS total_revenue
FROM dbo.orders
GROUP BY YEAR(occurred_at)
HAVING YEAR(occurred_at) = 2016;
```
* **Golden Optimization Rule:** Always filter row-level attributes with `WHERE` as early as possible. Reserve `HAVING` exclusively for conditions that depend on calculated aggregate values (e.g., `HAVING SUM(total_amt_usd) > 500000`).

## 11. Student Q&A & Key Takeaways
* **Q: Why does `HAVING` not work without `GROUP BY`?**
  * *A:* `HAVING` operates on grouped partitions. Without grouping, filtering must occur on raw individual rows using `WHERE`.
* **Q: Is SQL identical across PostgreSQL, SQL Server, and Snowflake?**
  * *A:* 85–90% of core SQL (`SELECT`, `WHERE`, `GROUP BY`, `JOIN`) follows ANSI standards and is identical. Dialect differences occur in procedural code (T-SQL vs. PL/pgSQL), specific date functions (`DATE_TRUNC` vs. `DATEPART`), and limiting keywords (`TOP` vs. `LIMIT`).
* **Q: How should I approach SQL optimization?**
  * *A:* First master business logic translation—know which questions to ask and how to write correct queries. Once fluent, study the logical execution order, indexing, and I/O execution plans.

This masterclass marked the transition from theoretical data modeling to a practical, modern analytics engineering workflow. The session covered:

2. The difference between operational and analytical data systems.
3. The move from traditional ETL to cloud-native ELT.
4. Reproducible Python and dependency management with Astral `uv`.
5. dbt project initialization and the purpose of each native dbt directory.
6. Medallion-style organization using staging, intermediate, and marts layers.
7. Multi-environment Databricks profiles using YAML anchors and environment variables.

9. Unity Catalog setup with catalogs and schemas.
10. Preparation for CI/CD, data testing, observability, and the first live dbt execution.

The main idea is that dbt brings software engineering practices to SQL transformations. It makes warehouse logic modular, version-controlled, reusable, testable, documented, and deployable without moving the underlying data out of the warehouse.

## 2. From Data Modeling to Analytics Engineering

### 2.1 Modeling progression

The class reviewed the three major stages of data modeling:

- **Conceptual modeling:** Describes high-level business entities and their relationships.
- **Logical modeling:** Defines attributes, keys, and relationships without committing to a particular database technology.
- **Physical modeling:** Implements tables, columns, constraints, indexes, partitions, and storage decisions in a specific platform.

### 2.2 OLTP and OLAP

Operational systems and analytical systems have different goals:

- **OLTP systems** support frequent inserts and updates for day-to-day business transactions. They commonly use normalized relational designs, often through Third Normal Form (3NF), to reduce duplication and maintain transactional integrity.
- **OLAP systems** support reporting, aggregation, trend analysis, and business intelligence. They commonly use dimensional models such as star or snowflake schemas.

In dimensional modeling:

- **Fact tables** contain measurable business events, metrics, and foreign keys.
- **Dimension tables** contain descriptive business context such as customers, products, dates, locations, and channels.

dbt provides the implementation layer that converts warehouse source data into these trusted analytical structures.

## 3. The Architectural Shift from ETL to ELT

### 3.1 Architecture comparison chart

```text
LEGACY ETL PIPELINE (Extract -> Transform -> Load)

+-------------+       +-----------------------------+       +-----------------------+
| Source OLTP | ----> | External transform engine   | ----> | Target data warehouse |
| PostgreSQL  |       | Middleware / VMs / scripts  |       | Final report data     |
+-------------+       +-----------------------------+       +-----------------------+
	Extract                 Transform                           Load

MODERN ELT WITH dbt (Extract -> Load -> Transform)

+----------------------+       +------------------------------------------------------+
| OLTP databases,      | ----> | CLOUD LAKEHOUSE / WAREHOUSE                         |
| APIs, and files      | Raw   | Databricks / Snowflake / BigQuery                   |
+----------------------+ load  |                                                      |
	  Extract                | +------------+    +-------------+    +-------------+ |
						| | Bronze/raw | -> | Silver/clean| -> | Gold/marts  | |
						| +------------+    +-------------+    +-------------+ |
						|                          ^                  ^          |
						|                          +------ dbt -------+          |
						+------------------------------------------------------+
```

| Comparison | Traditional ETL | Modern ELT with dbt |
|---|---|---|
| Order | Extract, transform, then load | Extract, load, then transform |
| Transformation location | External middleware, VMs, or source systems | Inside the cloud lakehouse or warehouse |
| Data loaded | Primarily preprocessed data | Raw data first, then curated data |
| Compute model | Separate transformation infrastructure | Elastic warehouse or lakehouse compute |
| Common limitation | Pipeline and network bottlenecks | Requires governance of raw and transformed layers |
| dbt's role | Usually limited or absent | Compiles and orchestrates in-engine SQL transformations |

### 3.2 Traditional ETL

In an ETL pipeline, transformation happens before data reaches the destination warehouse:

```text
[Source] -> Extract -> [External transformation engine] -> Transform -> Load -> [Warehouse]
```

This approach can create bottlenecks because transformation compute lives in middleware, virtual machines, or source systems. It may also require data to cross network boundaries several times before it is ready for reporting.

### 3.3 Modern ELT

In an ELT pipeline, raw data is loaded first and transformed inside the cloud platform:

```text
[OLTP databases / APIs / files]
							|
							| Extract and load with CDC, Airbyte, Fivetran, or another ingestion tool
							v
[Cloud lakehouse or warehouse]
		Bronze/raw -> Silver/clean -> Gold/marts
										^               ^
										+---- dbt ------+
```

Cloud platforms such as Databricks, Snowflake, and BigQuery separate storage from compute and provide elastic, massively parallel processing. This makes it practical to run transformations where the data already lives.

### 3.4 What dbt does

dbt does not extract, transport, or store data itself. It:

1. Reads modular SQL and Jinja files.
2. Resolves dependencies between models.
3. Compiles model code into the target platform's SQL dialect.
4. Generates statements such as `CREATE VIEW`, `CREATE TABLE AS SELECT`, or `MERGE INTO`.
5. Sends those statements to the Databricks SQL Warehouse for execution.

This pushdown model uses Databricks compute instead of a separate transformation engine.

## 4. Repository and Environment Setup with `uv`

Astral `uv` was introduced as a fast Python package and project manager that can replace a combination of `pip`, `venv`, and Poetry for this workflow. It provides deterministic dependencies through a lock file and gives Windows, macOS, and Linux users a consistent project environment.

### 4.1 Clone and open the repository

```bash
git clone <YOUR_GITHUB_REPO_URL>
cd cdc_modelling
```

The repository used in class was named `cdc_modelling`. It was cloned locally and opened in Visual Studio Code.

### 4.2 Initialize a minimal Python project

```bash
uv init --bare --name cdc_modelling --python 3.11
```

- `--bare` creates a minimal project without template application files.
- `--name` sets the project name.
- `--python 3.11` pins the intended Python runtime.
- The command creates `pyproject.toml`.

### 4.3 Install the Databricks adapter

```bash
uv add dbt-databricks
```

Installing an adapter also installs the compatible dbt Core dependencies. The adapter determines the SQL dialect and connection behavior for the target platform.

As clarified in response to questions from John Babatunde and Mercy Abaraonye, other platforms require their corresponding adapters:

```bash
uv add dbt-snowflake
uv add dbt-bigquery
```

### 4.4 Optional observability with Elementary

The session also explored Elementary, a dbt-native observability framework that can track test failures, schema changes, and model behavior and can send alerts to systems such as Slack:

```bash
uv add 'elementary-data[databricks]~=0.22.0'
```

Some learners experienced network timeouts and slow native-package builds. Elementary was therefore deferred so that dependency discrepancies would not block the core dbt setup.

### 4.5 Initialize the dbt project

```bash
uv run dbt init cdc_marketing --skip-profile-setup
```

The `--skip-profile-setup` option bypasses dbt's interactive creation of a basic user profile in `~/.dbt/profiles.yml`. This allowed the class to build a repository-based, multi-target profile designed for local development, CI, staging, and production.

### Why `--skip-profile-setup`?
When running standard `dbt init`, the CLI prompts users interactively for hostnames, tokens, and schemas, automatically generating a rudimentary, single-user profile in `~/.dbt/profiles.yml` . Skipping this allowed the class to construct an enterprise-grade, multi-environment profile within the repository root .

After initialization, the expected top-level structure is:

```text
cdc_modelling/
|-- .venv/                 # uv-managed environment; do not commit
|-- pyproject.toml         # project metadata and dependencies
|-- uv.lock                # resolved dependency lock file
`-- cdc_marketing/         # dbt project root
		|-- dbt_project.yml
		|-- profiles.yml
		|-- analyses/
		|-- macros/
		|-- models/
		|-- seeds/
		|-- snapshots/
		`-- tests/
```

## 5. Anatomy of a dbt Project

### 5.1 Directory reference table

| Directory | Purpose | Enterprise best practice and real-world usage |
|---|---|---|
| `models/` | Contains transformation SQL materialized as views, tables, incremental models, or ephemeral models. | Organize models into `staging/` for source-aligned cleaning, `intermediate/` for reusable joins and business logic, and `marts/` for facts, dimensions, and consumer-ready Gold models. |
| `macros/` | Stores reusable Jinja-templated SQL logic. | Apply DRY principles to repeated mappings and calculations, and implement project-level overrides such as dynamic schema or database naming. |
| `seeds/` | Stores small, static CSV reference datasets loaded by dbt. | Use for stable lookup and mapping data, generally fewer than about 1,000 rows. Never store rapidly changing transactions, credentials, or sensitive data. |
| `snapshots/` | Captures historical versions of mutable source records. | Implement Type 2 Slowly Changing Dimensions with validity timestamps and either timestamp-based or check-based change detection. |
| `tests/` | Contains reusable and custom data quality assertions. | Use generic YAML tests such as `unique`, `not_null`, `relationships`, and `accepted_values`, plus singular SQL tests that fail when they return rows. |
| `analyses/` | Holds ad hoc SQL that can use dbt compilation context without normal model materialization. | Use as a query scratchpad or a version-controlled archive for legacy logic that must not run in scheduled model builds. |


```text
cdc_modelling/ (Git Root)
├── .venv/                     # uv-managed virtual environment (Git-ignored)
├── pyproject.toml             # uv package dependencies
├── uv.lock                    # Cryptographic dependency lockfile
└── cdc_marketing/             # dbt Project Root
    ├── dbt_project.yml        # Main project configuration & metadata
    ├── profiles.yml           # Database connection & authentication credentials
    ├── analyses/              # Ad-hoc & legacy analytical queries (not compiled to DB)
    ├── macros/                # Reusable Jinja logic & functions (DRY principle)
    ├── models/                # Core SQL transformation logic
    │   ├── staging/           # Raw cleans, 1:1 with source (Bronze -> Silver)
    │   ├── intermediate/      # Complex multi-table business joins
    │   └── marts/             # Final dimensional models: Facts & Dims (Gold)
    ├── seeds/                 # Static version-controlled CSV files (lookups/mappings)
    ├── snapshots/             # Type-2 Slowly Changing Dimensions (SCD Type 2)
    └── tests/                 # Data quality validations
        ├── generic/           # Reusable tests (unique, not_null)
        └── singular/          # Custom SQL assertion scripts
```

### 5.2 `dbt_project.yml`

This is the main project configuration file. It defines the dbt project name, file paths, model configuration, and project-level behavior.

The profile name referenced by the project must match the root key in `profiles.yml`. The repository was initially called `cdc_modelling`, while the dbt project was created as `cdc_marketing`; these names serve different purposes and do not have to match. However, the `profile:` setting and the profile's root key must agree.

### 5.3 `models/`

The `models/` directory contains the main transformation queries. Each model is normally a `SELECT` statement that dbt materializes as a view, table, incremental model, or ephemeral model according to configuration.

The recommended structure follows the transformation flow:

```text
models/
|-- staging/
|-- intermediate/
`-- marts/
```

#### Staging

Staging models are the first dbt-managed layer over raw source data. They generally maintain a one-to-one relationship with source tables and perform lightweight cleanup:

- Rename columns consistently.
- Cast data types.
- Standardize values.
- Select required fields.
- Filter hard-deleted or unusable records.

In a broad Medallion mapping, staging is the bridge from Bronze raw data toward clean Silver data. It should not contain heavy business joins.

#### Intermediate

Intermediate models isolate reusable business logic between staging and final marts. They may:

- Join several staging models.
- Resolve entities.
- Deduplicate business records.
- Calculate reusable fields.
- Prepare wide business entities.

#### Marts

Marts are curated Gold-layer models intended for consumers such as Power BI, Tableau, analysts, and machine-learning pipelines. They commonly contain:

- Fact tables.
- Dimension tables.
- Domain-specific reporting tables.
- One Big Table designs where appropriate.

### 5.4 `macros/`

Macros are reusable Jinja blocks that behave like SQL utility functions. They support the DRY principle by defining logic once and invoking it from many models.

For example, a reusable currency mapping can be defined as:

```sql
{% macro map_currency_country(currency_column) %}
		case
				when {{ currency_column }} = 'USD' then 'USA'
				when {{ currency_column }} = 'EUR' then 'Europe'
				when {{ currency_column }} = 'GBP' then 'United Kingdom'
				else 'Unknown'
		end
{% endmacro %}
```

It can then be called from a model:

```sql
select
		transaction_id,
		amount,
		{{ map_currency_country('currency_code') }} as country_name
from {{ ref('stg_transactions') }}
```

The same pattern can standardize marketing channels, for example mapping Facebook to Paid Social. Macros can also override dbt's project behavior, including database routing and dynamic schema naming through mechanisms such as `generate_schema_name`.

### 5.5 `seeds/`

Seeds are small, static CSV files that dbt uploads into the target platform. Suitable examples include:

- Country and currency codes.
- ZIP-code-to-region mappings.
- Business-owned lookup tables.
- Static target definitions.

Seeds should normally remain small, generally fewer than about 1,000 rows, and change infrequently.

Important guardrails raised in response to Abdulsamad Ibrahim's question:

- Do not use seeds for transactional data or multi-gigabyte datasets.
- Never put credentials, secrets, or sensitive personally identifiable information in seeds.
- Frequently changing reference data should be ingested into the Bronze layer through a proper operational pipeline rather than maintained manually in Git.

### 5.6 `snapshots/`

Snapshots preserve changes to mutable source records and are commonly used to implement Type 2 Slowly Changing Dimensions.

dbt compares the current source state with the stored snapshot by using a timestamp strategy or selected-column checks. When a tracked record changes, dbt retains the previous version and manages metadata such as `dbt_valid_from` and `dbt_valid_to`. This supports historical questions involving changes to customer status, address, email, or other attributes.

### 5.7 `tests/`

Tests act as data quality gates. A dbt data test passes when its query returns zero rows and fails when it returns one or more invalid rows.

#### Generic tests

Generic tests are reusable assertions declared in YAML and attached to models or columns. Common built-in tests include:

- `unique`
- `not_null`
- `accepted_values`
- `relationships`

#### Singular tests

Singular tests are standalone SQL queries for business-specific rules:

```sql
-- tests/assert_transaction_amounts_are_positive.sql
select transaction_id, amount
from {{ ref('fct_transactions') }}
where amount < 0
```

Any rows returned by this query represent failures.

The project may organize reusable and custom test resources into `tests/generic/` and `tests/singular/` conventions where useful.

### 5.8 `analyses/`

The `analyses/` directory contains ad hoc queries that can use dbt's Jinja context and compile without being materialized as warehouse relations during a normal model run.

It can also act as a searchable archive for retired or legacy SQL. When archived code must not be parsed or compiled by dbt, its `.sql` extension can be removed while the file remains version-controlled for historical and lineage reference.

## 6. Enterprise Multi-Target `profiles.yml`

The class built `cdc_marketing/profiles.yml` to separate local development, pull-request validation, staging, and production. The first workshop draft left several environment values blank while resources were being provisioned. The completed structure expresses those values as environment variables:

```yaml
cdc_marketing:
	target: "{{ env_var('DBT_TARGET', 'dev') }}"

	meta:
		base: &base
			type: databricks
			threads: 8
		base_auth: &base_auth
			type: databricks
			auth_type: oauth
			client_id: "{{ env_var('DBX_ID_APPLICATION_ID') }}"
			client_secret: "{{ env_var('DBX_SECRET') }}"
			threads: 8
			connect_retries: 3
			retry_all: true

	outputs:
		dev: &dev_service_account
			<<: *base
			host: dbc-0196bfaf-1e17.cloud.databricks.com
			token: "{{ env_var('DATABRICKS_PAT_TOKEN') }}"
			catalog: "{{ env_var('DEV_CATALOG') }}"
			schema: "{{ env_var('DEV_SCHEMA') }}"
			http_path: "{{ env_var('DEV_HTTP_PATH') }}"

		ci: &ci_service_account
			<<: *base_auth
			catalog: "{{ env_var('CI_CATALOG') }}"
			schema: "{{ env_var('CI_SCHEMA') }}"
			host: dbc-0196bfaf-1e17.cloud.databricks.com
			http_path: "{{ env_var('CI_HTTP_PATH') }}"

		staging: &staging_service_account
			<<: *ci_service_account
			catalog: "{{ env_var('STAGING_CATALOG') }}"
			schema: "{{ env_var('STAGING_SCHEMA') }}"
			http_path: "{{ env_var('STAGING_HTTP_PATH') }}"

		production: &production_service_account
			<<: *base_auth
			catalog: "{{ env_var('PROD_CATALOG') }}"
			schema: "{{ env_var('PROD_SCHEMA') }}"
			host: dbc-0196bfaf-1e17.cloud.databricks.com
			http_path: "{{ env_var('PROD_HTTP_PATH') }}"

elementary:
	outputs:
		production:
			<<: *production_service_account
			catalog: "{{ env_var('PROD_CATALOG') }}"
			schema: "{{ env_var('ELEMENTARY_SCHEMA') }}"

		staging:
			<<: *staging_service_account
			catalog: "{{ env_var('STAGING_CATALOG') }}"
			schema: "{{ env_var('ELEMENTARY_SCHEMA') }}"
```

### 6.1 Dynamic target selection

```yaml
target: "{{ env_var('DBT_TARGET', 'dev') }}"
```

This selects the target from `DBT_TARGET` and defaults to `dev` on a developer's machine. A CI/CD runner can set it to `ci`, `staging`, or `production` without changing source code.

### 6.2 YAML anchors, aliases, and merges

YAML anchors avoid repeated configuration:

- `&base` defines shared adapter settings for PAT-based development.
- `&base_auth` defines shared OAuth and retry settings.
- `&ci_service_account`, `&staging_service_account`, and the other anchors name complete output blocks for reuse.
- `<<: *base` merges an anchored mapping into the current output.

This makes common settings consistent while allowing each target to override its catalog, schema, host, or SQL Warehouse path.

### 6.3 Environment variables and credential safety

Credentials and environment-specific endpoints must not be hardcoded into Git. The profile reads secrets and deployment values from environment variables, including:

- `DATABRICKS_PAT_TOKEN`
- `DBX_ID_APPLICATION_ID`
- `DBX_SECRET`
- Environment-specific catalog, schema, and HTTP path variables

The exact same version-controlled project can therefore run safely in several environments.

### 6.4 Workload and environment isolation

Each target should have its own schema and, in an enterprise setup, its own SQL Warehouse compute where appropriate:

- **Development:** Human developers use PATs and personal or isolated schemas.
- **CI:** Pull requests run automated builds and tests in disposable or isolated schemas.
- **Staging:** Release candidates are validated in a production-like environment.
- **Production:** Automated jobs use a non-human service principal and dedicated production resources.

As discussed with Prince Peter and Osakpolor Ogieriakhi, separating compute prevents experimental developer queries from starving production dashboards and scheduled pipelines.

## 7. Databricks Authentication and Provisioning

### 7.1 Databricks security and hierarchy chart

```text
+--------------------------------------------------------------------------+
| DATABRICKS UNITY CATALOG METASTORE                                       |
|                                                                          |
|   CATALOG: bronze_production                                             |
|   `-- SCHEMA: staging                                                    |
|       `-- TABLES / VIEWS: managed analytical relations                  |
+--------------------------------------------------------------------------+
| AUTHENTICATION PATHWAYS                                                  |
|                                                                          |
|   1. Human developer on a local machine                                  |
|      - Personal Access Token (PAT)                                       |
|      - Settings -> Developer -> Manage Access Tokens                     |
|      - Scoped lifetime and permissions                                   |
|                                                                          |
|   2. Automated CI/CD and production jobs                                 |
|      - Non-human service principal                                       |
|      - Settings -> Identity and Access -> Service Principals             |
|      - OAuth machine-to-machine client ID and client secret              |
+--------------------------------------------------------------------------+
```

### 7.2 Unity Catalog's three-level namespace

Databricks Unity Catalog uses:

```text
catalog.schema.table
```

As clarified in response to Qudus Abdulahi:

- A **catalog** is the highest governance and metadata boundary. It may represent an environment, data layer, or business domain.
- A **schema** is a namespace inside a catalog that groups related tables and views. It may represent staging, intermediate, or marts.
- A **table or view** is the relation that exposes the actual data.

The class initialized the required namespace in the Databricks SQL editor:

```sql
CREATE CATALOG IF NOT EXISTS bronze_production;
CREATE SCHEMA IF NOT EXISTS bronze_production.staging;
```

The shorter commands demonstrated during the walkthrough were:

```sql
CREATE CATALOG bronze_production;
CREATE SCHEMA bronze_production.staging;
```

Using `IF NOT EXISTS` makes repeated setup safer.

### 7.3 Personal Access Tokens for local development

Human developers authenticate locally with a Personal Access Token:

1. Open **Settings -> Developer -> Manage Access Tokens** in Databricks.
2. Create a dedicated token such as `dbt-dev-token`.
3. Choose an appropriate lifetime, for example 14 to 730 days according to policy.
4. Grant the API scopes needed to access the SQL execution backend.
5. Store the generated bearer token securely in `DATABRICKS_PAT_TOKEN`.

The workshop used broad API access to avoid learning-environment connection blocks. Production environments should follow least-privilege policies and restrict scopes to what the workload needs.

### 7.4 OAuth service principals for automation

CI/CD and production jobs should use a non-human machine identity:

1. Open **Settings -> Identity and Access -> Service Principals**.
2. Create a principal such as `sp-dbt-production`.
3. Assign the required workspace and Unity Catalog permissions.
4. Generate an OAuth client ID and client secret.
5. Supply them to dbt through `DBX_ID_APPLICATION_ID` and `DBX_SECRET`.

Service principals are preferable for automation because their lifecycle is independent of an employee account. A deployment does not fail merely because a staff member leaves or loses access.

### 7.5 SQL Warehouse connection information

Each profile output requires:

- The Databricks workspace host.
- The target SQL Warehouse HTTP path.
- Authentication credentials.
- A Unity Catalog catalog and schema.

Dedicated warehouse paths can be assigned per environment to isolate cost, concurrency, and failure impact.

## 8. CI/CD and Configuration Principles

### 8.1 Do not use branches as credential stores

In response to Prince Peter's question, the class established that hardcoding staging or production credentials in separate Git branches is an anti-pattern. Merging branches can overwrite configuration and expose secrets.

Branches manage the code lifecycle. Environment variables and deployment secret stores manage runtime configuration. CI/CD should inject the correct `DBT_TARGET`, credentials, catalog, schema, and HTTP path into the same codebase.

### 8.2 One adapter target per dbt invocation

Mercy Abaraonye and Ose Benson asked whether one dbt project can operate against Databricks and Snowflake simultaneously. A single dbt invocation uses one adapter profile target at a time.

During a cross-platform migration, an organization can keep separate Databricks and Snowflake dbt projects in the same parent repository, run each independently, compare outputs for parity, and retire the legacy project when migration is complete.

## 9. Troubleshooting from the Workshop

### 9.1 `uv: command not found` on Windows

**Cause:** The terminal had not reloaded its `PATH` after `uv` installation.

**Resolution:** Close and reopen the VS Code terminal, using Git Bash where that was the configured shell. In VS Code, a new terminal can be opened with `Ctrl+Shift+``.

### 9.2 `dbt: failed to spawn` or OS error 2

**Cause:** `uv run dbt ...` was executed before the dbt adapter had been installed into the project environment.

**Resolution:** Complete the adapter installation first:

```bash
uv add dbt-databricks
uv run dbt init cdc_marketing --skip-profile-setup
```

Confirm that `dbt-databricks` appears in `pyproject.toml` and that dependency resolution completes.

### 9.3 Slow or inconsistent Elementary installation

**Cause:** Network timeouts or platform-specific native dependency builds.

**Resolution:** Defer Elementary and complete the core dbt-databricks setup first. Observability can be added after the base environment is stable.

### 9.4 Repository and dbt project name mismatch

The repository or `uv` project can be named `cdc_modelling` while the dbt project is named `cdc_marketing`. The critical requirement is that the profile reference in `dbt_project.yml` matches the root profile key in `profiles.yml`.

## 10. Key Rules and Takeaways

1. Use normalized models for transactional integrity and dimensional models for analytical consumption.
2. Load raw data first and transform it in the cloud platform when following ELT.
3. Remember that dbt compiles and orchestrates transformations; it does not transport data.
4. Install the adapter for the actual destination platform rather than only installing generic dbt Core.
5. Keep staging models simple and source-aligned, intermediate models reusable, and marts consumer-ready.
6. Use macros to centralize repeated SQL and project behavior.
7. Use seeds only for small, static, non-sensitive reference data.
8. Use snapshots when historical versions of mutable records must be retained.
9. Treat every row returned by a dbt data test as a failing record.
10. Keep secrets out of source control and inject them with environment variables.
11. Use PATs for local human development and service principals for automated workloads.
12. Isolate schemas and compute across development, CI, staging, and production.
13. Use Git branches for code changes, not environment credentials.

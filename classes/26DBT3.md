## ⚙️ Enterprise Profiles Configuration (`profiles.yml`)

The connection profile (`cdc_marketing`) was structured to handle dynamic targeting across development, CI, staging, and production environments using environment variables, while mapping Elementary output models to target schemas.

### Key Connection Elements:
* **Target Engine:** Dynamically injected via `env_var('DBT_TARGET', 'dev')`.
* **Authentication:** OAuth or Databricks Personal Access Token (`PAT`).
* **Environment Variables Required:**
  * `DATABRICKS_PAT_TOKEN`
  * `DEV_CATALOG`
  * `DEV_SCHEMA`
  * `DEV_HTTP_PATH`
  * `DBX_ID_APPLICATION_ID` (OAuth)
  * `DBX_SECRET` (OAuth)
* **Elementary Target Schema:** Configured alongside `dev`, `staging`, and `production` targets so observability metrics and test executions persist into dedicated schemas without polluting clean staging layers.

## 📂 Domain Modeling: The Normalized Marketing Hierarchy

To ground the exercise in realistic analytics engineering, Victor introduced a normalized four-tier marketing domain model:

```
+-------------------------------------------------------------+
|                     Platform (e.g., Meta/Facebook)          |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                      Ad Account                             |
|              (PK: account_id, FK: platform_id)              |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                      Campaign                               |
|              (PK: campaign_id, FK: account_id)              |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                      AdGroup                                |
|              (PK: adgroup_id, FK: campaign_id)              |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|                        Ad                                   |
|              (PK: ad_id, FK: adgroup_id)                    |
+-------------------------------------------------------------+
```

### Relational & Referential Integrity Rules:
1. **Parent-Child Strictness:** Every lower-level entity must carry a valid foreign key referencing its parent.
2. **Cardinality:**
   * One **Account** $\rightarrow$ Multiple **Campaigns**.
   * One **Campaign** $\rightarrow$ Multiple **AdGroups**.
   * One **AdGroup** $\rightarrow$ Multiple **Ads**.
3. **Uniqueness Constraints:** An `ad_id` must map to one and only one `adgroup_id`.

## 🗄️ Ingestion & Source Declarations (`sources.yml`)

Four raw marketing CSV files were ingested into Databricks tables under `bronze_production.cdc_staging`:
* `accounts`
* `campaigns`
* `adgroups`
* `ads`

### Modular Folder Architecture
Victor strongly warned against creating a massive, monolithic `sources.yml` file in the project root. Instead, the project adopted a platform-partitioned staging structure:

```
cdc_marketing/
├── dbt_project.yml
├── packages.yml
├── profiles.yml
└── models/
    └── staging/
        └── facebook/
            ├── sources.yml
            ├── stg_facebook__accounts.sql
            ├── stg_facebook__campaigns.sql
            ├── stg_facebook__adgroups.sql
            └── stg_facebook__ads.sql
```

### Source Definition (`staging/facebook/sources.yml`)

```yaml
version: 2

sources:
  - name: facebook
    database: bronze_production
    schema: cdc_staging
    config:
      enabled: true
    meta:
      owner: "@cde_engineer" # Quoted to avoid YAML syntax errors with '@'
    freshness:
      warn_after:
        count: 2
        period: day
    tables:
      - name: campaigns
        description: "Raw ad campaign configurations and budgets."
        config:
          enabled: true
          event_time: campaign_updated_at
      - name: adgroups
        description: "Targeting sets and audience definitions."
        config:
          enabled: true
          event_time: adgroup_updated_at
      - name: ads
        description: "Creative level entities, links, and copy."
        config:
          enabled: true
          event_time: ad_updated_at
      - name: accounts
        description: "Top-level billing account info."
        config:
          enabled: true
          event_time: account_updated_at
```

## 💻 CLI Command Matrix & Execution Order

Victor walked the cohort through the execution lifecycle, emphasizing exact command behavior:

| Step | Command | Purpose & Behavior |
| :---: | :--- | :--- |
| **1** | `uv run dbt debug` | Validates YAML syntax, loads environment variables, tests Databricks network latency and authentication. |
| **2** | `uv run dbt deps` | Fetches package tarballs (`dbt_utils`, `elementary`, `dbt_expectations`) into `dbt_packages/`. |
| **3** | `uv run dbt compile` | Injects Jinja variables and generates pure SQL inside `target/compiled/` without executing on Databricks. |
| **4** | `uv run dbt build` | **All-in-one execution:** Executes upstream seeds, runs models, and fires generic/singular tests sequentially (`build = run + test`). |
| **5** | `uv run dbt source freshness --select source:facebook` | Evaluates max timestamp of `event_time` against system clock to confirm data pipelines are not stale. |
| **6** | `uv run edr report --days-back 90 --profiles-dir .` | Extracts test results, metrics, and schema drift history from Elementary models to generate a standalone HTML observability dashboard. |

> 💡 **Production Best Practice:** Host the output HTML report generated by `edr report` inside a secure shared cloud storage bucket (e.g., AWS S3, GCS, or Azure Blob) connected to Slack or Teams webhooks for automated engineering notifications.

## 🔍 Gotchas, Common Pitfalls & Troubleshooting Guide

During the workshop, several participants encountered errors. Victor paused to systematically debug each issue:

### 1. The GitHub Organization vs. Personal Account Disconnect
* **Symptom:** Participants could not find their project repo when linking dbt Cloud.
* **Root Cause:** dbt Cloud was authorized under a Personal GitHub space rather than the Organization workspace.
* **Fix:** Re-authorize the dbt Cloud GitHub App with explicit permissions granted to the organization.

### 2. Missing `packages.yml`
* **Symptom:** `Warning: No packages were found in packages.yml`.
* **Root Cause:** File misnamed as `package.yml` (singular) or saved in a subdirectory instead of the root directory (`cdc_marketing/`).
* **Fix:** Rename to `packages.yml` and place it at the project root. Enable IDE Auto-Save to ensure files are written to disk before running CLI commands.

### 3. YAML Parser Breakage (`@` and Typos)
* **Symptom:** Syntax parse exceptions preventing compilation.
* **Root Cause:** Unquoted `@` symbol in `meta.owner: @cde_engineer`, or typing plural `descriptions:` instead of singular `description:`.
* **Fix:** Wrap Slack/Teams handles in quotes (`"@cde_engineer"`) and enforce valid dbt source schema keys.

### 4. Selection Criterion Failure on Freshness
* **Symptom:** `The selection criterion 'source:facebook' does not match any enabled nodes`.
* **Root Cause:**
  1. `sources.yml` placed outside `models/staging/facebook/`.
  2. Naming mismatch between Databricks catalog tables and the `name:` keys under `tables:`.
  3. Missing `config.enabled: true`.
* **Fix:** Match table names identically, verify folder paths, and run `dbt deps` first.

### 5. `edr: command not found` & Windows Virtualenv Mismatches
* **Symptom:** Shell throws command not found when executing `edr report`.
* **Root Cause:** Elementary CLI binary was installed inside an isolated virtual environment not bound to global PATH.
* **Fix:** Prefix with the package environment runner:
  ```bash
  uv run edr report --days-back 90 --profiles-dir .
  ```
  Or run Elementary inside a Docker container matching the project dependencies.

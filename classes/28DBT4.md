## 1. Modern Data Architecture: The Three dbt Layers

Victor broke down the industry-standard multi-layer approach to transform data predictably without blowing up warehouse compute credits:

```
[ Raw Sources ] (Databricks Tables / CSVs)
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ 1. STAGING LAYER (models/staging/...)                       │
│    • Materialization: VIEW (Zero storage, fast compute)    │
│    • Operations: 1:1 with source, renaming columns,        │
│      casting data types, row/date filtering.                │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. INTERMEDIATE LAYER (models/intermediate/...)             │
│    • Materialization: TABLE / INCREMENTAL                   │
│    • Operations: Denormalization (Joins across 3NF tables), │
│      deduplication (ROW_NUMBER + QUALIFY), Cross-platform   │
│      unions (e.g., Facebook + Snapchat + TikTok).           │
└─────────────────────────────────────────────────────────────┘
       │
       ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. MARTS LAYER (models/marts/...)                           │
│    • Materialization: TABLE / INCREMENTAL / SECURE VIEW     │
│    • Operations: Business KPIs, metrics, window rollups,   │
│      RBAC (masking/hiding columns from non-authorized BI).   │
└─────────────────────────────────────────────────────────────┘
```

## 2. dbt Directory Structure & Configuration Hierarchy

### Anatomy of Key Folders

| Directory / File | Purpose & Lifecycle Behavior |
| :--- | :--- |
| `analysis/` | SQL playground and audit queries. Files here **never** get materialized during `dbt run` or `dbt build`. |
| `seeds/` | Static CSV lookup tables (e.g., country codes). Ideal file size: **$< 1\text{ GB}$**. |
| `snapshots/` | Houses **Slowly Changing Dimensions (SCD Type 2)** to retain historic states over time. |
| `target/` & `edr_target/` | Auto-generated artifacts, compiled SQL, and HTML report dashboards. **Must be added to `.gitignore`** so local developer metadata does not leak into git branches. |

### Configuration Precedence: Where Does dbt Look First?

When determining the target catalog, schema, or materialization strategy, dbt resolves conflicts using this strict priority cascade:

$$ \text{In-Model Config Block } ({{ \text{config(...) } }}) \succ \text{dbt\_project.yml} \succ \text{profiles.yml} $$

1. **Inside the Model File (`.sql`):** Overrides everything else via `{{ config(materialized='table') }}`.
2. **`dbt_project.yml`:** Sets defaults across entire folders (e.g., all models in `staging/` become views).
3. **`profiles.yml`:** The global fallback specifying warehouse connections and default target schemas.

## 3. The Power of Jinja: Hardcoded SQL vs. `{{ source() }}`

A central demonstration revealed why referencing database objects directly in dbt is an anti-pattern:

### ❌ The Hardcoded Way (Anti-Pattern)
```sql
SELECT * FROM bronze_production.cdc_staging.campaigns
```
* **Why it hurts:** Breaks environment portability (dev vs. prod), and dbt cannot parse lineage. In documentation, your model appears floating in isolation with **zero upstream sources**.

### The dbt Jinja Way (Best Practice)
```sql
SELECT * FROM {{ source('facebook_ads', 'campaigns') }}
```
* **Why it wins:** dbt dynamically substitutes the correct catalog and schema based on the active target environment and automatically draws the interactive **lineage DAG** in `dbt docs`!

### B. The Intermediate Model (`models/intermediate/facebook/int_facebook_ads_details.sql`)

This model deduplicates each upstream table to its latest state and denormalizes the marketing hierarchy:

```sql
WITH latest_ads AS (
    SELECT *
    FROM {{ ref('stg_facebook_ads_ad_history') }}
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY ad_id 
        ORDER BY updated_at DESC
    ) = 1
),

latest_adgroups AS (
    SELECT *
    FROM {{ ref('stg_facebook_ads_adgroup_history') }}
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY adgroup_id 
        ORDER BY updated_at DESC
    ) = 1
),

latest_campaigns AS (
    SELECT *
    FROM {{ ref('stg_facebook_ads_campaign_history') }}
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY campaign_id 
        ORDER BY updated_at DESC
    ) = 1
),

latest_accounts AS (
    SELECT *
    FROM {{ ref('stg_facebook_ads_account_history') }}
    QUALIFY ROW_NUMBER() OVER (
        PARTITION BY account_id 
        ORDER BY updated_at DESC
    ) = 1
)

SELECT 
    a.ad_id,
    a.ad_name,
    a.ad_status,
    ag.adgroup_id,
    ag.adgroup_name,
    c.campaign_id,
    c.campaign_name,
    acc.account_id,
    acc.account_name,
    a.updated_at
FROM latest_ads a
LEFT JOIN latest_adgroups ag ON a.adgroup_id = ag.adgroup_id
LEFT JOIN latest_campaigns c ON ag.campaign_id = c.campaign_id
LEFT JOIN latest_accounts acc ON c.account_id = acc.account_id
```

## 5. Data Quality, Testing & AI Documentation

### Testing Frameworks: Generic vs. Singular

* **Singular Tests:** Custom `.sql` queries returning failing rows, applied to a specific one-off business edge case.
* **Generic Tests:** Reusable assertions defined in YAML. Packages like `dbt_utils` and `dbt_expectations` provide out-of-the-box checks:
  * `dbt_utils.unique_combination_of_columns`: Enforces composite primary keys (e.g., `account_id` + `updated_at`).
  * `accepted_values`: Guarantees categorical fields (e.g., channel values like `Paid Social`) remain clean.
  * `expect_column_to_exist`: Acts as a data contract to catch breaking upstream schema drift before ingestion pipelines pollute downstream marts.

### Documenting for AI (Databricks Genie / Agents)

Victor emphasized that adding column comments in YAML is not just for human engineers—it directly empowers LLM data agents:
```yaml
version: 2

models:
  - name: int_facebook_ads_details
    description: "Denormalized marketing attribution model capturing the latest state of ads, adgroups, campaigns, and accounts."
    columns:
      - name: ad_id
        description: "Primary key. Unique identifier of the individual ad creative."
        tests:
          - not_null
      - name: ad_status
        description: "Latest operational status of the ad."
        tests:
          - accepted_values:
              values: ['ACTIVE', 'PAUSED', 'ARCHIVED']
```
> **Enterprise Tip:** Tools like Databricks Genie rely on catalog metadata comments to interpret metrics accurately. If columns are not documented, AI tools guess—leading to hallucinations.

## 6. dbt Graph Operators & CLI Command Matrix

The workshop demystified dbt's model selection graph operators (the `+` sign):

```
       Upstream                     Current Target                   Downstream
[ stg_facebook_ads ]  ───>  [ int_facebook_ads_details ]  ───>  [ fct_marketing_marts ]
         ▲                                                            ▲
         │                                                            │
    Selected by                                                  Selected by
  +int_model_name                                              int_model_name+
```

* `dbt build --select +int_model`: Builds the model **AND all its upstream dependencies**.
* `dbt build --select int_model+`: Builds the model **AND all its downstream models**.
* `dbt build --select +int_model+`: Builds the entire lineage spanning upstream and downstream.
* `dbt build --select int_model`: Isolates build execution strictly to that single model.

### Complete Command Cheat Sheet

```bash
# 1. Install required packages
uv run dbt deps

# 2. Check source data freshness
uv run dbt source freshness --select source:facebook_ads

# 3. Build intermediate model and its upstream ancestors
uv run dbt build --select +int_facebook_ads_details

# 4. Generate the static interactive documentation dashboard
uv run dbt docs generate --static

# 5. Extract Elementary test metrics and render HTML report
uv run edr report --days-back 90 --profiles-dir .
```

## 7. Live Troubleshooting Log & Solutions

| Error / Symptom | Root Cause | Verified Solution |
| :--- | :--- | :--- |
| `Compilation Error: depends on a source named 'facebook_ads.accounts' which was not found` | Mismatch between the source name defined in `sources.yml` (`facebook` vs `facebook_ads`). | Rename `sources.yml` root key to `name: facebook_ads` or align Jinja call to match the YAML name. |
| `Compilation Error: depends on a source named 'facebook_ads.ads_stats' which was not found` | The table was not provided in Databricks for this session. | Delete or comment out `stg_facebook_ads_basic_all_levels.sql` and its YAML entry. |
| `Runtime Error: while scanning a simple key ... could not find expected ':'` | Copied YAML indentation error (often caused by pasting "Show less" from web UI). | Clean out indentation and remove extraneous text from YAML manifests. |
| `MissingArgumentsPropertyInGenericTestDeprecation` | Outdated syntax in `dbt_utils.unique_combination_of_columns`. | Nest generic arguments under the `arguments:` key in modern dbt versions. |
| Noise in DAG lineage diagram | Lineage graph displaying internal Elementary & dbt package models. | In the documentation search bar, filter via: `source:facebook_ads+`. |

## Executive Overview: Moving from Retrieval to Transformation
Writing `SELECT *` only scratches the surface. In real-world data engineering, raw data is messy, riddled with `NULL` values, unformatted timestamps, and floating-point edge cases. Data engineers must know how to:
1. Perform mathematical row-level arithmetic while strictly honoring operator precedence (**BODMAS**).
2. Aggregate millions of transactional rows into actionable business metrics (`SUM`, `AVG`, `COUNT DISTINCT`).
3. Partition summaries cleanly across business dimensions with `GROUP BY` and filter aggregates using `HAVING`.
4. Cleanse corrupt records on the fly using `COALESCE`, conditional `CASE WHEN` branches, string manipulation (`UPPER`, `LOWER`, `TRIM`), and explicit data type conversions (`CAST` / `CONVERT`).

## 1. Row-Level Arithmetic Operations vs. Columnar Aggregations

A critical conceptual distinction established early in the masterclass:
* **Arithmetic Operations (`+`, `-`, `*`, `/`):** Operate **horizontally across columns within a single row** (e.g., `standard_qty + gloss_qty + poster_qty`).
* **Aggregate Functions (`SUM`, `AVG`, `MIN`, `MAX`):** Operate **vertically across rows within a single column** (e.g., `SUM(total_amt_usd)`).

```
 ROW-LEVEL ARITHMETIC (Across Columns)
 ┌──────────────┬───────────┬────────────┐
 │ standard_qty │ gloss_qty │ poster_qty │ ──> standard_qty + gloss_qty + poster_qty
 ├──────────────┼───────────┼────────────┤
 │     123      │    45     │     12     │ = 180 (Computed per individual row)
 └──────────────┴───────────┴────────────┘
        │
        ▼ COLUMNAR AGGREGATION (Down Rows)
   SUM(standard_qty) = Adds all rows down into one single scalar number
```

## 2. Arithmetic Mechanics & The BODMAS Rule

SQL strictly adheres to standard mathematical order of operations (**BODMAS** / **PEMDAS**):
* **B**rackets 
**O**rders (powers) 
**D**ivision 
**M**ultiplication 
**A**ddition 
**S**ubtraction.

### The Parenthesis Trap: Calculating Percentage of Total
When calculating the percentage of standard paper ordered:
```sql
-- BUGGY QUERY (Without Parentheses):
-- SQL evaluates standard_qty / standard_qty (= 1) first, then adds gloss and poster!
SELECT standard_qty / standard_qty + gloss_qty + poster_qty * 100 
FROM dbo.orders;

-- CORRECT QUERY (Explicit BODMAS Parentheses):
SELECT 
    id,
    standard_qty,
    (standard_qty + gloss_qty + poster_qty) AS calculated_total,
    (standard_qty * 1.0 / (standard_qty + gloss_qty + poster_qty)) * 100 AS standard_qty_pct
FROM dbo.orders;
```

### Production Safety: Handling Division by Zero (`0`)
Dividing by zero causes database transactions to abort with `Divide by zero error encountered`:
```sql
-- Solution 1: Conditional CASE WHEN Guard
SELECT 
    id,
    CASE 
        WHEN standard_qty = 0 THEN 0
        ELSE (standard_amt_usd / standard_qty)
    END AS unit_price
FROM dbo.orders;

-- Solution 2: NULLIF Function
-- If standard_qty is 0, NULLIF turns it into NULL. Dividing by NULL yields NULL (no fatal crash).
SELECT id, (standard_amt_usd / NULLIF(standard_qty, 0)) AS unit_price
FROM dbo.orders;
```

## 3. The Big Five Aggregate Functions

| Aggregate Function | Description | Null Behavior | Real-World Business Example |
| :--- | :--- | :--- | :--- |
| **`COUNT(*)`** | Counts total rows in a table/partition. | Includes `NULL` rows. | Total transactions processed. |
| **`COUNT(column)`** | Counts rows containing non-null values in that column. | **Ignores / Skips `NULL`s.** | Number of orders with confirmed delivery dates. |
| **`COUNT(DISTINCT col)`**| Counts unique non-null values. | **Ignores / Skips `NULL`s.** | Total unique customers who ordered this year. |
| **`SUM(column)`** | Calculates the numeric total across all rows. | Ignores `NULL`s. | Total company gross merchandise value (GMV). |
| **`AVG(column)`** | Calculates arithmetic mean (`SUM / COUNT(col)`). | Ignores `NULL`s. | Average order value (AOV) per customer. |
| **`MIN(column)`** | Finds lowest numeric value or earliest date. | Ignores `NULL`s. | Earliest recorded order date (`2013-12-04`). |
| **`MAX(column)`** | Finds highest numeric value or latest date. | Ignores `NULL`s. | Most recent web event recorded (`2017-01-01`). |

```sql
-- Enterprise Aggregation Dashboard Query:
SELECT 
    COUNT(*) AS total_orders,
    COUNT(DISTINCT account_id) AS unique_buying_accounts,
    SUM(total_amt_usd) AS gross_revenue_usd,
    AVG(total_amt_usd) AS average_order_value_usd,
    MIN(occurred_at) AS first_order_timestamp,
    MAX(occurred_at) AS latest_order_timestamp
FROM dbo.orders;
```

## 4. Multi-Dimensional Grouping & Partitioning (`GROUP BY`)

### The Golden Aggregation Law:
> *Every non-aggregated column listed in the `SELECT` statement **must** appear in the `GROUP BY` clause.* Failure to include it results in SQL compilation errors.

### Single vs. Multi-Column Grouping
```sql
-- 1. Single Dimension: Total Traffic Volume by Web Channel
SELECT 
    channel, 
    COUNT(*) AS total_events
FROM dbo.web_events
GROUP BY channel
ORDER BY total_events DESC;

-- 2. Multi-Dimension: Traffic Volume by Account AND Channel
SELECT 
    account_id, 
    channel, 
    COUNT(*) AS channel_event_count
FROM dbo.web_events
GROUP BY account_id, channel
ORDER BY account_id ASC, channel_event_count DESC;
```

## 5. Filtering Aggregates: The `HAVING` Clause in Action
Because `WHERE` evaluates at the row-level **before** grouping, it cannot filter aggregated results. The `HAVING` clause filters aggregated partitions **after** `GROUP BY`.

```sql
-- Find high-value client accounts generating over $200,000 in total spend
SELECT 
    account_id, 
    SUM(total_amt_usd) AS total_lifetime_revenue
FROM dbo.orders
GROUP BY account_id
HAVING SUM(total_amt_usd) > 200000
   AND account_id IN (1001, 1011, 1021) -- Filtering combined with set criteria
ORDER BY total_lifetime_revenue DESC;
```

## 6. Hands-on Data Cleaning: Techniques & Recipes

### A. The Silent Killer: Arithmetic with `NULL`
In SQL, **any arithmetic operation performed on a `NULL` produces `NULL`** (`100 + NULL = NULL`). If a customer bought standard paper but gloss paper is `NULL`, summing them wipes out the total.

```sql
-- Corrupted Calculation:
SELECT standard_qty + gloss_qty + poster_qty AS corrupted_total FROM dbo.orders;

-- Cleaned with COALESCE (Replaces NULL with 0):
SELECT 
    COALESCE(standard_qty, 0) + 
    COALESCE(gloss_qty, 0) + 
    COALESCE(poster_qty, 0) AS bulletproof_total
FROM dbo.orders;
```

### B. Conditional Bucketing with `CASE WHEN`
`CASE WHEN` constructs conditional branching logic (similar to `if/else` statements in Python):
```sql
SELECT 
    id,
    total_amt_usd,
    CASE 
        WHEN total_amt_usd >= 3000 THEN 'Large Order'
        WHEN total_amt_usd >= 1000 THEN 'Medium Order'
        ELSE 'Small Order'
    END AS order_tier
FROM dbo.orders;
```

### C. String Standardization (`UPPER`, `LOWER`, `TRIM`)
Text columns frequently contain accidental leading/trailing spaces or inconsistent casing that breaks `JOIN` and `WHERE` equality checks:
```sql
SELECT 
    name AS raw_name,
    UPPER(name) AS uppercase_name,
    LOWER(name) AS lowercase_name,
    TRIM(name) AS whitespace_stripped_name
FROM dbo.accounts;
```

### D. Data Type Casting & Conversions (`CAST` vs. `CONVERT`)
* **`CAST(expression AS data_type)`:** ANSI-SQL standard; portable across PostgreSQL, Snowflake, BigQuery, and SQL Server.
* **`CONVERT(data_type, expression [, style])`:** SQL Server specific; allows precise style formatting codes (especially for timestamps).

```sql
-- 1. Integer Truncation (Decimal -> Int)
SELECT id, CAST(total_amt_usd AS INT) AS integer_amount 
FROM dbo.orders;

-- 2. Timestamp to Date Only (Drops hh:mm:ss)
SELECT id, CAST(occurred_at AS DATE) AS order_calendar_date 
FROM dbo.orders;

-- 3. Converting Timestamp to Formatted String
SELECT id, CONVERT(VARCHAR(20), occurred_at, 120) AS iso_formatted_date 
FROM dbo.orders;

-- 4. Preventing Integer Division Truncation (Forces Floating-Point Precision)
SELECT id, CAST(standard_qty AS DECIMAL(10, 2)) / NULLIF(total, 0) AS exact_ratio
FROM dbo.orders;
```

## 7. Key Student Q&A & Technical Clarifications
* **Q: Why did our percentage return `0` instead of a decimal?**
  * *A:* In SQL engines, dividing an integer by another integer performs **integer division** (e.g., `123 / 169 = 0`). To preserve floating-point decimals, multiply the numerator by `1.0` or explicitly cast to `DECIMAL(10, 2)`: `CAST(standard_qty AS DECIMAL(10, 2)) / total`.
* **Q: When should I use `CAST` vs. `CONVERT`?**
  * *A:* Default to `CAST` because it is ANSI-SQL compliant and runs identically on PostgreSQL, MySQL, DuckDB, and BigQuery. Use `CONVERT` in SQL Server only when you need specialized third-argument date formatting styles (e.g., European vs. US date format codes).
* **Q: What is the schema difference between SQL Server and PostgreSQL?**
  * *A:* SQL Server uses `dbo` as its default system schema (`dbo.orders`), whereas PostgreSQL uses `public` (`public.orders`). Both support custom user-defined schemas (`demo.orders`).

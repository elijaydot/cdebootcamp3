## Part 1: Wildcard Pattern Matching Mechanics (`*`)

Before touching JSON syntax, Mayowa demonstrated why understanding wildcard matching is essential. In AWS IAM, wildcards allow administrators to target dynamic resources without hardcoding thousands of unique identifiers.

### 1. The Core Meaning of the Asterisk (`*`)
* The `*` represents **zero, one, or multiple characters** of any kind.
* It operates similarly to the `%` wildcard in SQL `LIKE` clauses or the `.*` quantifier in regular expressions.

### 2. Whiteboard Pattern Dissections

Using a mock roster of Data Engineers:
* `folake`
* `prince`
* `lane`
* `david`
* `dennis`

```
  Pattern: *an*           Pattern: *e             Pattern: Dav*
  ==============          ============            =============
  Matches:                Matches:                Matches:
  - "lane"                - "folake"              - "david"
  - "dennis"              - "prince"
                          - "lane"
  (Finds "an" anywhere)   (Ends with "e")         (Starts with "Dav")
```

* **`*an*`:** Matches any string that contains the sequence `an` anywhere (beginning, middle, or end). Matches: `lane` and `dennis`.
* **`*e`:** Matches any string ending with the letter `e`. Matches: `folake`, `prince`, and `lane`.
* **`Dav*`:** Matches any string starting strictly with `Dav`, followed by anything or nothing. Matches: `david`.
* **`*` (Standalone Star):** Matches **everything**. In SQL terms, this is equivalent to `SELECT *`. In AWS IAM, placing `*` in actions or resources grants god-mode universal scope.

> **Crucial Rule on Case Sensitivity:** AWS ARNs and action names are strictly case-sensitive. Matching `*staging*` will not match `*Staging*` unless explicitly configured.

### The String Matching Rules (More Explanation)

```
Pattern Structure            Rule & Behavior                       Matches Examples
─────────────────────────────────────────────────────────────────────────────────────────────
*staging*                    Matches ANY string containing the      airflow-staging,
                             word "staging" anywhere.              staging-db, prod-staging-v1

*e                           Matches ANY string that terminates    Prince, Lane,
                             with the letter "e".                  Database, Lakehouse

Dav*                         Matches ANY string that explicitly    David, Davenport,
                             begins with "Dav".                    Dav-Worker-01

*                            Universal Wildcard: Matches           EVERYTHING.
                             all strings, all actions, all resources.
```

### Case Sensitivity & Placement Nuances:

* **Wildcards are strictly case-sensitive:** Matching `*b*` will **not** match `Benz` or `BMW` because lowercase `b` does not equal uppercase `B`.
* **Middle Wildcards (`*character*`):** As explained by teaching assistant **Ayodeji Ajayi**, placing a character between two asterisks means: *"Match any string containing this specific character anywhere—at the beginning, middle, or end."*
* **Anchor Matching (`prefix*` vs. `*suffix`):** 
  * Omitting the leading star (`staging*`) mandates that the resource name **must begin** with `staging`.
  * Omitting the trailing star (`*staging`) mandates that the resource name **must terminate** with `staging`.

## Part 2: Deconstructing the Anatomy of an IAM Policy

An IAM policy is a formal JSON document defining authorization rules. Mayowa highlighted that while policies look intimidating, **98% of your attention must focus on only two fields: `Action` and `Resource`**.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SpecificStmtIdentifier",
      "Effect": "Allow",
      "Action": [
        "service:APIActionName"
      ],
      "Resource": "arn:aws:service:region:account-id:resource-type/resource-id",
      "Condition": {
        "StringEquals": {
          "aws:PrincipalTag/Role": "Lead"
        }
      }
    }
  ]
}
```

### Element-by-Element Breakdown:

1. **`Version`:** Specifies the language syntax version. Always set to `"2012-10-17"` (never use current calendar dates).
2. **`Statement`:** An array containing one or more authorization blocks.
3. **`Sid` (Statement ID):** An optional human-readable description for logging and code readability (e.g., `"AllowS3ReadAccess"`).
4. **`Effect`:** Explicitly dictates the result: either `"Allow"` or `"Deny"`.
5. **`Action`:** The exact API call or set of API calls being governed, formatted as `"service:ActionName"` (e.g., `"iam:DeleteUser"`, `"s3:GetObject"`).
6. **`Resource`:** The exact Amazon Resource Name (ARN) identifying the target cloud entity where the action is permitted or denied.
7. **`Condition` (Optional):** Fine-grained conditional checks (e.g., verifying client IP address, requiring MFA, or matching principal tags). Mayowa noted that data engineers rarely need complex conditions in day-to-day work; mastering `Action` and `Resource` is where core competence lies.


```
┌────────────────────────────────────────────────────────────────────────┐
│                        POLICY ELEMENT BREAKDOWN                        │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Version:   Must be "2012-10-17" (The current policy language standard)│
│ 2. Statement: An array of rule objects (a policy can contain multiple) │
│ 3. Sid:       Statement Identifier (Human-readable tracking label)     │
│ 4. Effect:    "Allow" or "Deny" (Explicit Deny ALWAYS overrides Allow) │
│ 5. Action:    Specific API operations allowed or blocked               │
│ 6. Resource:  The exact ARN(s) the action acts upon                    │
│ 7. Condition: (Optional) Contextual rules (IP blocks, MFA, VPC tags)   │
└────────────────────────────────────────────────────────────────────────┘
```

> **Where to Focus Your Brain:** Mayowa advised students not to waste mental energy memorizing obscure `Condition` blocks early on. **95% of real-world cloud data engineering permissions hinge on getting `Action` and `Resource` pairing right.**


## The Car Analogy: Actions vs. Resources

To clarify the conceptual boundary between an Action and a Resource, Mayowa presented the **Automobile Framework**:

```
                       THE ACTION VS. RESOURCE MATRIX
                       
  Action (The Verb)                         Resource (The Target Noun)
┌──────────────────────────────────┐      ┌──────────────────────────────────┐
│ What operation is attempted?     │      │ Upon WHICH physical entity?      │
│ • open_door                      │ ───> │ • arn:vehicle:mercedes:benz_c200 │
│ • drive_car                      │      │ • arn:vehicle:toyota:camry_v6    │
│ • inspect_trunk                  │      │ • arn:vehicle:bmw:m3_competition │
└──────────────────────────────────┘      └──────────────────────────────────┘
```

* **The Scope Vulnerability:** If you set `"Resource": "*"`, you give the user permission to open the door and drive **every single vehicle on the road**.
* **Least-Privilege Scoping:** By pairing `"Action": "car:OpenDoor"` with `"Resource": "arn:vehicle:bmw:*"` you grant permission to access only BMWs, leaving Toyotas and Mercedes vehicles securely locked.

---
### The Real-World Analogy:
* **Action:** Turning a key / opening a door (`car:OpenDoor`).
* **Resource:** The exact car parked in the driveway (`arn:...:car/Fatimas_Benz`).
* If you set `Resource: "*"`, you are giving the user a skeleton key that unlocks every car on the planet.

## Part 3: The Amazon Resource Name (ARN) Format

Every resource created across AWS receives an unambiguous, globally unique identifier called an **ARN**.

### Universal ARN Syntax Structure:
$$\Large \texttt{arn:partition:service:region:account-id:resource-type/resource-id}$$

* **`arn`:** The mandatory scheme prefix.
* **`partition`:** Typically `aws` (or `aws-cn` for China, `aws-us-gov` for US Government).
* **`service`:** The AWS service namespace (`iam`, `s3`, `rds`, `ec2`).
* **`region`:** The physical AWS Region (e.g., `eu-north-1`, `us-east-1`).
  * *Note:* Regional services (like RDS or EC2) require a region string. Global services (like IAM and S3 buckets) leave this field blank.
* **`account-id`:** The 12-digit AWS Account ID owning the resource.
* **`resource-type/resource-id`:** The internal hierarchy defining the item (e.g., `user/airflow-worker` or `bucket-name/folder/file.parquet`).

### Comparison Table:
| Service | Sample Resource | Concrete ARN Pattern |
| :--- | :--- | :--- |
| **IAM User** | User `staging-worker` | `arn:aws:iam::123456789012:user/staging-worker` |
| **S3 Bucket** | Bucket `cdebytes-orders` | `arn:aws:s3:::cdebytes-orders` |
| **S3 Object** | All files in `cdebytes-orders` | `arn:aws:s3:::cdebytes-orders/*` |
| **RDS Instance** | Postgres Database | `arn:aws:rds:eu-central-1:123456789012:db:pg-prod` |

## Part 4: S3 Security Architecture — Bucket Level vs. Object Level

One of the most common pitfalls for data engineers is failing to understand the dual-tier authorization model of Amazon S3. **An S3 Bucket is not the same as the Objects inside it.**

```
+-------------------------------------------------------------------------+
| S3 Bucket Container: arn:aws:s3:::cdebytes-customers                   |
| (Governed by Bucket-Level Actions, e.g., s3:ListBucket)                |
|                                                                         |
|   +-----------------------------------------------------------------+   |
|   | S3 Object: arn:aws:s3:::cdebytes-customers/data.parquet         |   |
|   | (Governed by Object-Level Actions, e.g., s3:GetObject)          |   |
|   +-----------------------------------------------------------------+   |
|   | S3 Object: arn:aws:s3:::cdebytes-customers/image.png            |   |
|   +-----------------------------------------------------------------+   |
+-------------------------------------------------------------------------+
```

### 1. The Schema vs. Table Analogy
* **In SQL / Databases:** To query a table, you need permission on the database/schema namespace **and** permission on the individual table.
* **In S3:**
  * **The Bucket Level:** The container holding the objects. Actions like `s3:ListBucket` query the metadata inventory of the container.
  * **The Object Level:** The actual files stored inside the container (`.parquet`, `.csv`, `.png`). Actions like `s3:GetObject` or `s3:PutObject` operate on the file payloads.

### 2. The Two-Tier Permission Failure
If a policy grants:
```json
{
  "Effect": "Allow",
  "Action": "s3:ListBucket",
  "Resource": "arn:aws:s3:::cdebytes-customers"
}
```
The user can see the file names listed in the bucket directory. However, if they click or attempt to download `data.parquet`, **AWS returns Access Denied (`403 Forbidden`)** because they lack `s3:GetObject` on `arn:aws:s3:::cdebytes-customers/*`.


## S3 Storage Permissions (The Bucket vs. Object Paradox)

Next, the class investigated **Amazon Simple Storage Service (S3)**. S3 introduces a multi-tier permission hierarchy that frequently confuses new cloud engineers.

```
       [ S3 SERVICE PERIMETER ]
                  │
                  ▼
   1. BUCKET LEVEL (The Exterior House)
   ARN: arn:aws:s3:::cdebites-orders
   Actions: s3:ListBucket, s3:GetBucketLocation
                  │
                  ▼
   2. OBJECT LEVEL (The Furniture Inside the Rooms)
   ARN: arn:aws:s3:::cdebites-orders/*
   Actions: s3:GetObject, s3:PutObject, s3:DeleteObject
```

### The Ingestion Scenario (CDE Bites):
* Two distinct S3 buckets were provisioned:
  * `s3://cdebites-customers` (Contains confidential PII data: BVN, phone numbers, addresses).
  * `s3://cdebites-orders` (Contains transactional order records).
* **The Goal:** Allow the **BI Analytics Group** to list and read `cdebites-orders`, but completely block them from reading sensitive customer records in `cdebites-customers`.

### Step 1: Navigating the Console (`s3:ListAllMyBuckets`)
When students navigated to the S3 console with zero permissions, the UI threw red banner exceptions:
> `Access Denied: You do not have permissions to list buckets.`

* **The Console Quirk:** To allow the AWS S3 Console home page to display the names of existing buckets, you must grant `s3:ListAllMyBuckets`.
* **Resource Requirement:** AWS mandates that `s3:ListAllMyBuckets` **can only be applied to `"Resource": "*"`**. You cannot specify a single bucket ARN for this specific action because the console needs to scan the whole account.

```json
{
  "Sid": "AllowConsoleBucketListing",
  "Effect": "Allow",
  "Action": [
    "s3:ListAllMyBuckets"
  ],
  "Resource": "*"
}
```

### Step 2: Accessing Objects Inside a Bucket (`s3:ListBucket` vs `s3:GetObject`)
Once students could see the bucket list, clicking into `cdebites-orders` immediately threw a secondary error:
> `Access Denied: Insufficient permissions to list objects.`

Mayowa demonstrated that viewing the contents of a bucket requires **`s3:ListBucket`** mapped specifically to the bucket ARN, while reading the actual files requires **`s3:GetObject`** mapped to the wildcard path (`/*`).

### The Production Enterprise Policy (`s3-analytics-read-policy.json`)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowUserToSeeBucketListInConsole",
      "Effect": "Allow",
      "Action": [
        "s3:ListAllMyBuckets"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AllowListingSpecificBucketContents",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::cdebites-orders"
    },
    {
      "Sid": "AllowReadingObjectsInsideSpecificBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::cdebites-orders/*"
    }
  ]
}
```

```
┌────────────────────────────────────────────────────────────────────────┐
│                        S3 PERMISSION SUMMARY                           │
├────────────────────────────────────────────────────────────────────────┤
│ Target                              Required Action       Target ARN   │
├────────────────────────────────────────────────────────────────────────┤
│ 1. View all bucket names in console s3:ListAllMyBuckets   *            │
│ 2. View file names inside a bucket  s3:ListBucket         ...:::bucket │
│ 3. Download/read file contents      s3:GetObject          ...:::bucket/*
└────────────────────────────────────────────────────────────────────────┘
```

## 5.1. S3 Read-Only Policy Reference: Choosing the Right Scope

Read-only access can mean **reading object data**, **inspecting bucket configuration**, or both. Choose explicit actions and resource ARNs based on the user's actual needs rather than treating every read-only policy as equivalent.

### A. Read-Only Access to One Specific Bucket

Use this policy to list a bucket, view its region, and read its objects and object versions. Replace `my-bucket-name` with your actual bucket name in **both** resource ARNs.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::my-bucket-name"
    },
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:GetObjectVersion"
      ],
      "Resource": "arn:aws:s3:::my-bucket-name/*"
    }
  ]
}
```

**What this grants:**

- Browse object names with `s3:ListBucket`.
- View the bucket's region with `s3:GetBucketLocation`.
- Download/read objects with `s3:GetObject`.
- Read a specified object version with `s3:GetObjectVersion`. To enumerate versions, also add `s3:ListBucketVersions` to the bucket-level statement.

**What this does not grant:** Uploading or deleting objects, modifying bucket settings, changing ACLs or tags, or viewing bucket policies and other configuration.

For the S3 console's account-wide bucket list, add the separate `s3:ListAllMyBuckets` statement demonstrated in Section 5. That reveals bucket names but does not grant access to other buckets' contents.

### B. Broad S3 Read-Only Access (`s3:Get*` and `s3:List*`)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:Get*",
        "s3:List*"
      ],
      "Resource": "*"
    }
  ]
}
```

The action wildcards match **all S3 actions beginning with `Get` or `List`**, including matching actions introduced in the future. This is a broad read-only pattern similar to the AWS-managed `AmazonS3ReadOnlyAccess` policy, not a guarantee of an identical managed-policy definition.

| Action family | Examples | What users can inspect |
| :--- | :--- | :--- |
| `s3:List*` | `s3:ListAllMyBuckets`, `s3:ListBucket`, `s3:ListBucketVersions` | Bucket names, object names, and object versions |
| `s3:List*` | `s3:ListBucketMultipartUploads`, `s3:ListMultipartUploadParts` | In-progress multipart uploads and uploaded parts |
| `s3:Get*` | `s3:GetObject`, `s3:GetObjectVersion`, `s3:GetObjectTagging`, `s3:GetObjectAcl` | Object data, versions, tags, and ACLs |
| `s3:Get*` | `s3:GetBucketLocation`, `s3:GetBucketPolicy`, `s3:GetBucketTagging`, `s3:GetBucketVersioning` | Bucket region, policy, tags, and versioning status |
| `s3:Get*` | `s3:GetEncryptionConfiguration`, `s3:GetBucketLogging`, `s3:GetLifecycleConfiguration`, `s3:GetReplicationConfiguration`, `s3:GetBucketAcl` | Encryption, logging, lifecycle, replication, and bucket ACL settings |

> **Important:** This is more than "download objects." Configuration details can be sensitive, so broad read access is not automatically appropriate for every analyst or auditor. The IAM action for reading bucket encryption settings is `s3:GetEncryptionConfiguration`, not `s3:GetBucketEncryption`.

Although often used for account-wide access, `"Resource": "*"` does **not** restrict permissions to the current account. It can also authorize matching operations on resources in other accounts when their resource policies permit access.

### C. Narrower Actions for Bucket Discovery and Object Reading

If users need to see bucket names, browse objects, and download data without inspecting bucket configuration beyond its region, use explicit actions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBuckets",
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    },
    {
      "Sid": "BrowseBuckets",
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:ListBucket"
      ],
      "Resource": "arn:aws:s3:::*"
    },
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:GetObjectVersion"
      ],
      "Resource": "arn:aws:s3:::*/*"
    }
  ]
}
```

This limits **actions**, but still has a broad **resource scope**. For least privilege, replace the bucket and object wildcards with approved bucket ARNs, as in example A. Keep `s3:ListAllMyBuckets` on `"Resource": "*"` only when account-wide bucket discovery is required.

### D. Add Only the Extra Read Permissions Needed

To let users inspect bucket tags, add `s3:GetBucketTagging` to the **bucket-level** action list. For example, replace example A's first statement with:

```json
{
  "Sid": "ListBucketAndReadTags",
  "Effect": "Allow",
  "Action": [
    "s3:GetBucketLocation",
    "s3:ListBucket",
    "s3:GetBucketTagging"
  ],
  "Resource": "arn:aws:s3:::my-bucket-name"
}
```

Keep the object-reading statement unchanged. Other optional read permissions must likewise be paired with the correct resource:

| Additional action | Purpose | Resource level |
| :--- | :--- | :--- |
| `s3:GetBucketTagging` | View bucket tags | Bucket ARN |
| `s3:GetObjectTagging` | View current object tags | Object ARN |
| `s3:GetBucketVersioning` | View versioning status | Bucket ARN |
| `s3:GetEncryptionConfiguration` | View encryption configuration | Bucket ARN |
| `s3:GetBucketPolicy` | View bucket policy | Bucket ARN |

**Effective-access caveats:** These examples grant permissions; they do not explicitly deny writes allowed by other policies. Explicit denies, permissions boundaries, organization policies, and resource policies can still restrict access. Objects encrypted with SSE-KMS may also require `kms:Decrypt` on the relevant KMS key and authorization through its key policy.

## Part 5: The Enterprise Data Platform Architecture

Mayowa mapped how IAM, networking (VPC), and compute (EC2) form an interconnected triangle across modern data platforms:

```
[ Ingestion Sources ]               [ Enterprise VPC / Data Platform ]
+---------------------+             +------------------------------------------------------+
| RDS Postgres (DB A) |             |  Airbyte / Ingestion Node (EC2 Instance)             |
| RDS Postgres (DB B) | --Network-> |  - Requires IAM Role to write to S3 Data Lake        |
| RDS Postgres (DB C) |             +--------------------------+---------------------------+
+---------------------+                                        |
                                                               v
                                            +--------------------------------------+
                                            | Amazon S3 Raw Data Lake Bucket       |
                                            | (arn:aws:s3:::cdebytes-raw/*)        |
                                            +------------------+-------------------+
                                                               |
                                                               v
                                            +--------------------------------------+
                                            | dbt Transformation Engine            |
                                            | - Connects via IAM Database Auth     |
                                            | - Transforms to Amazon Redshift DWH  |
                                            +--------------------------------------+
```

1. **Airflow / Airbyte on EC2:** Compute instances require attached IAM policies (Instance Profiles) granting explicit `s3:PutObject` access to land ingested files.
2. **Database Authentication:** Instead of hardcoding plain-text passwords into pipeline configuration files, modern databases leverage **IAM Database Authentication**, verifying connecting users through short-lived cryptographic tokens.
3. **The Lesson for Data Engineers:** If your IAM policies are broken, your dbt models will fail to authenticate, your Airbyte syncs will crash with S3 permission errors, and your Airflow DAGs will stall.


## The Big Picture: How IAM, VPC & EC2 Intersect in Data Platforms

To conclude the evening, Mayowa connected these IAM fundamentals to the wider analytics ecosystem:

```
                               THE CLOUD DATA PLATFORM
 ┌─────────────────────────────────────────────────────────────────────────────────────┐
 │  VIRTUAL PRIVATE CLOUD (VPC - Private Network Isolation)                            │
 │                                                                                     │
 │  ┌───────────────────────┐                    ┌──────────────────────────────────┐  │
 │  │      EC2 SERVER       │                    │          AMAZON RDS              │  │
 │  │  (Runs Apache Airflow │ ── Private VPC ──> │      (Transactional OLTP)        │  │
 │  │   or Airbyte Engine)  │     Networking     │   Requires DB Auth & Security Grp│  │
 │  └──────────┬────────────┘                    └──────────────────────────────────┘  │
 │             │                                                                       │
 └─────────────┼───────────────────────────────────────────────────────────────────────┘
               │
               ▼ IAM Role Authorization (Instance Profile)
 ┌─────────────────────────────────────────────────────────────────────────────────────┐
 │  OBJECT STORAGE (AWS S3) & DATA WAREHOUSING (Amazon Redshift / Snowflake)           │

```

1. **Airflow / Airbyte Runs on Compute (EC2):** They do not run in thin air; they execute on Linux servers.
2. **Network Traffic Stays in the VPC:** Airflow cannot extract records from an internal RDS database without proper VPC security groups, subnets, and routing tables.
3. **IAM Governs Everything:** Even with valid database passwords and open network routes, Airflow cannot write raw files into S3 or trigger a Redshift query without an attached **IAM Role (Instance Profile)** carrying explicit S3 write policies.

### Demo 1: Scoped IAM User Deletion Using Wildcard Pattern Matching

#### Objective
Author a custom IAM policy that grants permission to delete **only** users whose names contain the string `staging` (e.g., `airflow-staging-user`, `staging-test`), attach the policy to targeted student groups, prove that deletion of non-staging users is blocked, create a staging user, and successfully delete it.

```
       [ Client / Student Operator ]
                     |
                     v
       +----------------------------+
       |   Attempts iam:DeleteUser   |
       +--------------+-------------+
                      |
        +-------------+-------------+
        |                           |
        v                           v
[ Target: osas ]            [ Target: airflow-staging ]
Policy Check: Matches *staging*?
        |                           |
        v                           v
❌ DENIED (AccessDenied)     ✅ ALLOWED (User Deleted)
```

#### Step-by-Step Instructions

##### 1. Author the Scoped Policy in JSON
Open your local code editor (VS Code) and construct the policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DeleteStagingUsersOnly",
      "Effect": "Allow",
      "Action": [
        "iam:DeleteUser"
      ],
      "Resource": "arn:aws:iam::123456789012:user/*staging*"
    }
  ]
}
```
*(Replace `123456789012` with your actual 12-digit AWS Account ID).*

##### 2. Deploy the Policy in the AWS Console
1. Navigate to **IAM Console** $\rightarrow$ Click **Policies** $\rightarrow$ Click **Create policy**.
2. Toggle to the **JSON** tab in the editor.
3. Paste the JSON document authored above.
4. Click **Next**.
5. Set **Policy name** to: `Group_XX_DeleteStagingUserPolicy`.
6. Set **Description** to: `Allows deletion of IAM users with staging in their name`.
7. Click **Create policy**.

##### 3. Attach Policy and Baseline Read Permissions
1. In the IAM Console, navigate to **User groups** $\rightarrow$ Select your group (e.g., `Group_25`).
2. Under the **Permissions** tab, click **Add permissions** $\rightarrow$ **Attach policies**.
3. Search for and select the AWS-managed policy: `IAMReadOnlyAccess` *(allows members to see the IAM dashboard and list users)*.
4. Search for and select your newly created custom policy: `Group_XX_DeleteStagingUserPolicy`.
5. Click **Add permissions**.

##### 4. Negative Test: Attempting Unauthorized Deletion
1. Log in to the AWS Console as an IAM user belonging to `Group_25`.
2. Navigate to **IAM** $\rightarrow$ **Users**.
3. Select an existing user that does **not** contain the word `staging` (e.g., user `osas` or `mayowa`).
4. Click **Delete**. Type the user name and click **Delete user**.
5. **Expected Error Output:**
   ```
   User: arn:aws:iam::123456789012:user/student is not authorized to perform: 
   iam:DeleteUser on resource: arn:aws:iam::123456789012:user/osas 
   because no identity-based policy allows the iam:DeleteUser action
   ```
   *The operation is successfully blocked by the policy engine.*

##### 5. Positive Test: Successful Authorized Deletion
1. As an administrative user, create a temporary testing user:
   * Navigate to **IAM** $\rightarrow$ **Users** $\rightarrow$ **Create user**.
   * User name: `airflow-staging`.
   * Uncheck *Provide user access to the AWS Management Console* (API-only user with no credentials).
   * Click **Next** $\rightarrow$ **Next** $\rightarrow$ **Create user**.
2. Switch back to the student user window and refresh the **Users** list.
3. Select `airflow-staging`.
4. Click **Delete** $\rightarrow$ Confirm the deletion prompt.
5. **Result:** The user is deleted cleanly:
   ```
   User "airflow-staging" deleted successfully.
   ```

### Demo 2: Granular Multi-Statement S3 Governance (List Buckets vs. Object Scoping)

#### Objective
Construct a robust, production-style multi-statement IAM policy that permits a user to:
1. List all S3 buckets in the AWS Console (avoiding console crash errors).
2. Read, list, and download objects **exclusively** from a specific business bucket (`cdebytes-customers`), while blocking access to sensitive buckets (`cdebytes-orders`).

```
                              [ IAM User / Group ]
                                        |
                 +----------------------+----------------------+
                 |                                             |
                 v                                             v
        [ s3:ListAllMyBuckets ]                        [ s3:GetObject ]
        Resource: "*"                                  Resource: "arn:aws:s3:::cdebytes-customers/*"
                 |                                             |
                 v                                             v
     Lists all bucket names                        Can download files from
     in the S3 Console                             cdebytes-customers ONLY!
                                                   (cdebytes-orders = 403 Forbidden)
```

#### Step-by-Step Instructions

##### 1. Author the Multi-Statement Policy in VS Code
Create a policy containing two distinct statements: one for bucket listing across the account, and one scoped strictly to the target bucket's object ARN:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowConsoleBucketListing",
      "Effect": "Allow",
      "Action": [
        "s3:ListAllMyBuckets",
        "s3:GetBucketLocation"
      ],
      "Resource": "*"
    },
    {
      "Sid": "AllowSpecificBucketObjectAccess",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::cdebytes-customers",
        "arn:aws:s3:::cdebytes-customers/*"
      ]
    }
  ]
}
```

* **Why `arn:aws:s3:::cdebytes-customers`?** Governs `s3:ListBucket` (inspecting folder and file inventories inside the bucket).
* **Why `arn:aws:s3:::cdebytes-customers/*`?** Governs `s3:GetObject` (downloading and viewing specific file payloads).

##### 2. Deploy and Attach the S3 Governance Policy
1. Navigate to **IAM Console** $\rightarrow$ **Policies** $\rightarrow$ Click **Create policy**.
2. Select the **JSON** tab and paste the multi-statement policy above.
3. Click **Next**.
4. Policy name: `Group_XX_CustomersS3AccessPolicy`.
5. Click **Create policy**.
6. Attach this policy to your targeted student group (e.g., `Group_18`).

##### 3. Verify Console Listing & Object Permission Isolation
1. Log in to the AWS Console as a member of `Group_18`.
2. Navigate to the **Amazon S3 Console** $\rightarrow$ Click **Buckets**.
3. **Verification 1 (Bucket Visibility):**
   * You can see all buckets in the account (`cdebytes-customers`, `cdebytes-orders`, `cdebytes-staging`).
   * No permission error banners appear at the top of the console.
4. **Verification 2 (Authorized Access):**
   * Click on `cdebytes-customers`.
   * You can see the files listed (`customer_data.parquet`, `profile.png`).
   * Select `customer_data.parquet` and click **Download** or **Open**.
   * **Result:** The file downloads successfully without errors.
5. **Verification 3 (Unauthorized Access Enforcement):**
   * Navigate back to **Buckets** and click on `cdebytes-orders`.
   * **Result:** An immediate error banner appears:
     ```
     Insufficient permissions: You do not have permissions to list objects in this bucket.
     (Service: Amazon S3; Status Code: 403 Forbidden; Error Code: AccessDenied)
     ```
   * You cannot view, inspect, or download any transaction records in `cdebytes-orders`.
